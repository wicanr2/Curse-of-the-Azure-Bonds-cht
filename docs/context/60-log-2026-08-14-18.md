## 2026-08-17（第 565–568 輪）：法術覆蓋的分母歸零

戰鬥可施放的 79 支法術裡有 6 支職業模型不支援（德魯伊，表裡沒有職業 3），
可宣告的分母是 **73**。最後 23 支逐支讀完之後 **73／73**，
`handler`／`visual`／`sound` 三欄都是 observed（spec 1125）。

三個判讀上會反過來咬人的點：

- **解除魔法**的對抗是「相同 50%、高出去每級 ＋5、低下去每級 −2」——
  兩個方向的係數不一樣。
- **移除詛咒**先拿掉效果 `24h`；拿掉了就結束，沒拿掉才解開第一件詛咒裝備的
  **已裝備**旗標（詛咒本身還在）。
- **疾病**的 `2Bh`／`2Ch` 是**效果 `22h` 的 handler** 掛的，不是法術掛的，
  所以規則要寫在效果那一側。

覆蓋稽核本身也修過：先前只讀 `combat_state.go` 又靠函式名猜 behavior，
把 48 支的 sound 讀成沒有。**那是量測的洞，不是覆蓋的洞**——改成掃整個
`internal/game` 並跟著分派表找真正的施法函式之後 sound 73／73 observed。

演出那一側（spec 1126）：原作不是「一支法術一套圖」。整個遊戲只用三個槽
（18 共用施法投射物、19 閃電電弧、23 魔法命中），而**共用投射物在 `CASTSPELL`
裡、分派到 handler 之前就播**，所以每一支法術都有演出。`槽 = COMSPR 區塊 + 13`。

## 2026-08-18（第 569–571 輪）：README 五張圖背後的四類對齊錯誤

使用者逐張指出 README 圖不對。量下去是同一類問題：**兩層各自算座標，然後對不上**
（spec 1130）。

| 症狀 | 真正的原因 |
|---|---|
| 黃框裡的人像沒佔滿 | sub-image 當繪製目的地時**只裁切**，座標仍是母圖的；呼叫端多扣了一次 `clip.Min` |
| 人站在綠色灌木上 | 地形層沒過相機與鏡像，與戰鬥員走的不是同一條座標路徑 |
| 人站在牆裡、四隻蜘蛛全不見 | 同上 ＋ 敵方縱帶 `7..9` 落在七欄視野外 ＋ 佈陣不看地面 |
| 3D 組成可疑 | 幾何與 spec 1006 逐項相符；問題是**一大半牆磚根本沒畫出來** |

最後一格拉出 spec 1131：`Put8x8Symbol` 把符號編號切成五段，
**第 0 段（`1..45`）是全遊戲共用的一份，先前完全沒載**。它就是 `8X8D1.DAX`
的 `0CBh`——六個 `8X8D*.DAX` 裡唯一一個 45 項的區塊，內容是天空格與斜邊收邊磚。
而且 **EGA index 13（洋紅）是透明鍵不是顏色**，不遮罩會在牆角畫出桃紅三角形。

順帶抓到兩件事：checkpoint 開戰時**完全沒有地形**（三支戰鬥地形投影裝在
`RunGame` 前一行，而確定性 checkpoint 在那之前就已經 `StartCombat`），
以及戰鬥地圖與畫面可以是**兩份**（spec 1132：戰鬥地圖由地城座標生成，
劇情流程會在開戰前移動隊伍，而地圖還是啟動時生的那一份）。

## 2026-08-18（第 572 輪）：第一人稱畫面與原版逐格比對

提爾佛頓五格 × 四個朝向、共二十張畫面與原版逐格比對：**十九張完全相同，
一張差一格**（spec 1134）。修的是天花板——`indoor_sky_color` 宣告成 0（黑），
原版的 runtime 值是 9（白）。

★ 那兩個數字取自原版**在地圖上**紮營存檔寫出來的 `Area1`。從**選單**存的那一份
兩個都是 0：**同一支存檔常式，存的時機不同，欄位意義不同**。

取 oracle 的方式從「猜一整串定時按鍵、等一輪、看結果」換成容器常駐、逐步送鍵、
每一步把畫面上的 8×8 文字格讀成字串再決定下一鍵。先前那條路已經燒掉約 50 輪
擷取，而錯位的鍵可能剛好按到 `EXIT TO DOS`。

過程中被誤讀的一個症狀值得記著：合成存檔載入後「按下槽的字母就回主選單」
看起來像原版拒絕讀檔，實際上是**隊伍載入為空**——檔名欄指到不存在的檔案時
原版不報錯、直接跳過那名角色。**沒有錯誤訊息的失敗，症狀會長得像另一個問題。**

天空色的來源查到一半：那兩個欄位每次進地圖都會重算（清成 0 會變回來），
而改存檔的 `Current3DMapBlockID` 到不了別的地圖（同樣被重算）。靜態掃描在
全 overlay 找不到寫入，但 **disp16 掃描結構上抓不到指標間接寫入**，
所以那只能當弱證據；下一步要用 runtime watchpoint。

## 2026-08-18（第 573–576 輪）：回合開始、突襲遮罩、面向、扇形

回合開始那一段逐項對回原作（spec 1135）。先攻是
`敏捷遠程命中調整(overlay-24 entry#11) + 1d6`，夾底 1；`20` 從擲骰擲不出來
（上限 11），它是快速戰鬥的哨兵值，回合開始再夾成 19。

**修掉一個玩家看得到的 bug**：`CHECKFX(07h)`（「這個人這一回合動得了嗎」）
原本只有 AI 那一側走得到，玩家控制的隊員完全套不到——纏繞術那一族的
效果 `88h` 對隊員沒有作用。原作是在**分派到 AI 或玩家選單之前**就呼叫。
負對照拿隊員測（拿敵人測會過，什麼都證明不了）。

**突襲遮罩（`Area2+596h`）是死碼**（spec 1136）：整個 DOS 與 PC-98 build 裡
只有先攻讀它一次、戰鬥主迴圈清 0 一次，沒有任何地方寫進非 0。所以先攻的
`−6` 那一支走不到，CoAB 一律傳 0 是有證據的值，不是預設值。三重補強：
正對照（同一份掃描抓得到別的欄位的寫入）、指標間接掃描、PC-98 第二證人。

`+18Dh^[7]`（保留中的機會攻擊）的**設定端是 GUARD**（`overlay-24 entry#35`，
印字串 `Guarding`），設定／消費（spec 817）／清除（回合開始）三段接起來。

面向那一格（spec 1137／1138）踩到一個普查方法的洞：`es:[暫存器+位移]` 的掃描
**認不出這個遠指標指向哪一種記錄**，所以「七處分支」裡有兩處根本不是戰鬥狀態
（一處是角色記錄的智力基底、一處是 LOS 的 Bresenham 狀態）。普查要先看到
`les …, es:[…+18Dh]` 才算數。

`+09h` 的幾何意義**兩個寫入端互相矛盾**（攻擊動作寫 `(d+4) mod 8`，轉向記帳
比較時沒有那個 `+4`），所以只做字面移植，不解釋欄位。第二個 AC 欄位 `+19Bh`
的算法還沒讀，用 `ArmorClassFacingKnown` 擋住——機制接上、條件測得到、數值留白。

90° 扇形判斷（`overlay-31:054Ah`，PC-98 符號名 **`INARC`**）八個方向逐條讀完
（spec 1002）。八段是**同一個形狀**：兩支半平面判斷取聯集，程式長度都是
0x55 bytes；正交向的兩支互為鏡像，斜向的兩支是被對角線切開的兩個 45° 楔形。
接上 spec 1010（PC-98 符號名 `CHECKPARTINGBLOWS`）的機會攻擊面向閘：
朝向 −2..＋2 五個方向任一成立就打得到，先攻未歸零或這一輪還沒動過時整段跳過。

★ **錐的頂點是起點往前一格，不是起點**。拿起點當頂點推，正西方的目標會算成
「三個方向都收得到」，實際上只有正西那一支收得到。

## 2026-08-18（第 577 輪）：第二個 AC 解出來，順帶量到刻度不一致

`+19Bh` 的算式在派生數值重算的收尾（spec 1000 §七）。關鍵是 `var_D` 是
`[bp−0Dh]` 起的**五個位元組**，也就是 `var_D`／`var_C`／`var_B`／`var_A`／`var_9`
這五格；`+19Ah` 是五格全加，`+19Bh` 只加其中三格再減 2。相減得到

> `+19Bh ＝ +19Ah − 敏捷防禦調整 − 盾牌那一槽 − 2`

——AD&D 1e 的背後攻擊正是抵銷盾牌與敏捷加值並給 ＋2 命中。

拿原作資料驗過：六章 `MON*CHA` 共 81 筆，78 筆殘差 0，另外三筆是 1、1、2
（DARK ELF LORD 兩筆、TYRANTHRAXUS）——正好是 ＋1／＋2 盾牌。
**盾牌那一槽的加值靜態讀不到（表在 BSS），但殘差把它量出來了。**

★ 投影到 `Fighter` 搬的是**差值**不是絕對值：`monster.CombatArmorClass` 會把
儲存值反轉成顯示值，而命中判定是 `attackTotal >= AC`（數字小才好打），
直接搬 `+19Bh` 會讓背後攻擊變成更難打——而且兩種寫法在「有沒有換到第二個 AC」
上看起來一模一樣。

順著這條線量到一件更大的事：**AC 與命中的刻度在三個地方不一致**。
真實怪物匯進來是 AC 1..7、命中加值 41..53，`d20 ＋ 41 >= 1` 永遠命中；
隊員那一側是 AD&D 降序的 AC 配升序的判定，敏捷越高反而越好打。
原作的對照是 FIRE KNIFE 儲存命中 41、儲存 AC 59 ⇒ 需要 d20 ≥ 18
（畫面 THAC0 19／AC 1）。這一項列進 WORKLIST 沒有動——統一刻度會改到
隊員模型、怪物匯入、效果修正與整批戰鬥測試。

## 2026-08-20（第 578 輪）：AC 與命中的刻度統一

先把證據看齊再動手。`ATTEMPTTOHIT`（DOS `overlay-23:123Fh`）65 條逐條讀完，
宣告順序是**兩個遠指標在前、門檻在後**：加進骰值的是**攻擊者**的 `+199h`，
比較的門檻是傳進來的那個 byte ＝ 防禦者的 AC。`sub_14E8` 挑好三段 AC 之一
就是送進這裡當門檻。

> `d20 ＋ 攻擊者^[199h] ＋ v >= 目標 AC`（儲存值越大越難打）

remake 統一用**顯示刻度**（AD&D 習慣：AC 越小越難打）。兩邊各減一個常數之後
命中式是 `d20 ＋ 命中加值 ＋ 目標 AC >= 20`——同一個函式。
FIRE KNIFE（`+199h ＝ 41` ⇒ THAC0 19、`+19Ah ＝ 59` ⇒ AC 1）自己打自己
原作要 18，remake 也是 18。

選顯示刻度而不是儲存刻度的理由是量出來的：`ArmorClass` 在程式碼裡出現 430 次，
其中 367 次在測試，而那些測試寫的是 AD&D 值（`AC 10 ＋ 命中加值 20` 這種
「一定打得中」的組合）。改成儲存刻度會讓那組數字變成「一定打不中」，
整批測試要重寫；改判定式則一條都不用改。**修完全套測試只紅了自己新加的兩條。**

順著這條線，程式碼裡原本就寫成降序意圖的地方一次全部變正確：隊員的
`10 − (敏捷 − 10) / 2`、`ArmorClass -= 護甲改善`、除錯用的 `ArmorClass = −10`
（不死身）——它們本來都是反的，現在都對了。**這是「選對域」的旁證**。

換算點四處：怪物匯入、`CanHitTarget` 的呼叫端、ECL 隊伍戰力
（`AC > 60`、`命中 > 39` 才算分，一看就是儲存刻度）、`CHECKFX` 的護甲記錄寫入
（`add_capped 2 cap 60`，上限 60 就是儲存值的 AC 0）。

★ 第二個護甲欄位的換算**由第一格決定**：`+19Bh` 系統性地比 `+19Ah` 小 2..8，
會掉出 `CombatArmorClass` 的 `50..70` 視窗——各判各的會變成一格換、一格沒換，
而症狀只是「背後攻擊的 AC 有點怪」。

## 2026-08-20（第 579 輪）：機會攻擊的四道閘、隊員的命中與 AC 表

三項「還開著」的收尾，其中一項根本不是開著的。

**`v` 早就接好了。** 命中式裡那個由攻擊者隊號選的修正是 bank 1 的
`+6E0h`／`+6E2h`，而 bank 1 的映射是 `(ECL 位址 − 7C00h) × 2` ——換算回去就是
ECL 的 `7F70h`（敵方側）與 `7F71h`（隊伍側），劇情用 `SAVE` 寫進去，
remake 接在 `SetSideAttackRollModifier`（spec 390）。**把兩份既有結論放在一起
就有答案，不必再查。**

**機會攻擊的四道閘**：三道靠既有資料解得出來，一道要讀 DOS 側的原始位址。
`overlay-24 entry#6` 的四個效果碼在台帳裡記的是 `49D3h`——那是 PC-98 的位址，
DOS 側是 `27C9h`，而且落在 BSS 界線之前，直接讀得出 `33h 34h 35h 1Fh`。
那四個就是 `CHECKFX(07h)`（這一回合動得了嗎）的成員。
`sub_1144` 的兩個 far call 解出來都是 `CHECKFX`，而時機 `00h` 在 CoAB 是空的、
`01h` 全是可見性那一組 ⇒ 整道閘就是「看得見離場的人嗎」。

★ **子集不是同一組**：那四個碼是 `MonsterIsHeld` 五個碼的子集，少一個 `1Bh`。
借用現成的判斷會多擋一個效果，而症狀只是「某些情況下沒有機會攻擊」。

**隊員的命中與 AC**：`+73h` 的算法在 TRAINING（`overlay-17:0782h`）——八個職業槽
各查 `DS:3E38h`（每槽 13 bytes，索引是等級）取最大值。表在資料段讀得出來，
逐格對回 AD&D 1e 的三組攻擊進程；職業槽的名字來自 game pack 既有的
`class_slots`，兩者對上是**獨立的交叉驗證**。建角另有兩個預設值
`+124h = 32h`（AC 10）與 `+73h = 28h`（THAC0 20）。

★ 一個讀錯的分支被測試當場抓到：空槽那條 `jle` 跳到的是迴圈**尾巴**不是出口，
所以是 continue 不是 break。聖騎士只有槽 3 有等級，讀成 break 會在槽 0 就結束。

★ engine 的測試在寫的時候當場抓到一個文件錯誤：`AccountTurn` 問分類器的是

跨 repo 的流程：engine 側 commit → `tools/engine-proxy.sh` → CoAB
`tools/go.sh get <印出來的版本>`。⚠ engine repo 的 push 需要另外授權，
沒 push 之前 `go.sum` 指到的 commit 只存在本機。

## 2026-08-20（第 581 輪）：力量的命中與傷害調整，以及一份原版存檔的 oracle

spec 694／697 早就把三張表讀完了，這一輪是把它們接上——表放進 engine 的
`combat/ability`（與敏捷防禦調整同一個 package），CoAB 只留 `+125h` 那道閘。

★ **`+125h` 不是「玩家角色」的同義詞**：建角寫 1、全 build 沒有任何地方寫 0，
但六章 `MON*CHA` 的 81 筆記錄裡 **61 筆是 0、20 筆是 1**。怪物那一側兩種都有。

★ **傷害表的索引 19 是單獨一格（＋3）**，不是 `i − 17` 那一段的一部分。
寫成一段會讓 18/01–50 的角色少一點傷害加值——engine 的表格測試當場抓到。

| 欄位 | 記錄 | 重算 |
|---|---:|---|
| `+73h` | 44 | 職業命中表 slot 2 等級 5 |
| `+199h` | 45 | `44 ＋ 力量命中 1`（索引 19） |

## 2026-08-20（第 582 輪）：讓乾淨 clone 建得起來

兩個東西都不在 CoAB 的版控裡——`golden-box-remake-engine/`（獨立 repo）與
`workplace/`（工作目錄，檔案型 proxy 放在裡面）。所以**剛 clone 完的 CoAB
既沒有 engine 原始碼、也沒有 proxy**，而 engine 是私有 repo，
`proxy.golang.org` 取不到、容器裡又不該放 GitHub 憑證。

`tools/engine-bootstrap.sh` 補上這一段：從 `go.mod` 讀出鎖住的 pseudo-version、
取尾巴那 12 碼當 commit、需要時 clone 或 fetch engine，再用那個 commit 重建
proxy，最後核對打包出來的版本與 `go.mod` 一致。

★ **不 checkout、不動 engine 的工作區**——`git archive <commit>` 不需要工作區
配合，硬要 checkout 只會踩掉開發者自己在 engine 上的改動。

順帶放寬 `engine-proxy.sh` 的髒工作區檢查：那道檢查只在**沒有指定 commit**
（要打包 HEAD）時才有意義，明確指定 commit 時打包內容毫無歧義。不放寬的話，
