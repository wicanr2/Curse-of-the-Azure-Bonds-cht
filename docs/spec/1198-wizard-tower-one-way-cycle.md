# 1198：巫師塔那四格為什麼繞不出來——單向環 ＋ 路線沒有放手條件

狀態：`READY`
證據等級：一手（原版 `GEO5.DAX` 位元組、`ECL5.DAX` 位元組碼、可重跑的按鍵實測）

## 現象

按鍵重放走到哈普托斯（Haptooth）巫師塔之後，隊伍在四格之間打轉，
再多幀也一樣：

| 幀數上限 | 走過的格 | 記到的話 | 最後一次有新東西 |
|---:|---:|---:|---:|
| 2,600 | 245 | 200 | 第 1,961 幀 |
| 6,000 | 245 | 200 | 第 1,961 幀 |
| 15,000 | 245 | 200 | 第 1,961 幀 |

停滯報表指名那四格：`0x33(4,2)`、`0x33(4,3)`、`0x33(5,2)`、`0x33(5,3)`，
各繞了 157–163 次。**幀數不是瓶頸**——三個量級的上限停在同一幀。

## 一、地圖本身是一個單向環

`GEO5` 段 `0x33` 那四格的牆面（`cmd/geo-wall-grid`，nibble ＝ 北 1／東 2／南 4／西 8）：

| 格 | 牆 | 走得出去的方向 |
|---|---|---|
| `(4,2)` | `9` ＝ 北＋西 | 東、南 |
| `(5,2)` | `3` ＝ 北＋東 | 南、西 |
| `(4,3)` | `C` ＝ 南＋西 | 北、東 |
| `(5,3)` | `6` ＝ 東＋南 | 北、西 |

四格互相之間**只有一個方向通**：
`(4,3)→北→(4,2)→東→(5,2)→南→(5,3)→西→(4,3)`。
這是一個**單向四格環**，而且四面朝外的方向全部是牆。

⚠ 這不是解析錯誤。原始平面對得上：`(4,2)` 的平面 0 是 `60`（北面牆型 6、東面 0）、
平面 1 是 `05`（南面 0、西面 5），四面合起來正是 `9`。

⚠ 也不是「走不出去」。同一格的**細節平面**（平面 3，四個 2-bit 欄位，
順序北／東／南／西）寫著門：

| 格 | 細節位元組 | 解出來 |
|---|---|---|
| `(4,2)` | `01` | 北面是門（值 1 ＝ 可通行）|
| `(5,3)` | `04` | 東面是門 |

引擎的 `CanMoveDungeonWrapped` 早就照這條規則走，`cmd/geo-move-mask` 印出
`(4,2)` 的可走遮罩是 `7`（北＋東＋南）。**地圖沒有把人關起來，走位那一側才有問題。**

## 二、`routeDead` 結構上擋不住這一種卡法

重放端有兩層保險，但兩層都不管用：

- `routeDead` 數的是「路線說往這邊走、按下去**沒動**」。環裡每一步都**真的走得動**，
  所以一次都不會被判死。
- 選單那一側有放手條件（`menuSinceProgress > routeMenuPatience`），**走位那一側沒有**。

⇒ 路線把隊伍鎖在環裡，而兩層保險都認為一切正常。這正是
`~/.claude/rules/00-rules-index.md` 那條「固定參數重試 N 次不是實驗，是抽樣」的
實例：加幀數是在同一個世界裡多取樣，不會換到另一個世界。

## 三、修法與量測

走位比照選單加一個放手條件：同一格從上一次有新東西到現在已經照路線走過
N 次，就不再問路線，交給啟發式。

實測（2,600 幀，同一份路線）：

| 耐心 | 走過的格 | 記到的話 | 最深的段 |
|---:|---:|---:|---|
| 1 | 111 | 66 | `0x02` |
| **2** | **342** | **225** | **`0x51`** |
| 3 | 335 | 215 | `0x33` |
| 4 | 280 | 205 | `0x33` |
| 8 | 279 | 205 | `0x33` |
| 16 | 274 | 205 | `0x33` |

⚠ 選單那一側的 8 不能照搬：一個選單按錯只浪費一幀，走位按錯會讓隊伍**離開**
原本站對的那一格，代價高得多，所以放手要早。耐心 1 又太早——連提爾佛頓都走不完。

放寬幀數之後（耐心 ＝ 2）：

| | 走過的格 | 記到的話 | ECL 段序列 |
|---|---:|---:|---|
| 修好之前 | 245 | 200 | …→`0x32`→`0x33`（到此為止）|
| 修好之後（5,000 幀）| **452** | **262** | …→`0x32`→`0x33`→`0x32`→`0x33`→`0x50`→`0x51`→**`0x10`** |

隊伍現在會進出巫師塔、回世界地圖、再進第三章的地城（`ECL3/0x10`）。
落回原文仍是 0 句。

## 四、順帶查清楚的塔內機制（尚未實作驗收）

`ECL5/0x33` 的 entry 0 在 `0x07A3`，開頭就是
`AND C04F, 7F → 7F7A`——**地形碼的低 7 位是這一格的樓梯編號**，
而 `cmd/ecl-cell-events` 只列得出 `ON GOTO` 那張 10 格的表，
所以 10 以上的編號（塔內的樓梯）在那份對照表裡是看不到的。

樓梯是**查表**驅動的（`0x090C` 起）：

```
090C GETTABLE 9C81[7F7A] → 7F79    ; 這道樓梯要求的朝向
0916 COMPARE  C04D, 7F79
091D IF <>
091E EXIT                          ; 朝向不對 → 什麼都不會發生
091F PRINTCLEAR "THE STAIRS LEAD"
092E GETTABLE 9C96[7F7A] → 7F79    ; 0 ＝ UP、1 ＝ DOWN
0942 PRINT     "HERE. DO YOU WANT TO TAKE THEM?"
096A GETTABLE 9C6D[7F7A] → C04B    ; 目的地 X
0974 GETTABLE 9C77[7F7A] → C04C    ; 目的地 Y
```

⇒ 五層樓共用同一張 16×16 地圖，樓層之間是**不相連的區域**，只有樓梯事件接得起來；
「站對方向踏上去」就是 `0916` 那一條比較。塔內出現的地形編號有
`0A`、`0B`、`0C`、`0E`、`0F`、`11`、`12`、`13`、`14`。

進塔的落點也是腳本寫的，不是引擎放的（`ECL5/0x32` `0x0537`）：

```
0513 PRINTCLEAR "YOU ARE HEADING UP INTO THE WIZARD'S TOWER."
0537 SAVE 07 → C04B
053D SAVE 0F → C04C
0543 SAVE 03 → C04D
0549 NEWECL 33
```

與 gamepack 宣告的 `(7,15,6)` 一致。
