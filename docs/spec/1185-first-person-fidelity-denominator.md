# 1185 — 第一人稱 fidelity：585 種畫面，已比過 40 種

- 證據等級：`exact`（原版 GEO 逐格計算）＋ `derived`（可見性模型取自 spec 1130
  的第一人稱幾何；遮蔽規則寫在下面，可以被推翻）
- 上游：spec 1134（原版第一人稱 oracle 與逐格比對）、spec 1130（幾何與框）
- 產物：`cmd/fp-screen-plan`、`docs/audit/fp-screen-plan.md`

## 問題

原版截圖 oracle 第 572 輪就建好了（`tools/dos-oracle-session.sh` 那六支），
spec 1134 也用它比過提爾佛頓的 20 張畫面。**缺的不是工具，是分母**——沒有一份
「該比哪些畫面」的清單，20 這個數字就沒有母數，於是 UI fidelity 永遠只能寫成
一句「尚未逐張比對」。

## 兩個軸要分開算

第一人稱畫得對不對有兩件互相獨立的事：

| 軸 | 決定於 | 分母 |
|---|---|---|
| **幾何**：哪裡該畫一面牆、透視怎麼收斂 | 視野內牆的**有無** | 相異的可見牆面配置 |
| **貼圖**：那面牆用哪一張牆磚 | `LOADWALLSET` ＋ 地圖宣告，與站在哪一格無關 | 相異的**牆型值** |

## 結果

| 項目 | 數 |
|---|---:|
| `first_person` 地圖 | 18 |
| 格子 | 4,608 |
| 其中四面都是牆的 | 187 |
| 格子 × 四個朝向 | 18,432 |
| **相異的可見牆面配置（幾何）** | **585** |

18,432 張畫面裡真正長得不一樣的只有 585 張。逐張比對因此是**做得完**的事。

spec 1134 那 20 張換算成簽章只蓋掉 **12 種**——同一條走廊上的五格朝同一個方向
看到的常常是同一張畫面。`-covered` 同時排出「接下來拍哪一格」：貪婪法，
每一列是「一次能蓋掉最多還沒蓋到的簽章」的格子，一格拍四個朝向。

第 669 輪照那張清單補拍了提爾佛頓的五格（`(0,0)`、`(3,2)`、`(3,3)`、`(4,3)`、
`(1,6)`），**12 → 31 / 585**。二十張新畫面與 remake 逐格比對的結果：
**十八張完全相同，兩張不同**。

## ⚠ 找到一個差異：`(1,6)` 朝北與朝南

| 畫面 | 不同的取樣點 | 顏色類別（原版 → remake）|
|---|---:|---|
| `(1,6)` N | 48 | `8→7 ×13`、`7→8 ×11`、`0→8 ×8`、`15→7 ×7` |
| `(1,6)` S | 48 | 完全相同的四類 |
| `(1,6)` E／W | 0 | — |

那一格的牆是 `[N=0, E=0Eh, S=0, W=0Eh]`（terrain `95h`）：**朝東西是正面對著
`0Eh` 那面牆，兩張都完全相同；朝南北才是把 `0Eh` 當側牆畫進透視**，而那兩張
就是不同的兩張。

差異全部是**顏色類別的互換**（8 與 7 對調，再加 `0→8`、`15→7`），沒有任何一個
形狀位移 ⇒ 指向**明暗配對**而不是幾何。

### 判準格 `(1,8)`：假說成立，而且順便驗到簽章模型本身

`(1,8)` 的牆與 terrain 與 `(1,6)` 完全相同（`[N=0, E=0Eh, S=0, W=0Eh]`／`95h`），
所以它們的**簽章是同一個**。第 670 輪把它拍下來比對：

| 畫面 | 不同的取樣點 | 顏色類別 |
|---|---:|---|
| `(1,8)` N | 48 | `8→7 ×13`、`7→8 ×11`、`0→8 ×8`、`15→7 ×7` |
| `(1,8)` S | 48 | 同上 |
| `(1,8)` E／W | 0 | — |

**與 `(1,6)` 逐項相同**。兩件事同時成立：

1. `0Eh` 當側牆畫時 remake 與原版不同，兩格獨立重現。
2. ★ **簽章相同的兩格真的畫出同一張畫面**——連差異都一模一樣。這是 585 這個
   分母的定義第一次被實測驗到，而不是只有推理。

## ⚠ 「不是有磚被丟掉」是錯的——而錯法本身值得記

第一次查的時候，我把 `prepareWallPreview` 裡三處靜默 `continue`（畫面外、
共用符號編號超界、`RGBA` 失敗）全部加上輸出，重畫一次 `layout=8 type=14`
**一次都沒觸發**，於是判定「22 格全部畫出來了」。

那三處全在 `BuildWallLayout` **回來之後**。真正的丟棄在它**裡面**：

```go
picture, item, symbolID, ok := piece.WallSymbolItem(record, slice, index)
if ok {                       // ← ok=false 的格子不會被 append
    stamps = append(stamps, …)
}
```

⇒ 儀器裝在錯的一層，量到的零是**沒有涵蓋到那條路徑**。這與本專案反覆踩過的
假零是同一個形狀，只是這一次的「掃描範圍」是**程式的哪一層**而不是資料的哪一段。
**下「沒有發生」的結論之前，要先確認儀器裝在事情真的會發生的那一層。**

## 成因：符號編號跨段，而查表只看記錄自己那一段

逐格印出那 2×2 磚實際蓋上去的符號之後：

| 格子 | WALLDEF 要的編號 | 實際畫出來 |
|---|---:|---|
| r8 c10 | 225 | ✅ 第 3 段第 39 項 |
| r9 c9 | 33 | ✅ 共用段 |
| **r8 c9** | **185** | ❌ 沒有 |
| **r9 c10** | **185** | ❌ 沒有 |

`PieceSet.WallSymbolItem` 只在**這一筆記錄自己掛的那一段**裡找符號：

```go
item = int(id) - int(SymbolSetBase[p.SymbolSetIDs[record]])
if item < 0 || item >= int(picture.ItemCount) { return …, false }
```

`0Eh` ⇒ `wallSet = 3`，記錄掛第 3 段（基準 `BAh` ＝ 186）。而 WALLDEF 引用的
`185` 是**第 2 段的最後一項**（基準 `74h` ＝ 116）⇒ `185 − 186 = −1` ⇒ 丟掉。

**段是由編號本身決定的，不是由記錄掛哪一段決定的。**

## 修法與驗收

`cmd/azure-bonds-game` 這一側：`sharedWallGroupStamps`（只補共用段）改成
`unresolvedWallStamps`（收**所有正規展開解不開的格子**），再由
`wallSymbolSegment` 依編號落在哪一段去對應的符號集取圖。引擎那一份版面表沒有動。

驗收就是 oracle 本身：

| | 不同的取樣點（40 張合計）|
|---|---:|
| 修之前 | 97 |
| 修之後 | **1** |

剩下的那 1 個是 spec 1134 早就記過的 `(1,7) W` 單格差異，與這次無關。

第 673 輪再補提爾佛頓的 `(3,4)`、`(1,5)`、`(0,7)` 三格共 12 張，**全部逐點相同**
（修好之後拍的，沒有再出現跨段的洞）。覆蓋率 **40 / 585**。

## ⚠ 提爾佛頓的高價值格子用完了，往下要先把管線接到別張圖

貪婪清單接下來四格分別在下水道（`GEO2/0x03`）、`GEO3/0x11`、贊提爾暗黑神殿
（`GEO4/0x21`）與比荷洞（`GEO4/0x25`）。兩側都還不通：

- **原版側**：`cmd/dos-save-export -map-block` 改得了地圖編號，但牆面素材是
  `LOAD PIECES` 在 ECL 裡載的。直接跳到別張圖的存檔會不會帶對牆組**沒有驗過**。
- **remake 側**：已解決，加了 `-first-person`（第 674 輪）。原本的說法「只認
  提爾佛頓」是錯的——`-guildmaster`、`-sewers` 都走得完，而且**沒有壞**。
  真正的限制是：故事流程會**停在事件上**。`-sewers` 走完停在火刀 checkpoint 的
  投降問句，那是一張文字畫面，不是第一人稱。

  `-first-person` 把「流程停下來的那一格」轉成第一人稱畫面：取流程**最後載入
  的那張圖**（`GeoMapSet`／`GeoMapBlock`，`-sewers` 是 GEO2 區塊 3）算牆面與
  地形，切到 `ModeDungeon`，清掉事件的選項與訊息。實測：

  | 指令 | 第一人稱面板 |
  |---|---|
  | `-sewers -first-person` | ✅ 與提爾佛頓差 18,244 像素 |
  | `-sewers -first-person -dungeon-x 8 -dungeon-y 8 -dungeon-facing 0` | ✅ 與上一格差 13,808 像素 |

  ⚠ 牆面要用流程載入的那張圖算，不是 `-geo-set`／`-geo-block` 那張。拿錯的那張
  算出來的牆型是**另一張圖的牆**，而畫面看起來仍然「正常」——這種錯不會自己現形。

### 原版側：同一張圖裡跳得到，跨圖跳不到（第 675 輪實測）

`cmd/dos-save-export -base` 把原版存檔的座標改掉再讓原版讀回去，**同一張圖裡
任一格都到得了**，一步都不用走。`tools/dos-oracle-jump-capture.sh` 把這件事
接成迴圈：寫存檔 → 重開遊戲 → 主選單按 L → 拍四個朝向。

### 換圖：同一個 GEO 檔集內做得到，跨檔集做不到（第 678 輪實測）

原版的第一人稱地圖是**當前 ECL 段的進入碼**跑 `LOAD FILES` 決定的。而存檔的
第四塊就是那一段的**位元組碼本身**：實測 slot B 的視窗正是 `ECL2` 段 `0x01`
的資料**從位移 2 起**逐 byte 相同（前兩個 byte 是段頭，不進記憶體）。

所以換圖＝把另一段的位元組碼換進那個視窗（`dos-save-export -ecl-block`）。

- ✅ **同一個 GEO 檔集內成立。** 換進 `ECL2` 段 `0x03`（下水道），原版拍到的
  (1,8) E 與 remake 畫的下水道**逐格相同（0／7744）**，與提爾佛頓差 48%。
- **跨檔集**：第 678 輪寫「原版根本沒換圖、還站在提爾佛頓」，**那是錯的**。
  第 679 輪拿原版**自己的錯誤訊息**逐步證實，換章其實是有效的：

  | 存檔怎麼改 | 原版的反應 |
  |---|---|
  | 只改 `-area 4` | `Unable to load geo in Load3DMap.` |
  | 再加 `-ecl-block 0x21` | `Unable to load 1 from WALLDEF4.` |
  | 再換掉存檔裡的牆面參數 | 正常進到冒險畫面，座標讀數 (6,7) N |

  第一則證明**章號有生效**（`GEO4` 裡沒有 `0x01` 這一段，而舊的 ECL 段要的正是
  `0x01`）；第二則證明**地圖載進來了**，卡住的是牆磚——存檔記著三組「用哪一塊
  牆磚」（`SetBlocks`，就是 `DS:7210h`／`7212h`），載入時原版拿它們去
  `WALLDEF<章>.DAX` 重載，而它們還指著提爾佛頓的 `1,2,3`。

  ⇒ 換圖要**同時**換四樣：章號、ECL 段的位元組碼、段編號、牆面參數。牆面參數
  現在直接取自**正要裝進去的那一段自己發的** `37h LOAD PIECES`（`ecl.BlockWallPieces`）。

### 試過但不能用：拿 AREA 自動地圖當地圖識別（第 680 輪）

想法是：`AREA` 指令那張自動地圖是**原版自己**照 GEO 資料畫的，與 remake 的算圖
無關，所以拿它解出 16×16 的牆面有無、再跟 `cmd/geo-wall-grid` 的指紋比對，就能
獨立判定「現在站在哪一張圖」。

**不成立。** 拿已知答案的提爾佛頓校準格線（原點與格距全域搜過），最高只到
**63.3%** 相符，而且既不是 GEO 牆的子集也不是超集（誤報 64、漏報 312）。
也就是說自動地圖**不是** GEO 牆格的忠實投影——它畫的是別的東西（可能只畫某些
牆型，或只畫走過的地方）。在弄清楚它到底畫什麼之前，這條路不能用來裁決地圖。

### 可以用的那把尺：移動探測（第 681 輪，已驗證）

原版那一側只要按一次方向鍵、把座標讀回來，就量得到「這個方向走不走得動」
（`tools/dos-oracle-move-probe.sh`）。預測值用引擎的地城移動規則算
（`cmd/geo-move-mask`）。

**為什麼這不算循環論證**：要驗的是第一人稱**算圖**，而移動是**另一個子系統**。
第一人稱畫錯不會讓移動也跟著錯，所以拿移動當識別依據，不是拿待測物當標準。

**定錨**：提爾佛頓 (7,13) 四面都有牆（牆型 `04/06/04/05`），但**往西走得出去**
——那一面是門。實機四個方向逐一量到的是「北／東／南 不動、西 動到 (6,13)」＝
遮罩 `8`，與 `cmd/geo-move-mask` 算出來的 `8` 相同。

⚠ 這一格同時證明**「有牆」不等於「走不動」**：指紋要用移動規則算，不能用牆的
有無。第 680 輪拿牆的有無去比自動地圖，卡在 63.3%，有一部分就是這個原因。

**分辨力**：16 張圖在 **(3,3) 與 (12,9) 兩格**上的遮罩全部相異（16 張 → 16 個
相異指紋，0 衝突）。也就是**一張圖只要 8 次探測**（兩格 × 四個方向）就認得出來。
`cmd/geo-move-mask` 的測試釘住這件事；分不開的時候要**加格子**，不是改斷言。

⚠ 每個方向都要**重新載一次存檔**、朝向直接寫進存檔。在遊戲裡轉向再走會累積
誤差：實測「走一步再走回來」會漂到隔壁格，整格的探測就廢了。

⇒ 這把尺本身是好的，但**流程還沒完整**（見下一節）。

### 真正的原因：擷取腳本一直沒把換圖參數傳下去（第 683 輪找到）

第 678／682 輪那兩批「拍到別張圖」的擷取，**原因不是識別方法有問題，也不是
開機批次的問題**——是 `tools/dos-oracle-jump-capture.sh` 裡那一行寫死了
`-area 2`、而且**根本沒帶 `-ecl-block`／`-map-block`**。第 678 輪我以為自己加
上去了，實際上那次字串取代**沒有命中**，而我沒有斷言，所以它無聲地什麼都沒改。

於是：檔名前綴照著 `PREFIX` 寫成 `geo2-b03-…`，內容卻是提爾佛頓。移動探測那一支
帶的是正確參數，所以**它一直是對的**——兩邊給出矛盾的答案時，我先懷疑了那把新
做的尺，其實該懷疑的是沒有斷言的那次編輯。

⇒ 兩條教訓：
1. **改腳本的字串取代一定要斷言命中**（`assert s.count(old)==1`）。沒斷言的
   取代失敗時不會有任何徵兆，而它改的是「這批資料是哪張圖」這種說謊不臉紅的東西。
2. **兩個量測互相矛盾時，先去看兩者的輸入是不是真的一樣。** 我花了五輪懷疑量測
   本身，而差異其實在命令列。

修好之後，同一格 (1,8) 的四個朝向與 remake **逐格相同（0／7744）**。

### 識別要與擷取在**同一次開機**裡（第 682 輪，仍然成立）

第 682 輪照「先識別、再擷取」跑了一次下水道，結果**還是不能收**：

1. 移動探測在 (3,3)、(12,9) 量到 `C`、`8`，與 GEO2 段 `0x03` 的預測**完全相符**
   ⇒ 那一刻原版確實在下水道。
2. 接著拍了 41 張，逐格比對**每一張都差**，而 (1,8) E 差 3,735 格——
   這個數字正好等於「原版下水道 vs remake **提爾佛頓**」。
3. 再往下追：remake 用兩條路（故事流程、SAVGAM 匯入）畫下水道**逐格相同**
   （0／7744），所以錯的不是 remake ⇒ **那批擷取拍到的是提爾佛頓**。

也就是說：**識別成功的那次開機，和擷取的那些開機，不是同一次**。中間我還動過
`dos-save-export` 的牆面參數行為，前後兩次同一格的原版畫面就差了 3,735 格。

⇒ 教訓：**識別必須與擷取在同一批開機裡，而且前後都要驗一次**。「這張圖我上次
確認過」不算數——每一次重載都是一次新的機會走到別的狀態。目前的擷取腳本只核對
**座標**，座標對而圖錯時它一句話都不會說。

⚠ 另外記一筆：牆面參數（`SetBlocks`）只在**換章**時才該改。同章之內段自己的
`LOAD PIECES` 會設對；先寫進去反而讓原版走到不一樣的狀態。跨章不改則會停在
`Unable to load 1 from WALLDEF4.`。

  ⚠ **但跨檔集的擷取仍然不可信**：換完之後原版與 remake 差 2,390 格，而拿原版
  畫面去跟 17 張圖逐一比對時，**GEO5 段 `0x35` 與 GEO6 段 `0x40` 同時差 0 格**
  ——兩張不相干的圖都「完全相符」，表示這個識別方法本身不可靠，不能用它裁決
  拍到的是哪一張。在有可信的地圖識別方法之前，跨檔集的畫面一張都不收。

⚠⚠ **畫面上的座標讀數驗得到格子，驗不到「哪一張圖」。** 擷取腳本每一張都核對
座標與朝向，這一輪照樣收下了 54 張**不知道是哪張圖**的畫面——座標是對的，圖是
錯的。後來全部移除。**要收進索引之前，得先有一個獨立於 remake 的地圖識別方法**；
「跟 remake 比對，像就收下」是循環論證，會把量測變成自我證明。

⚠ **`-map-block` 換不到別張圖。** 拿提爾佛頓的存檔寫 `-map-block 3`（下水道）
再讓原版讀進去，站上 (1,8) 拍到的畫面與 remake 畫的**提爾佛頓** (1,8) 逐格
相同（88×88 差 **0** 格），與下水道那張差 48%。整份 13,149 bytes 的存檔掃過
六個 GEO 檔集，**沒有任何一塊 GEO 區塊的位元組**——地圖幾何不跟著存檔走，
原版是照存檔裡的 ECL 狀態重跑 `LOAD FILES` 決定載哪一張。要換圖得換 ECL 狀態。

⚠⚠ 而 remake 這一側**認**那個位元組（`Current3DMapBlockID`），所以兩邊會指向
不同的圖、**而且都不會報錯**。這正是最危險的形狀：畫面兩邊都「正常」，只是
畫的是兩張不同的地圖。第一次拍的時候我差點把它收進索引標成下水道。

### 每一格都要把座標讀回來核對

送出的按鍵**不保證被收下**。實測有兩格轉向鍵被吞掉，畫面停在上一個朝向——
而那張圖看起來完全正常。`dos-oracle-jump-capture.sh` 因此每一張都用
`dos_screen_pos.py` 把畫面上的座標與朝向讀回來比對，不符就不收。那兩格因此
被擋下來，沒有進索引。**沒有這道核對，索引會標成 A 而內容是 B**，之後每一次
比對都被污染，而且不會有任何錯誤訊息。

### 找到一部分原因：有些選圖**任何 WALLDEF 檔都沒有**

把每一段要的選圖與各章 `WALLDEF*.DAX` 實際有的區塊對起來：

| 檔案 | 有的區塊 |
|---|---|
| `WALLDEF2` | 1,2,3,4 |
| `WALLDEF3` | 3,5,6,7 |
| `WALLDEF4` | 3,8,9,10,11 |
| `WALLDEF5` | 12,8,14 |
| `WALLDEF6` | 13,16,3,17 |

**選圖 15 與 18 在任何一個檔案裡都不存在**，而有四段要它們：

| ECL 段 | 要的選圖 | 缺 |
|---|---|---|
| `ECL5/0x33` | `14,15,255` | 15 |
| `ECL5/0x35` | `14,15,8` | 15 |
| `ECL6/0x40` | `17,18,16` | 18 |
| `ECL6/0x45` | `17,18,13` | 18 |

這四張圖 remake **一面牆都不畫**（天空與地板完全正確，只有牆不見了）——
`syncLoadPiecesRequest` 載入失敗時只設一個標籤就 `return`，`pieceSets` 維持空的，
**沒有任何錯誤訊息**。而原版在同一格畫得出鐵柵欄與藤蔓，所以它一定有別的解法。

### 為什麼原版不需要那兩塊：**兩槽模式**（第 686 輪）

原作的 `37h LOAD PIECES` handler 有三條分支，其中一條是（spec 1087）：

```pascal
else if (bank0^[1CEh] <> 0) and (bank0^[1D0h] <> 0) then begin
    if o[1] <> 0FFh then LOADWALLSET(1, o[1]);
    if o[3] <> 0FFh then LOADWALLSET(3, o[3]);
end
```

**只載槽 1 與槽 3，槽 2 完全不動。** 所以 `ECL6/0x40` 的 `17,18,16` 從來不會去要
選圖 18，`ECL5/0x33` 的 `14,15,255` 也從來不會去要 15——**這正是那兩塊在任何
`WALLDEF*.DAX` 裡都不存在的原因**。不是資料缺了，是根本不會被讀。

⚠ 而閘門那兩格是**執行時**的值。remake 從存檔進來時不重跑該段的進入碼，拿不到
它們，所以會照三個運算元硬載。

### 三個修法（第 686 輪）

1. **一個槽載不到，不再把整組牆丟掉**，而且會印出是哪一槽。以前是整批 `return`，
   `pieceSets` 維持空的 ⇒ 天空與地板照畫、**一面牆都不畫**、不報錯。
2. **載入原版存檔時還原存檔自己的牆面參數**（`SetBlocks`）。原版載入時就是照著
   它重載的；不還原的話 remake 只能靠查表重建，而查表會把槽 2 填上一個腳本
   從來不會載的選圖。
3. **自製存檔不再寫入該章 `WALLDEF` 沒有的選圖**，改寫哨兵。

`geo6-b40` (12,6) N 因此從差 1,827 格降到 **1,227 格**，取樣八張裡有三張變成
逐格相同（原本 0／20）。

⚠ **還沒完全解決。** `geo6-b43`（選圖 `13,16,3`，全都有）與 `geo5-b32`
（`8,255,255`，全都有）本來就不符合「缺塊」這個解釋。合理的猜測是槽 2 的內容
**跟著遊玩歷史走**——兩槽模式下它保留上一張圖的值，而自製存檔沒有那段歷史。
真要對齊可能得讓 remake 也重跑該段的進入碼，或是把閘門那兩格一起寫進存檔。

⚠ 這兩處**不要當成「remake 畫錯」就急著改**——也可能是擷取時餵給原版的狀態
不對（`geo3-b15` 的天空原本就是這樣被誤判過一次：存檔沿用了提爾佛頓的地形
位元組，修好之後朝北那張才對上）。先找出原因再說。

### 剩下的那一個像素

(1,7) W，可視區 (col 64, row 46)。原版是底灰（EGA 8），remake 畫成黑（0），
**四周每一個像素都相同**——所以不是取樣誤差，是真的差一格。

那一帶的顏色很雜（1／2／3／4／5／8／9／12 都有），形狀像牆上的裝飾符號。
往下兩列（y=142..143）同一欄原版與 remake 都是 8 ⇒ 該欄的底色就是 8。
合起來看最像**那一個像素在原版是透明的**（底色 8 透出來），而 remake 把它
畫成了符號自己的黑。尚未定案。

### 載入原版存檔之後，牆是空氣（第 676 輪修好）

原版存檔裡**沒有**牆磚選圖，也沒有地圖幾何。原版是靠**重跑當前 ECL 段的進入
碼**，把 `LOAD FILES`／`LOAD PIECES` 再發一次拿回來的。remake 載入存檔時不重跑
那一段（會連帶觸發劇情副作用），於是 `LoadPieces` 停在 `[0 0 0]`。

⚠ 全零不報錯，它把**每一面牆都畫成空氣**：天空、地板、UI 全都在，畫面看起來
完全正常。第 675 輪就是拿這種畫面去跟原版比，差 37.6%，差一步被判成
「第一人稱畫錯了」。

修法是查表補值。`cmd/ecl-wall-pieces` 掃過全部六個 ECL 檔：**19 個段各發出
剛好一組常數三元組，沒有一個是多組，也沒有一個是記憶體參照**——查表在這份
corpus 上才成立，這是先量過才敢做的前提。

⚠ 鍵是 **ECL 段**，不是地圖。GEO5 的 `0x31` 與 `0x32` 共用同一張幾何區塊
`0x32`，牆磚選圖卻是 `12,255,255` 與 `8,255,255`。照地圖查會在其中一塊給出
自洽但錯的牆。

⚠ 而且要用**存檔記下來的**那個段（`LastECLBlockID`），不是 session 當下的段：
載入之後 `CurrentBlockID()` 還停在初始化的世界地圖段 `0x50`，拿它去查一定
查不到，而查不到的後果是安靜地不補，牆照樣是空氣。

驗收：拿**同一份存檔**餵原版與 remake，(8,2) N 的 88×88 可視區差 **0 格**。

逐地圖的「新增幾種」那一欄直接就是工作順序：提爾佛頓 108 種全新、
`geo5/0x33` 104 種、墓園 45 種……而 `myth-drannor.inner-ruins` 與
`geo6/0x45` 各只新增 1 種——那兩張幾乎不必單獨比。

## 遮蔽是這個分母能用的唯一原因

前兩版都算出沒有用的數字：

| 版本 | 簽章內容 | 相異數 |
|---|---|---:|
| 一 | 前方三排 × 橫向 ±1，記**牆型值** | 15,693 |
| 二 | 同上，改記**有無** | 14,294 |
| 三 | 有無 ＋ **遮蔽** | **585** |

第一版把兩個軸混在一起，牆型在幾乎每一格都不同，於是去重等於沒做。
第二版分開了軸，但簽的是**原始鄰域**而不是**看得到的東西**：走廊裡一面牆擋住
之後，後面那幾排根本不會畫出來，把它們簽進去等於在區分兩張一模一樣的畫面。

⚠ 兩個數字都是誠實的——它們確實是那個定義下的相異數。**誠實但沒有用**：
定義本身沒有對上「玩家看到什麼」。分母的定義跟數字一樣需要被檢查。

第三版的遮蔽規則：

- 中央那一行從腳下往前，每一格記左右牆；**前方有牆就記下來並停止**。
- 兩側只有「側牆是開的」那一格看得進去；側牆一擋，那一側往後全部不可見。

## ⚠ 「站得住」那個過濾器是錯的

第一版把「四面都是實牆」的格子排除在分母外，理由是玩家進不去。
`-covered` 一跑就出現四張擷取**對不到任何格子**——而那四張是
`GEO2/0x01 (7,13)` 的四個朝向，也就是**開新遊戲的起點**。它確實是密室
（劇情要求先找出口），而它是每個玩家看到的第一張畫面。

⇒ 分母改收全部 256 格／張，密室只記數字不拿來過濾。工具照實回報「對不到」
而不是靜靜丟掉，那個矛盾才浮得出來——**過濾器也是斷言**（AGENTS §3）。

## 明確不宣稱

- **沒有宣稱比完 585 種就等於第一人稱正確。** 天空色、牆磚選圖與調色盤跟著
  地圖宣告走，各自要比——spec 1134 那個黑掉的天花板就是這一類，而它在 20 張
  裡的每一張都錯，逐格比對本身抓不出「兩邊都照同一個錯宣告畫」。
- **沒有宣稱這 585 種玩家都走得到。** 「站得住」的判準是「至少一面沒有牆」，
  那不是可達性。真正的可達性要從入口做連通性走訪，還要考慮腳本傳送。
- **沒有宣稱那 12 種是對的。** spec 1134 說那 20 張裡 19 張與原版相同、1 張差
  一格；這裡只算「比過幾種」，不重述比對結果。
- 遮蔽模型是 `derived`：它取自 spec 1130 的幾何，沒有逐條對過 `BUILDVIEW`。
  如果原作在某些情況下畫得比這個模型多（例如門的另一側），585 會偏低。
