# 1185 — 第一人稱 fidelity：585 種畫面，已比過 40 種

- 證據等級：`exact`（原版 GEO 逐格計算）＋ `derived`（可見性模型取自 spec 1130
  的第一人稱幾何；遮蔽規則寫在下面，可以被推翻）
- 上游：spec 1134（原版第一人稱 oracle 與逐格比對）、spec 1130（幾何與框）
- 產物：`cmd/fp-screen-plan`、`docs/audit/fp-screen-plan.md`

## 問題

原版截圖 oracle 第 572 輪就建好了（`tools/dos-oracle-session.sh` 那六支），
spec 1134 也用它比過提爾佛頓的 20 張畫面。**缺的不是工具，是分母**——沒有一份
「該比哪些畫面」的清單，20 這個數字就沒有母數，於是 UI fidelity 永遠只能寫成
一句「尚未逐張比對」。

## 兩個軸要分開算

第一人稱畫得對不對有兩件互相獨立的事：

| 軸 | 決定於 | 分母 |
|---|---|---|
| **幾何**：哪裡該畫一面牆、透視怎麼收斂 | 視野內牆的**有無** | 相異的可見牆面配置 |
| **貼圖**：那面牆用哪一張牆磚 | `LOADWALLSET` ＋ 地圖宣告，與站在哪一格無關 | 相異的**牆型值** |

## 結果

|---|---:|
| `first_person` 地圖 | 18 |

| 格子 × 四個朝向 | 18,432 |

18,432 張畫面裡真正長得不一樣的只有 585 張。逐張比對因此是**做得完**的事。

spec 1134 那 20 張換算成簽章只蓋掉 **12 種**——同一條走廊上的五格朝同一個方向
看到的常常是同一張畫面。`-covered` 同時排出「接下來拍哪一格」：貪婪法，
每一列是「一次能蓋掉最多還沒蓋到的簽章」的格子，一格拍四個朝向。

第 669 輪照那張清單補拍了提爾佛頓的五格（`(0,0)`、`(3,2)`、`(3,3)`、`(4,3)`、
`(1,6)`），**12 → 31 / 585**。二十張新畫面與 remake 逐格比對的結果：
**十八張完全相同，兩張不同**。

## ⚠ 找到一個差異：`(1,6)` 朝北與朝南

| 畫面 | 不同的取樣點 | 顏色類別（原版 → remake）|
|---|---:|---|
| `(1,6)` N | 48 | `8→7 ×13`、`7→8 ×11`、`0→8 ×8`、`15→7 ×7` |
| `(1,6)` S | 48 | 完全相同的四類 |
| `(1,6)` E／W | 0 | — |

那一格的牆是 `[N=0, E=0Eh, S=0, W=0Eh]`（terrain `95h`）：**朝東西是正面對著
`0Eh` 那面牆，兩張都完全相同；朝南北才是把 `0Eh` 當側牆畫進透視**，而那兩張
就是不同的兩張。

差異全部是**顏色類別的互換**（8 與 7 對調，再加 `0→8`、`15→7`），沒有任何一個
形狀位移 ⇒ 指向**明暗配對**而不是幾何。

### 判準格 `(1,8)`：假說成立，而且順便驗到簽章模型本身

`(1,8)` 的牆與 terrain 與 `(1,6)` 完全相同（`[N=0, E=0Eh, S=0, W=0Eh]`／`95h`），
所以它們的**簽章是同一個**。第 670 輪把它拍下來比對：

| 畫面 | 不同的取樣點 | 顏色類別 |
|---|---:|---|
| `(1,8)` N | 48 | `8→7 ×13`、`7→8 ×11`、`0→8 ×8`、`15→7 ×7` |
| `(1,8)` S | 48 | 同上 |
| `(1,8)` E／W | 0 | — |

**與 `(1,6)` 逐項相同**。兩件事同時成立：

1. `0Eh` 當側牆畫時 remake 與原版不同，兩格獨立重現。
2. ★ **簽章相同的兩格真的畫出同一張畫面**——連差異都一模一樣。這是 585 這個
   分母的定義第一次被實測驗到，而不是只有推理。

## ⚠ 「不是有磚被丟掉」是錯的——而錯法本身值得記

第一次查的時候，我把 `prepareWallPreview` 裡三處靜默 `continue`（畫面外、
共用符號編號超界、`RGBA` 失敗）全部加上輸出，重畫一次 `layout=8 type=14`
**一次都沒觸發**，於是判定「22 格全部畫出來了」。

那三處全在 `BuildWallLayout` **回來之後**。真正的丟棄在它**裡面**：

```go
picture, item, symbolID, ok := piece.WallSymbolItem(record, slice, index)
if ok {                       // ← ok=false 的格子不會被 append
    stamps = append(stamps, …)
}
```

⇒ 儀器裝在錯的一層，量到的零是**沒有涵蓋到那條路徑**。這與本專案反覆踩過的
假零是同一個形狀，只是這一次的「掃描範圍」是**程式的哪一層**而不是資料的哪一段。
**下「沒有發生」的結論之前，要先確認儀器裝在事情真的會發生的那一層。**

## 成因：符號編號跨段，而查表只看記錄自己那一段

逐格印出那 2×2 磚實際蓋上去的符號之後：

| 格子 | WALLDEF 要的編號 | 實際畫出來 |
|---|---:|---|
| r8 c10 | 225 | ✅ 第 3 段第 39 項 |
| r9 c9 | 33 | ✅ 共用段 |
| **r8 c9** | **185** | ❌ 沒有 |
| **r9 c10** | **185** | ❌ 沒有 |

`PieceSet.WallSymbolItem` 只在**這一筆記錄自己掛的那一段**裡找符號：

```go
item = int(id) - int(SymbolSetBase[p.SymbolSetIDs[record]])
if item < 0 || item >= int(picture.ItemCount) { return …, false }
```

`0Eh` ⇒ `wallSet = 3`，記錄掛第 3 段（基準 `BAh` ＝ 186）。而 WALLDEF 引用的
`185` 是**第 2 段的最後一項**（基準 `74h` ＝ 116）⇒ `185 − 186 = −1` ⇒ 丟掉。

**段是由編號本身決定的，不是由記錄掛哪一段決定的。**

## 修法與驗收

`cmd/azure-bonds-game` 這一側：`sharedWallGroupStamps`（只補共用段）改成
`unresolvedWallStamps`（收**所有正規展開解不開的格子**），再由
`wallSymbolSegment` 依編號落在哪一段去對應的符號集取圖。引擎那一份版面表沒有動。

驗收就是 oracle 本身：

| | 不同的取樣點（40 張合計）|
|---|---:|
| 修之前 | 97 |
| 修之後 | **1** |

剩下的那 1 個是 spec 1134 早就記過的 `(1,7) W` 單格差異，與這次無關。

第 673 輪再補提爾佛頓的 `(3,4)`、`(1,5)`、`(0,7)` 三格共 12 張，**全部逐點相同**
（修好之後拍的，沒有再出現跨段的洞）。覆蓋率 **40 / 585**。

## ⚠ 提爾佛頓的高價值格子用完了，往下要先把管線接到別張圖

貪婪清單接下來四格分別在下水道（`GEO2/0x03`）、`GEO3/0x11`、贊提爾暗黑神殿
（`GEO4/0x21`）與比荷洞（`GEO4/0x25`）。兩側都還不通：

- **原版側**：`cmd/dos-save-export -map-block` 改得了地圖編號，但牆面素材是
  `LOAD PIECES` 在 ECL 裡載的。直接跳到別張圖的存檔會不會帶對牆組**沒有驗過**。
- **remake 側**：已解決，加了 `-first-person`（第 674 輪）。原本的說法「只認
  提爾佛頓」是錯的——`-guildmaster`、`-sewers` 都走得完，而且**沒有壞**。
  真正的限制是：故事流程會**停在事件上**。`-sewers` 走完停在火刀 checkpoint 的
  投降問句，那是一張文字畫面，不是第一人稱。

  `-first-person` 把「流程停下來的那一格」轉成第一人稱畫面：取流程**最後載入
  的那張圖**（`GeoMapSet`／`GeoMapBlock`，`-sewers` 是 GEO2 區塊 3）算牆面與
  地形，切到 `ModeDungeon`，清掉事件的選項與訊息。實測：

  | 指令 | 第一人稱面板 |
  |---|---|
  | `-sewers -first-person` | ✅ 與提爾佛頓差 18,244 像素 |
  | `-sewers -first-person -dungeon-x 8 -dungeon-y 8 -dungeon-facing 0` | ✅ 與上一格差 13,808 像素 |

  ⚠ 牆面要用流程載入的那張圖算，不是 `-geo-set`／`-geo-block` 那張。拿錯的那張
  算出來的牆型是**另一張圖的牆**，而畫面看起來仍然「正常」——這種錯不會自己現形。

### 原版側：同一張圖裡跳得到，跨圖跳不到（第 675 輪實測）

`cmd/dos-save-export -base` 把原版存檔的座標改掉再讓原版讀回去，**同一張圖裡
任一格都到得了**，一步都不用走。`tools/dos-oracle-jump-capture.sh` 把這件事
接成迴圈：寫存檔 → 重開遊戲 → 主選單按 L → 拍四個朝向。

### 換圖：同一個 GEO 檔集內做得到，跨檔集做不到（第 678 輪實測）

原版的第一人稱地圖是**當前 ECL 段的進入碼**跑 `LOAD FILES` 決定的。而存檔的
第四塊就是那一段的**位元組碼本身**：實測 slot B 的視窗正是 `ECL2` 段 `0x01`
的資料**從位移 2 起**逐 byte 相同（前兩個 byte 是段頭，不進記憶體）。

所以換圖＝把另一段的位元組碼換進那個視窗（`dos-save-export -ecl-block`）。

- ✅ **同一個 GEO 檔集內成立。** 換進 `ECL2` 段 `0x03`（下水道），原版拍到的
  (1,8) E 與 remake 畫的下水道**逐格相同（0／7744）**，與提爾佛頓差 48%。
- **跨檔集**：第 678 輪寫「原版根本沒換圖、還站在提爾佛頓」，**那是錯的**。
  第 679 輪拿原版**自己的錯誤訊息**逐步證實，換章其實是有效的：

  | 存檔怎麼改 | 原版的反應 |
  |---|---|
  | 只改 `-area 4` | `Unable to load geo in Load3DMap.` |
  | 再加 `-ecl-block 0x21` | `Unable to load 1 from WALLDEF4.` |
  | 再換掉存檔裡的牆面參數 | 正常進到冒險畫面，座標讀數 (6,7) N |

  第一則證明**章號有生效**（`GEO4` 裡沒有 `0x01` 這一段，而舊的 ECL 段要的正是
  `0x01`）；第二則證明**地圖載進來了**，卡住的是牆磚——存檔記著三組「用哪一塊
  牆磚」（`SetBlocks`，就是 `DS:7210h`／`7212h`），載入時原版拿它們去
  `WALLDEF<章>.DAX` 重載，而它們還指著提爾佛頓的 `1,2,3`。

  ⇒ 換圖要**同時**換四樣：章號、ECL 段的位元組碼、段編號、牆面參數。牆面參數
  現在直接取自**正要裝進去的那一段自己發的** `37h LOAD PIECES`（`ecl.BlockWallPieces`）。

### 試過但不能用：拿 AREA 自動地圖當地圖識別（第 680 輪）

想法是：`AREA` 指令那張自動地圖是**原版自己**照 GEO 資料畫的，與 remake 的算圖
無關，所以拿它解出 16×16 的牆面有無、再跟 `cmd/geo-wall-grid` 的指紋比對，就能
獨立判定「現在站在哪一張圖」。

**不成立。** 拿已知答案的提爾佛頓校準格線（原點與格距全域搜過），最高只到
**63.3%** 相符，而且既不是 GEO 牆的子集也不是超集（誤報 64、漏報 312）。
也就是說自動地圖**不是** GEO 牆格的忠實投影——它畫的是別的東西（可能只畫某些
牆型，或只畫走過的地方）。在弄清楚它到底畫什麼之前，這條路不能用來裁決地圖。

### 可以用的那把尺：移動探測（第 681 輪，已驗證）

原版那一側只要按一次方向鍵、把座標讀回來，就量得到「這個方向走不走得動」
（`tools/dos-oracle-move-probe.sh`）。預測值用引擎的地城移動規則算
（`cmd/geo-move-mask`）。

**為什麼這不算循環論證**：要驗的是第一人稱**算圖**，而移動是**另一個子系統**。
第一人稱畫錯不會讓移動也跟著錯，所以拿移動當識別依據，不是拿待測物當標準。

**定錨**：提爾佛頓 (7,13) 四面都有牆（牆型 `04/06/04/05`），但**往西走得出去**
——那一面是門。實機四個方向逐一量到的是「北／東／南 不動、西 動到 (6,13)」＝
遮罩 `8`，與 `cmd/geo-move-mask` 算出來的 `8` 相同。

⚠ 這一格同時證明**「有牆」不等於「走不動」**：指紋要用移動規則算，不能用牆的
有無。第 680 輪拿牆的有無去比自動地圖，卡在 63.3%，有一部分就是這個原因。

**分辨力**：16 張圖在 **(3,3) 與 (12,9) 兩格**上的遮罩全部相異（16 張 → 16 個
相異指紋，0 衝突）。也就是**一張圖只要 8 次探測**（兩格 × 四個方向）就認得出來。
`cmd/geo-move-mask` 的測試釘住這件事；分不開的時候要**加格子**，不是改斷言。

⚠ 每個方向都要**重新載一次存檔**、朝向直接寫進存檔。在遊戲裡轉向再走會累積
誤差：實測「走一步再走回來」會漂到隔壁格，整格的探測就廢了。

⇒ 這把尺本身是好的，但**流程還沒完整**（見下一節）。

### 真正的原因：擷取腳本一直沒把換圖參數傳下去（第 683 輪找到）

第 678／682 輪那兩批「拍到別張圖」的擷取，**原因不是識別方法有問題，也不是
開機批次的問題**——是 `tools/dos-oracle-jump-capture.sh` 裡那一行寫死了
`-area 2`、而且**根本沒帶 `-ecl-block`／`-map-block`**。第 678 輪我以為自己加
上去了，實際上那次字串取代**沒有命中**，而我沒有斷言，所以它無聲地什麼都沒改。

於是：檔名前綴照著 `PREFIX` 寫成 `geo2-b03-…`，內容卻是提爾佛頓。移動探測那一支
帶的是正確參數，所以**它一直是對的**——兩邊給出矛盾的答案時，我先懷疑了那把新
做的尺，其實該懷疑的是沒有斷言的那次編輯。

⇒ 兩條教訓：
1. **改腳本的字串取代一定要斷言命中**（`assert s.count(old)==1`）。沒斷言的
   取代失敗時不會有任何徵兆，而它改的是「這批資料是哪張圖」這種說謊不臉紅的東西。
2. **兩個量測互相矛盾時，先去看兩者的輸入是不是真的一樣。** 我花了五輪懷疑量測
   本身，而差異其實在命令列。

修好之後，同一格 (1,8) 的四個朝向與 remake **逐格相同（0／7744）**。

### 識別要與擷取在**同一次開機**裡（第 682 輪，仍然成立）

第 682 輪照「先識別、再擷取」跑了一次下水道，結果**還是不能收**：

1. 移動探測在 (3,3)、(12,9) 量到 `C`、`8`，與 GEO2 段 `0x03` 的預測**完全相符**
   ⇒ 那一刻原版確實在下水道。
2. 接著拍了 41 張，逐格比對**每一張都差**，而 (1,8) E 差 3,735 格——
   這個數字正好等於「原版下水道 vs remake **提爾佛頓**」。
3. 再往下追：remake 用兩條路（故事流程、SAVGAM 匯入）畫下水道**逐格相同**
   （0／7744），所以錯的不是 remake ⇒ **那批擷取拍到的是提爾佛頓**。

也就是說：**識別成功的那次開機，和擷取的那些開機，不是同一次**。中間我還動過
`dos-save-export` 的牆面參數行為，前後兩次同一格的原版畫面就差了 3,735 格。

⇒ 教訓：**識別必須與擷取在同一批開機裡，而且前後都要驗一次**。「這張圖我上次
確認過」不算數——每一次重載都是一次新的機會走到別的狀態。目前的擷取腳本只核對
**座標**，座標對而圖錯時它一句話都不會說。

⚠ 另外記一筆：牆面參數（`SetBlocks`）只在**換章**時才該改。同章之內段自己的
`LOAD PIECES` 會設對；先寫進去反而讓原版走到不一樣的狀態。跨章不改則會停在
`Unable to load 1 from WALLDEF4.`。

  ⚠ **但跨檔集的擷取仍然不可信**：換完之後原版與 remake 差 2,390 格，而拿原版

### 找到一部分原因：有些選圖**任何 WALLDEF 檔都沒有**

把每一段要的選圖與各章 `WALLDEF*.DAX` 實際有的區塊對起來：

| 檔案 | 有的區塊 |
|---|---|
| `WALLDEF2` | 1,2,3,4 |
| `WALLDEF3` | 3,5,6,7 |
| `WALLDEF4` | 3,8,9,10,11 |
| `WALLDEF5` | 12,8,14 |
| `WALLDEF6` | 13,16,3,17 |

選圖 15 與 18 在任何一個 `WALLDEF` 裡都查不到，而有四段的第二個運算元要它們：

| ECL 段 | 三個運算元 | 第二個 |
|---|---|---|
| `ECL5/0x33` | `14,15,255` | 15 |
| `ECL5/0x35` | `14,15,8` | 15 |
| `ECL6/0x40` | `17,18,16` | 18 |
| `ECL6/0x45` | `17,18,13` | 18 |

**這不是資料缺了一塊。** 選圖 14 與 17 的區塊各 1,560 bytes ＝ **兩個槽**，
其餘每一塊都剛好 780 ＝ 一個槽；而 `LOADWALLSET` 一次呼叫會把檔案裡的每一個
780-byte 區段依序填進**連續的槽**。所以 `LOADWALLSET(1, 14)` 自己就填滿了
槽 1 與槽 2，第二個運算元（`15`／`18`＝第一個 ＋ 1）**永遠不會被讀**——
兩槽模式那條分支的存在理由就是不要重覆載一次。細節見下一節。

### `LOADWALLSET` 一次填幾個槽，以及 `OLDWALL`

`LOADWALLSET(槽, 選圖)` 在 PC-98 是 `overlay-30:0F8Fh`（Borland 符號表給的
`LOADWALLSET` 位移 3983 落在這一支裡）。它做四件事：

```pascal
procedure LOADWALLSET(slot, num: byte);
begin
  if not (slot in [1..3]) then exit;              { 0F95h：範圍外直接回 }
  讀 WALLDEF<章>.dax 的第 num 塊 → 大小 size;     { 0FA4h..0FEAh，檔名字串在 0F44h }
  if (size = 0) or (slot + size div 780 > 4) then { 0FEFh..100Bh：放不下就報錯 }
    印 'Unable to load <num> from WALLDEF<章>.';
  for k := 0 to size div 780 - 1 do               { 1082h..10BDh：逐段填連續的槽 }
    THEWALLSET^[(slot + k - 1) * 780] := 檔案第 k 段;
  chunks := size div 780;
  for k := 1 to chunks do begin                   { 10E5h..11F4h }
    OLDWALL[slot + k - 1] := (-1, -1);            { 110Dh／1122h }
    符號索引 ≥ [4894h] 的格子加上 [488Ah + slot*2] - [488Ch];   { 1131h..11AFh }
    if chunks > 1 then 載入 8X8D 區塊 num*10 + k   { 11BAh }
                  else 載入 8X8D 區塊 num;         { 11D9h }
  end;
  OLDWALL[slot] := (num, slot);                   { 11F7h..121Fh }
end;
```

`OLDWALL` 是 `array[1..3] of record num, slot: integer end`，基底 `A2AAh`
（符號表把 `OLDWALL` 標在 `A2AEh` ＝ 元素 1）。DOS 側的同一份是 `7210h`——
`37h LOAD PIECES` handler 收尾寫的 `[7210h+槽×4] := 片`／`[7212h+槽×4] := 槽`
（spec 1087）就是這個陣列，也就是**存檔第 9..14 欄**。

三個號碼互相印證，而且**兩邊獨立**：

| 證據 | 內容 |
|---|---|
| `WALLDEF5.DAX` 區塊大小 | 8＝780、12＝780、**14＝1,560** |
| `WALLDEF6.DAX` 區塊大小 | 3／13／16＝780、**17＝1,560** |
| `8X8D5.DAX` 有的區塊 | 8、12、**141、142**（沒有 14，也沒有 15） |
| `8X8D6.DAX` 有的區塊 | 3、13、16、**171、172**（沒有 17，也沒有 18） |

`141`／`142` 就是 `11BAh` 算出來的 `14*10+k`；`171`／`172` 同理。**所以「選圖
15／18 不存在」與「槽 2 有內容」不衝突**：槽 2 的內容是選圖 14／17 的第二段，
由同一次呼叫填進去，跟上一張圖無關，也跟存檔有沒有歷史無關。

remake 這一側 `graphics.ParsePieceSet` 早就照這個形狀寫了（`ParseWallDefs` 按
780 切段、`len(walls) > 1` 時符號區塊用 `selector*10 + index + 1`、並且照
`SymbolSetBase` 做同一個索引平移），所以四張圖不需要新的載入路徑。

### 為什麼第二個運算元不會被讀：**兩槽模式**（第 686 輪）

原作的 `37h LOAD PIECES` handler 有三條分支，其中一條是（spec 1087）：

```pascal
else if (bank0^[1CEh] <> 0) and (bank0^[1D0h] <> 0) then begin
    if o[1] <> 0FFh then LOADWALLSET(1, o[1]);
    if o[3] <> 0FFh then LOADWALLSET(3, o[3]);
end
```

**只載槽 1 與槽 3，槽 2 完全不動。** 所以 `ECL6/0x40` 的 `17,18,16` 從來不會去要
選圖 18，`ECL5/0x33` 的 `14,15,255` 也從來不會去要 15——**這正是那兩塊在任何
`WALLDEF*.DAX` 裡都不存在的原因**。不是資料缺了，是根本不會被讀。

⚠ 而閘門那兩格是**執行時**的值。remake 從存檔進來時不重跑該段的進入碼，拿不到
它們，所以會照三個運算元硬載。

### 三個修法（第 686 輪）

1. **一個槽載不到，不再把整組牆丟掉**，而且會印出是哪一槽。以前是整批 `return`，
   `pieceSets` 維持空的 ⇒ 天空與地板照畫、**一面牆都不畫**、不報錯。
2. **載入原版存檔時還原存檔自己的牆面參數**（`SetBlocks`）。原版載入時就是照著
   它重載的；不還原的話 remake 只能靠查表重建，而查表會把槽 2 填上一個腳本
   從來不會載的選圖。
3. **自製存檔不再寫入該章 `WALLDEF` 沒有的選圖**，改寫哨兵。

`geo6-b40` (12,6) N 因此從差 1,827 格降到 **1,227 格**，取樣八張裡有三張變成
逐格相同（原本 0／20）。

⚠ **還沒完全解決。** 目前各張圖取樣八張的結果：

| 圖 | 相同 |
|---|---|
| `geo6-b40` | 3／8 |
| `geo5-b32` | 4／8 |
| `geo5-b33` | 1／8 |
| `geo6-b43`／`geo5-b35` | 0／8 |

`geo6-b40` 那一格看得出改善：石牆與藤蔓現在畫出來了（原本一面牆都沒有），
**剩下的差異是遠處那道高鐵柵欄**——原版畫出來，remake 在同一個位置畫了一面矮的
平牆。槽 2 在原版那邊有內容，來源是選圖 17 的第二段（符號區塊 `172`），
由 `LOADWALLSET(1, 17)` 同一次呼叫填進去。

第 687 輪加了 `-two-slot-walls`（把閘門兩格寫成 1）。它寫的是原版也會讀的真實
狀態，但**對這個量測沒有影響**：還原存檔自己的 `SetBlocks` 那條路徑優先。

⚠ 這兩處**不要當成「remake 畫錯」就急著改**——也可能是擷取時餵給原版的狀態
不對（`geo3-b15` 的天空原本就是這樣被誤判過一次：存檔沿用了提爾佛頓的地形
位元組，修好之後朝北那張才對上）。先找出原因再說。

#### 逐格證據（`-wall-trace`）

`azure-bonds-game -wall-trace <TSV>` 把每一格牆磚的解析過程寫出來（來源、牆型、
起始槽、段數、版面、列欄、編號、段、段內項、取用區塊）。它寫在
`prepareWallPreview` 裡而不是另開一支工具——另開一支就得抄一次選塊邏輯，
而抄出來的那一份會漂移，於是追到的不是畫面上的行為。

`geo6-b40` (2,9) W 共 242 格，最大的一群是：

| 來源 | 牆型 | 起始槽 | 段 | 格數 |
|---|---:|---:|---:|---:|
| 回退 | 8 | 1 | **3** | **132** |
| 回退 | 8 | 1 | 0（共用）| 32 |
| 回退 | 2 | 1 | 0（共用）| 30 |
| 引擎 | 2 | 1 | 1 | 18 |

牆型 8 查的是槽 2 ＝ 選圖 17 的**第 2 段**。那 132 格的編號是 `192`–`197`，
落在**段 3** ⇒ 走回退路徑，改用 `pieceSets[3]`（選圖 16）的圖。而 `192−70 = 122`
——原始編號本來就在段 2（`116..185`），也就是選圖 17 第 2 段自己的區塊 `172`。
**逐段重算 rebase 把這一段自己的編號推出了這一組**，於是牆畫在對的位置、
用的是另一個牆面組的圖。這一筆與 `geo5-b35`／`geo6-b45` 的爭議無關，可以獨立成立。

`geo6-b45` (12,2) N 那一邊只有 20 格受影響（牆型 6／4 落在段 2），
卻對應到將近一千格的差異 ⇒ **一個 stamp 蓋到的畫面格數比估的多**，
用格數反推 stamp 數會估錯。

#### 原作怎麼把編號變成圖（`SQRPAK8`，第 749 輪解出）

畫牆的是 `THREED` 的 `sub_39F(版面, 牆型, 欄, 列)`（`overlay-30:039Fh`）：

```pascal
索引 := 版面索引表[版面];                     { 三張表在 16ACh／16B6h／16C0h }
for 列 := … do for 欄 := … do begin
  格 := THEWALLSET^[(牆型 - 1) * 156 + 索引]; { 0442h：156 ＝ WALLBYTES }
  if 格 <> 0 then PUT8X8SYMBOL(欄+2, 列+2, 格, 1, 1);   { 0489h → 232h:2Fh }
  索引 := 索引 + 1;
end;
```

**`THEWALLSET^` 是一整塊平的三槽緩衝，用 `(牆型 − 1) × 156` 定址——原作裡根本
沒有「這一格出自哪一段」這個概念。** 格子裡的位元組原封不動交給 `PUT8X8SYMBOL`。

`PUT8X8SYMBOL`（`SQRPAK8`＝`overlay-35:032Ah`）只看編號本身：

| 編號 | 符號組 |
|---|---:|
| `01h`..`2Dh` | 0（共用，45 個）|
| `2Eh`..`73h` | 1（70 個）|
| `74h`..`B9h` | 2（70 個）|
| `BAh`..`FFh` | 3（70 個）|
| `100h`..`127h` | 4（40 個）|
| 其他 | 印錯誤訊息 |

然後取 `[964Ch + 符號組 × 4]` 那張遠指標表。表由 `LOAD8X8SET(槽索引, 區塊)`
填（`overlay-35:004Ch`），而 `LOADWALLSET` 對每一段呼叫一次，槽索引 ＝
`起始槽 + 段序 − 1`（`overlay-30:11BAh`／`11D9h`）⇒ 選圖 17 從槽 1 起載時，
符號組 1 ← 區塊 `171`、符號組 2 ← 區塊 `172`。

⇒ **規則是「編號決定符號組」，與這一格出自第幾段無關。** 兩條候選規則裡，
「區塊照 ID 選」是對的；`geo6-b40` 打到 312 不是巧合。而 remake 目前的形狀
（`pieceSets` 以槽為鍵、每一組各自帶自己的區塊清單）與原作的**平表**不同，
`geo5-b35`／`geo6-b45` 在那個變體下變差，要在改成平表之後重量，
不能拿舊形狀的量測去否定這條規則。

那張分段表在資料段裡有名字，兩份都是 **5 組**：

| 符號 | 位址 | 內容 |
|---|---|---|
| `SETFIRST` | `488Ah` | `1, 46, 116, 186, 256` |
| `SETLAST` | `4894h` | `45, 115, 185, 255, …` |

`LOADWALLSET` 的 rebase 就是 `SETFIRST[起始槽] − SETFIRST[1]`（`overlay-30:1064h`），
而套用的條件是 `編號 >= SETLAST[0]`（`116Bh`，＝ **45**）。

⚠ **門檻是 45 不是 46**，所以編號 `45` 會被 rebase——即使 45 屬於共用組
（`SETFIRST[0]=1`..`SETLAST[0]=45`）。這是原作自己的行為，remake 的
`OffsetSymbols` 用 `value < 0x2D` 跳過，剛好一致；**改成「跳過整個共用組」
會與原作不同**。

⚠ 編號 `100h..127h`（第 4 組）remake 沒有模型（`SymbolSetBase` 只有四項）。
WALLDEF 的格子是**位元組**，放不下 `>= 256`，所以那一組不會從 WALLDEF 進來——
但 `SETFIRST` 有五項，抄 `SymbolSetBase` 時不要把四當成上界。

⚠ `SymbolSetBase[0]` 是 `0`，而 `SETFIRST[0]` 是 **1**。remake 這一邊由
`wallSharedFirstID` 擔任 `SETFIRST[0]`，所以目前沒有出事；但兩個常數表的第 0 項
語意不同，合併它們之前要先確認。
⚠ 三個已經站得住的事實，下一輪不必重推：

  - 原作的 rebase **只算一次**，取自呼叫時指定的起始槽
    （`overlay-30:1064h` 的 `var_A = 符號基底[起始槽] − 符號基底[1]`），
    對每一段都套同一個值。
  - 符號 ID 的段由**編號本身**決定（`wallSymbolSegment`，基準 `2Eh／74h／BAh`，
    每段 70 個，而每一塊 8X8D 牆面區塊剛好 70 項）。
  - 多段組的 8X8D 區塊編號是 `選圖 × 10 + 段序`（`overlay-30:11BAh`），
    `8X8D5` 有 `141`／`142`、`8X8D6` 有 `171`／`172`。

### 載檔時「會跑到什麼」是一個共用問題（第 749 輪）

天空選色與牆磚選圖是**同一個形狀**：值由段的進入碼寫入，而 remake 載檔時不重跑
進入碼 ⇒ 不補就沿用底檔（別章）的值。兩者都要問同一個問題——
**載入一份 `LastECLBlockID == 段號` 的存檔時，這一段會跑到哪裡？**

走訪收在 `internal/ecl/loadtime.go` 的 `ReachableOnLoad`，**只有一份**：

- 在「`4BF2h == 段號`」的前提下走五個進入點（前置不一定掛在第 0 個）。
- `IF` 只守下一條；判得出來就照判，判不出來而守的是一般指令就跳過那一條。
- 判不出來而守的是控制流（`GOTO`／`GOSUB`／`EXIT`）⇒ 停，不猜。走回頭路也停。

兩支產生器都走它：

| 產生器 | 產物 | 收到幾段 |
|---|---|---:|
| `cmd/ecl-sky-colours` | `eclBlockLoadTimeWrites`（`4BE7h`／`4BE8h`／`4BFDh`／`4BFEh`）| 11 |
| `cmd/ecl-wall-pieces` | `eclBlockWallPieces`（`37h` 的三元組）| 8 |

⚠ **`37h` 有兩個不同的問題，兩個都有人問，答案不一樣**：

| 問題 | 誰在問 | 函式 |
|---|---|---|
| 這一段**宣告**的三元組是什麼？ | `cmd/dos-save-export`（**組**一份存檔，宣告「這張圖的牆是這三塊」）| `ecl.BlockWallPieces` |
| 載檔時這一條**會不會被執行**？ | remake 補回選圖 | `ecl.BlockWallPiecesOnLoad` |

把前者也改成後者會壞掉：`dos-save-export` 換章時要靠宣告值把存檔的牆面參數換成
新章的，不換的話原版會拿**上一張圖的**選圖去新章的 `WALLDEF` 裡找，印
`Unable to load 1 from WALLDEF4.`。第 749 輪一度只留一支共用的，
`geo3-b10` 從 24／24 逐格相同掉到每張差 1,500～2,700 格——**兩個呼叫端問的
不是同一個問題，共用一支就會有一邊拿到錯的答案。**

⚠ **兩張表收到的段不一樣，而且應該不一樣。** `ECL5/0x33` 的天空寫在 `0x25`／
`0x3E`（閘門前，會跑），`LOAD PIECES` 卻在 `0x58`——那一段只有 `0x1B` 的
`GOTO 8045h` 到得了，而載檔時那個 `GOTO` 不會被執行（`IF <>` 條件不成立）⇒
`LOAD PIECES` 不重發，牆面要**以存檔記的 `OLDWALL` 為準**。

#### 段自己的 `LOAD PIECES` 贏過存檔

`ECL2/0x03`（下水道）的 `LOAD FILES`／`LOAD PIECES` 在 `0x14`／`0x1B`，
**閘門前，一定跑**，發的是 `1,2,4`。而 `dos-save-export` **同一章之內不改存檔的
牆面參數**（改了反而讓原版走到不一樣的狀態，第 679 輪實測），於是存檔帶著的是
提爾佛頓的 `1,2,3`。

以存檔為準的話槽 3 會用錯一塊：44 張畫面每一張差約 2,900 格，佔全量 545 張
剩餘差異的 **98.6%**——而畫面看起來完全正常（左右兩側最近的那一列牆換了圖，
中間整片逐格相同）。

⇒ 順序是：**段在 `eclBlockWallPieces` 裡就用表，不在就用存檔的 `OLDWALL`。**
不能反過來。

⚠ 兩槽模式的閘門 `4BE7h`／`4BE8h` 也要一起補，而且要**補在算牆面分派之前**：
`WallSetAssignmentsFor` 讀那兩格決定走兩槽還是三槽分支，拿底檔（提爾佛頓，
兩格都是 0）的值去判會走三槽，把死運算元 `15`／`18` 也當成要載的槽。

### 擷取的位置驗得出來，靠原版的區域地圖（第 751 輪）

`tools/dos-oracle-jump-capture.sh` 用自製存檔把原版放到指定的格子——**存檔寫
進去不等於原版照著站**，每一格都要核對。有座標顯示的圖直接從畫面把座標讀
回來；**不顯示座標的那些**（`geo5-b33`、`geo3-b15` 這一類只顯示朝向與時間）
改按 `AREA` 讀區域地圖：原版會在隊伍所在格畫一個箭頭，`tools/dos_screen_areamap.py`
從目標座標算出箭頭該落在哪一個字元格，再逐像素比對 `ARROW_NORTH`。

視窗是 16×16 地圖上的 11×11 窗，原點 `clamp(座標 − 5, 0, 5)`，預期字元格
`(3 + y − oy, 3 + x − ox)`，每格 16×16 像素。兩個正對照（`(1,4)`、`(8,15)`）
判 `ok`，兩個對調過的負對照都判 `mismatch`。

⚠ **區域地圖要在四張都拍完之後才按。** 進出區域地圖之後第一人稱視窗會停在
舊畫面：同一格「先拍再核對」是 **0 格差**，「先核對再拍」是 **5,953 格差**。
腳本把四行索引緩衝在 `$pending`，核對過了才寫進索引。

⚠ **每一張都要等畫面穩定再拍**（`settle()`：連拍到兩張完全相同才收）。
穩定判定**只比視窗**（640×400 畫面的第 48..223 列）——比整個畫面永遠等不到，
時鐘與游標一直在動。少了這一步，拍到的是上一格的殘影，而殘影本身是一張
**完全正常的遊戲畫面**，事後看不出來。(8,15) 四個朝向補這兩步之前是
3,334／2,319／2,451／2,480 格差，補完是 **0／0／119／0**。

⚠ **不要拿 GEO 幾何反推「擷取站錯格」。** 試過用 GEO 推「深度 1 有沒有牆」，
再看畫面在該有牆的地方是不是一整片同色，兩個方向都有偽陽性：

- 「有牆卻是一整片同色」——深度 1 的牆可能是**側牆**，畫在可視區邊緣、
  根本不蓋到中間那一帶。13 筆裡 9 筆是這種，其中幾筆逐格比對完全相同。
- 「沒有牆卻有內容」——**深度 2／3 的遠牆就畫在可視區中間**，正好落在同一帶。
  `geo5-b33` (13,14) N 被這樣誤標，而它逐格比對是 **0**。

⇒ 差異大不代表站錯格。**位置只能用畫面上的座標或區域地圖核對，核不到就別
下結論**；用幾何反推會得到自洽但錯的答案。

#### 剩下那 29 張差在哪（第 751 輪的線索）

**29 張裡有 28 張的視錐會走出 16×16 的地圖**（深度 0..3、側向 ±2）。唯一的例外
`geo5-b33-x02-y04-S` 把側向放寬到 ±3 也會出界 ⇒ **全部都與「視錐外緣落在地圖
之外」有關**。

`wrap` 改成 `false` 之後，`(0,4)` 朝南從 **差 222 變成差 2,101** ⇒ 原作**有**繞
回，remake 的繞回是對的。另一個方向也不成立——視錐出界的張數有 **265** 張，
其中 237 張逐格相同；繞回進來的格子有牆的有 **332** 張，其中 304 張逐格相同。

- `geo5-b33 (0,4) 朝南`：原版右側是天空，remake 多畫了一根帶門的岩柱。

  東西畫在不同的地方，不是少畫。

補拍到 `geo2-b04`（火刀據點）的兩格之後冒出 **13,748 格**差異，而**每一格的
差異都是同一個代換**（EGA 4 → 15）：原版是紅天花板、remake 是白的，牆與地板
完全相同——看起來就是一張正常的畫面。

成因在 `ECL2/0x04` 的進入碼：

```
0022  GOSUB   0x96F4                    { LOAD FILES／LOAD PIECES 之後 }
…
16F4  COMPARE C04F 0x95                 { C04Fh ＝ 牆頂／地形碼 }
16FA  IF =   → 16FB  SAVE 0A 4BFE       { 紅 }
1701  IF <>  → 1702  SAVE 09 4BFE       { 白 }
1708  CALL   2E10                       { 重畫 }
```

⇒ **天花板顏色由當下那一格的地形碼決定**，不是每段一個固定值。資料也對得上：
`geo2-b04` 地形 `95h` 的格子原版是紅（4），`80h`／`C0h` 是白（15）；而
`geo2-b01` 的地形 `95h` 是**白**的——同一個地形碼在不同段不同色，因為決定它的
是段自己的腳本。

三個修法，缺一不可：

| 修法 | 少了它會怎樣 |
|---|---|
| `ReachableOnLoad` 跟進 `GOSUB`／`RETURN` | 走訪在 `LOAD PIECES` 之後就停，那支子程式整個看不到 |
| 一個 `COMPARE` 後面可以跟好幾個 `IF` | `IF <>` 那一條變成「判不出來」被跳過，那一段只收得到一半 |
| 用**載檔當下的記憶體**重走一次（`ReachableOnLoadWithMemory`）| 靜態的表表達不了「看情況」 |

⚠ 第三個修法讀的 `C04Fh` 是 `syncDungeonECLRegisters()` 寫進去的 ⇒
`applyLoadTimeECLWrites` 一定要排在它之後。

量測（177 張子集：全部有差的 ＋ 每張圖 8 張逐格相同的控制組）：**18,600 →
4,852**，`geo2-b04` 16／16 全等，**129 張控制組一張都沒被打壞**；產生器產的
兩張表（天空選色、牆磚選圖）逐字未變。

#### 最尖的線索：`geo5-b33` 的最後一欄在解析出來的 GEO 裡是空的

那 6 個「remake 根本沒畫」的格子集中在兩張畫面：`geo5-b33 (15,4) E` 與
`(15,5) E`——都是**站在 x ＝ 15 往東看**。逐格看：

```
        原版（欄1）                  remake（欄1）
列4     B6BBBBBB … 767BBBBB          BBBBBBBB（天空）
列5     77786777 … 77606077          BBBBBBBB／00000000（天空與地平線）
列6     77606077 … 77778778          87787787（地板）
```

原版在那裡畫了一整片岩壁，remake 畫的是天空與地板。畫那一塊的是
`drawWallNear` 的正面牆（版面 6，`ColStart = −5`，欄 −5..1），它要求**近側左邊
那一格 `(15,4)` 有東面牆**——而解析出來的 GEO 說那一格**四面都沒有牆**。

★ 掃過全部 16 張圖的最後一欄：

| | 末欄 |
|---|---|
| `geo5-b33` | `0000000000000000`（**全 0**）|
| 其餘 15 張 | 全部非 0（如 `geo2-b01` 是 `36363AE363636367`）|

**只有這一張**。而 29 張有差的畫面裡 28 張都在 GEO5，其中 26 張就是這張圖。

⇒ 下一步：**用原版自己的區域地圖核對 GEO5 段 `0x33` 的解析**（`AREA` 會把整張
地圖畫出來）。拿 remake 的區域地圖去比是循環論證——兩邊讀的是同一份解析。

**原始位元組看過了：地圖本來就長那樣。** `cmd/geo-raw-dump` 把四個平面原樣
印出來——`geo5-b33` 的 x ＝ 15 那一欄在**牆面兩個平面與地形平面都是 `00`**，
不是解析漏了一欄（前綴 `00 04` ＝ 0x400，四個 0x100 的平面依序是
北東 nibble／南西 nibble／地形／細節）。

⚠ **「地形 0」也不是「不能站」。** 先做正對照再下結論：全作 4,096 格裡有
**1,042 格**地形是 0，而 `geo6-b42` 有 **204／256** 格是 0，卻是 27／27 逐格
全等。29 張有差的裡雖然有 27 張站在地形 0 的格子上，但**另外 341 張站在地形 0
上的畫面逐格相同** ⇒ 這個相關性解釋不了差異。

⇒ 所以 `(15,4)`／`(15,5)` 那兩張的「remake 沒畫」仍然沒有解釋：原版在那裡畫了
岩壁，而那一格四面都沒有牆、地形也是 0。下一步還是要用原版的**區域地圖**看它
自己認為那一帶長什麼樣。

#### ⚠ 三個把我送進死路的量測錯誤

- **`-facing` 是 0／2／4／6，不是 0／1／2／3。** 手動下
  `cmd/dos-save-export -facing 2` 想拍朝南，拍到的是朝東，於是「同一格重畫差
  2,101」看起來像 remake 不穩定。`tools/fp-oracle-compare.py` 的 `FACING`
  才是唯一真相（`{"N": 0, "E": 2, "S": 4, "W": 6}`）。
  ⇒ **要重現批次的數字就用批次的腳本**（餵一份只有那幾列的 `index.tsv`），
  不要手打參數。
- **檔名前綴有兩種**：`geo{集}-b{段}`（ECL 段＝幾何區塊）與
  `geo{集}-e{ECL段}-b{幾何區塊}`。只認前一種的話 `geo5-e31-b32` 會被餵成
  ECL 段 `0x32`，而 GEO5 的 `0x31` 與 `0x32` **共用幾何區塊、牆磚選圖卻不同**
  ⇒ 算出來的差異是假的（第一版因此把那三張多報了 96 個符號格）。
- **`gamepack` 的 `wrap` 旗標不影響第一人稱視野。** `prepareWallPreview` 一律
  呼叫 `gfx.TraverseWallViewWrapped`；`dungeonWrapEnabled()` 是給移動用的。
  把 `original.geo5.block-33` 的 `wrap` 改成 `false` 量到的差異變化**與視野
  無關**。真正的對照是把那一行換成 `gfx.TraverseWallView`——換了之後
  `(14,7) E` 48 → 150、`(15,5) E` 282 → 1,319 ⇒ **原版有繞回，remake 的繞回
  是對的**（這個結論不變，但先前的證據是無效的）。


### 天空選色也在該段的進入碼裡（第 749 輪）

`geo5-b35` 二十張畫面**每一張都差** 2,000～3,400 格，而差異全部是同一個代換：
原版 EGA `4`、remake EGA `15`，其餘顏色的直方圖逐色相同。位置是可視區上緣
整片全寬的那一帶（第 0..15 列滿寬，第 16..31 列隨透視收窄）——天空。

兩格的來源是 ECL 段自己的進入碼：

```
ECL5/0x35  0x002e  SAVE 0Ah 4BFEh          { 室內天空選色 := 10 }
ECL5/0x33  0x0025  SAVE 0Bh 4BFDh          { 室外 := 11 }
           0x0031  IF >
           0x0032  SAVE 08h 4BFDh          { 條件成立才覆寫成 8 }
           0x003e  SAVE 0Ah 4BFEh          { 室內 := 10 }
```

`4BFDh`／`4BFEh` 就是存檔 Area1 的 `OutdoorSkyColor`／`IndoorSkyColor`：Area1 的
字組索引是 `位址 − 4B00h`，位元組位移 `× 2` ⇒ `01FAh`／`01FCh`。選色索引再經
引擎的 `skyPalette`（`00,0F,04,0B,0D,02,09,0E`）查表才是 EGA 色號，
所以 `0Ah` → `skyPalette[2]` ＝ EGA **4**（原版），`09h` → `skyPalette[1]` ＝
EGA **15**（remake 從底檔繼承的值）。

⚠ **兩邊餵的是同一份存檔**（`dos-save-export` 兩側共用），所以這不是餵錯狀態：
原版載檔之後會跑該段的進入碼，把兩格改成這一段自己的選色；remake 不跑。
`cmd/ecl-sky-colours` 把 19 段的選色掃成 `internal/game/skycolors_table.go`，
與牆磚選圖同一個做法、同一個鍵（**ECL 段**，不是地圖）。

⚠ **只掃「有沒有這條 `SAVE`」會多收八段。** 段的開頭幾乎都有一道
`COMPARE 4BF2h, <自己的段號>` 的閘門，而**兩個方向都有人用**：

| 段 | 閘門 | 載檔時（`4BF2h == 段號`）|
|---|---|---|
| `ECL4/0x21` | `IF =` → `GOTO 8112h` | 跳過整段前置，天空**不寫** |
| `ECL3/0x11` | `IF =` → `EXIT` | 直接結束，天空**不寫** |
| `ECL5/0x33` | `IF <>` → `GOTO 8045h` | 不跳，天空**照寫** |
| `ECL3/0x15` | 沒有閘門 | 天空**照寫** |

`4BF2h` 就是存檔的 `LastECLBlockID`，而 remake 套這張表的時機正是「載入一份
記著這一段的存檔」⇒ 那一刻 `4BF2h == 段號`。所以 `cmd/ecl-sky-colours` 是在
**這個條件成立的前提下走一次五個進入點**，只收真的會跑到的寫入：
43 處 → **23 處、11 段**。判斷不了的分支一律停下來，不猜。

⚠ 第一版沒有這一層，多收了八段，把 `geo2-b03`／`geo3-b10`／`geo4-b21`／
`geo4-b25` 四張圖的天空改錯，合計 **32 萬格**——而症狀是整片純色換成另一片純色，
**沒有任何視覺提示**。這一筆是全量 545 張跑完才浮出來的：四張目標圖的 80 張
全部變好，同一次改動卻在**沒去看的地方**壞掉。
**改一個跨全域的查表之後，不能只量你瞄準的那幾張。**

⚠ 段內的第二層守衛（例如 `ECL5/0x33` 那條被 `IF >` 守著的 `08h`）要看執行時的
記憶體，靜態決定不了 ⇒ 那一條照樣跳過。

⚠ 這一類錯誤**沒有任何視覺提示**：天空是一整片純色，錯的顏色也是一整片純色。
一開始它被算進「四張圖畫不出牆」那一筆，但其實與牆無關。

### 載入原版存檔之後，牆是空氣（第 676 輪修好）

原版存檔裡**有**牆磚選圖：第 9..14 欄就是 `OLDWALL`（見上面那一節）。載檔時
原版走 `overlay-16:4DF3h`（`LOADSAVE`）把它重播一次：

```pascal
if OLDWALL[1].num > 0 then                    { 4DF3h }
  載入這一張圖的天／地資源;                    { 4DFAh..4E04h }
for i := 1 to 3 do                            { 4E09h..4E53h }
  if OLDWALL[i].num > 0 then
    LOADWALLSET(OLDWALL[i].slot, OLDWALL[i].num);
```

`num ≤ 0` 的槽跳過——`0` 是沒載過，`-1` 是被多槽載入當成續段填掉的（上一節的
`110Dh`）。**牆面不靠重跑 ECL 段的進入碼還原**。

remake 載入存檔時同樣不重跑那一段（會連帶觸發劇情副作用）。存檔的第 9..14 欄
是空的時候（自製存檔的預設）`LoadPieces` 才會停在 `[0 0 0]`。

⚠ 全零不報錯，它把**每一面牆都畫成空氣**：天空、地板、UI 全都在，畫面看起來
完全正常。第 675 輪就是拿這種畫面去跟原版比，差 37.6%，差一步被判成
「第一人稱畫錯了」。

修法是查表補值。`cmd/ecl-wall-pieces` 掃過全部六個 ECL 檔：**19 個段各發出
剛好一組常數三元組，沒有一個是多組，也沒有一個是記憶體參照**——查表在這份
corpus 上才成立，這是先量過才敢做的前提。

⚠ 鍵是 **ECL 段**，不是地圖。GEO5 的 `0x31` 與 `0x32` 共用同一張幾何區塊
`0x32`，牆磚選圖卻是 `12,255,255` 與 `8,255,255`。照地圖查會在其中一塊給出
自洽但錯的牆。

⚠ 而且要用**存檔記下來的**那個段（`LastECLBlockID`），不是 session 當下的段：
載入之後 `CurrentBlockID()` 還停在初始化的世界地圖段 `0x50`，拿它去查一定
查不到，而查不到的後果是安靜地不補，牆照樣是空氣。

驗收：拿**同一份存檔**餵原版與 remake，(8,2) N 的 88×88 可視區差 **0 格**。

逐地圖的「新增幾種」那一欄直接就是工作順序：提爾佛頓 108 種全新、
`geo5/0x33` 104 種、墓園 45 種……而 `myth-drannor.inner-ruins` 與
`geo6/0x45` 各只新增 1 種——那兩張幾乎不必單獨比。

## 遮蔽是這個分母能用的唯一原因

前兩版都算出沒有用的數字：

| 版本 | 簽章內容 | 相異數 |
|---|---|---:|
| 一 | 前方三排 × 橫向 ±1，記**牆型值** | 15,693 |
| 二 | 同上，改記**有無** | 14,294 |
| 三 | 有無 ＋ **遮蔽** | **585** |

第一版把兩個軸混在一起，牆型在幾乎每一格都不同，於是去重等於沒做。
第二版分開了軸，但簽的是**原始鄰域**而不是**看得到的東西**：走廊裡一面牆擋住
之後，後面那幾排根本不會畫出來，把它們簽進去等於在區分兩張一模一樣的畫面。

⚠ 兩個數字都是誠實的——它們確實是那個定義下的相異數。**誠實但沒有用**：
定義本身沒有對上「玩家看到什麼」。分母的定義跟數字一樣需要被檢查。

第三版的遮蔽規則：

- 中央那一行從腳下往前，每一格記左右牆；**前方有牆就記下來並停止**。
- 兩側只有「側牆是開的」那一格看得進去；側牆一擋，那一側往後全部不可見。

## ⚠ 「站得住」那個過濾器是錯的

第一版把「四面都是實牆」的格子排除在分母外，理由是玩家進不去。
`-covered` 一跑就出現四張擷取**對不到任何格子**——而那四張是
`GEO2/0x01 (7,13)` 的四個朝向，也就是**開新遊戲的起點**。它確實是密室
（劇情要求先找出口），而它是每個玩家看到的第一張畫面。

⇒ 分母改收全部 256 格／張，密室只記數字不拿來過濾。工具照實回報「對不到」
而不是靜靜丟掉，那個矛盾才浮得出來——**過濾器也是斷言**（AGENTS §3）。

## 明確不宣稱

- **沒有宣稱比完 585 種就等於第一人稱正確。** 天空色、牆磚選圖與調色盤跟著
  地圖宣告走，各自要比——spec 1134 那個黑掉的天花板就是這一類，而它在 20 張
  裡的每一張都錯，逐格比對本身抓不出「兩邊都照同一個錯宣告畫」。
- **沒有宣稱這 585 種玩家都走得到。** 「站得住」的判準是「至少一面沒有牆」，
  那不是可達性。真正的可達性要從入口做連通性走訪，還要考慮腳本傳送。
- **沒有宣稱那 12 種是對的。** spec 1134 說那 20 張裡 19 張與原版相同、1 張差
  一格；這裡只算「比過幾種」，不重述比對結果。
- 遮蔽模型是 `derived`：它取自 spec 1130 的幾何，沒有逐條對過 `BUILDVIEW`。
  如果原作在某些情況下畫得比這個模型多（例如門的另一側），585 會偏低。
