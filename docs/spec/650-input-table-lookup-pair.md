# 第六百五十輪：表查詢的 byte／word 兩個版本，與輸入緩衝的輸出轉換

狀態：`READY`。等級：`exact`。日期：2026-08-14
位置：PC-98 `PC98-GAME.EXE` 的 `1711Fh`、`170C5h`、`16FCFh`。

## `1711Fh` 與 `17148h`：同一種表，兩個寬度

```text
共同的表格式：第一個 byte 是筆數 n，其後是 n 個項目
共同的呼叫方式：DX ＝ 表位址（ES 段），BX 低位 ＝ 要找的值
共同的回傳：1 起算的序號；找不到回 0
```

| 位址 | 項目寬度 | 比較 |
|---|---|---|
| `1711Fh` | **byte** | `cmp al, dl` |
| `17148h` | **word** | `cmp ax, dx` |

兩支開頭都是 `xchg bx, dx`——**呼叫端把表放 DX、值放 BX**，進來才對調。照抄時容易
把兩者搞反。

因為 `0` 專門表示找不到，兩種表都最多 255 筆。

## `170C5h`：把輸入緩衝轉成輸出字串

```text
ES:DI := dword_1EB2D^ 指的位置
cl    := es:[di]                 ← 目前長度
di    := di + 1
es:[di] := 0                     ← 先放一個結尾 0
si := 28A4h                      ← 輸入緩衝
while cl <> 0 do
    bx := [si] ; cl := cl − 1
    if bh = 0 then
        es:[di] := bl ; di := di + 1            ← 單位元組直接搬
    else
        i  := <17148h>(bx, 2AE2h)               ← 用整個 word 查表
        ax := word[2AAEh + (i − 1) × 2]         ← 由序號取另一張表的值
        es:[di] := ax ; di := di + 2            ← 寫兩個 byte
    si := si + 2
```

**兩張表是平行的**：`2AE2h` 存「緩衝裡的表示法」、`2AAEh` 存「輸出用的
Shift-JIS 碼」，用同一個序號對應。所以緩衝裡存的**不是**最終碼，輸出時要翻一次。

這解釋了 [spec 649](649-japanese-input-buffer.md) 的合成寫法：合成階段把新 byte
併進前一字的高位元組，得到的是「緩衝表示法」；真正的 Shift-JIS 碼在這裡才查出來。

`i` 為 0（查不到）時 `(i − 1) × 2` 會變成 `−2`，讀到 `2AAEh` 前面兩個 byte——
**函式沒有檢查查表失敗**。緩衝內容若不在表裡，輸出的是表格前面那個位址的內容。

## `16FCFh`：清屬性

```text
ES := 0A200h
ax := byte_1ED35 重複兩次（高低位元組相同）
cx := byte_1ED34 × 2
rep stosw
```

填的格數是 `byte_1ED34 × 2`——因為每個字佔兩格
（[spec 648](648-pc98-text-draw-core.md)）。屬性值直接取 `byte_1ED35`，不像
`17D72h`／`169B6h` 那樣現算。

## 三張表在載入時不是表

試著把內容抄出來，結果不成立，記在這裡免得下次重做：

`dseg` 的基底可由兩組已命名的全域反推——`byte_1ED34` ＝ `dseg+2AA4h`、
輸入緩衝 `dseg+28A4h` 緊接在 `byte_1EB33` 之後——兩組都指向 **`1C290h`**。
再用 `169D9h` 的位元組在檔案裡定位，得到 linear 與檔案位移差 `0F660h`。

依此讀出 `2AAAh`／`2AAEh`／`2AE2h` 的載入時內容：前兩者是連續的 0，第三者是
`83 60 83 46 83 43 83 93`（Shift-JIS「チェイン」）——**是物品名稱的 Pascal 字串，
不是「筆數 ＋ 項目」的表**。

兩種可能：表在執行期才填（載入時那塊是別的用途），或 `dseg` 基底推導有誤。
本輪**不判斷是哪一種**，也因此不抄表格內容。要往下走的話，動態 dump 比靜態推更
直接。

## 明確不宣稱

- 三張表的實際內容與筆數（見上節）。
- `byte_1ED35` 的屬性語意。
- `170C5h` 開頭 `mov cl, byte_1ED34` 之後只做了一次 `stosb`（沒有 `rep`），
  那個 `cl` 賦值在該處沒有作用——是否為編譯／手寫殘留，本輪不判斷。
