# 867 — 結局動畫的一格重畫：3 × 40 的物件表，只送可見的去畫

- 證據等級：`exact`（DOS 側逐條讀完；PC-98 側逐條列出差異，**有兩處真的不同**）
- 作法見 spec 783

## `overlay-18:00780h` ↔ `overlay-18:00682h`（DOS 75 條／PC-98 76 條）

`overlay-18` ＝ ENDSTUFF（結局動畫）。`retf 0Ch` ＝ 6 個 word，
但本體只用到 `arg_0` 那個遠指標。

```pascal
Move(arg_0^, var_3, 3);                       { ⚠ var_3 之後沒有被讀 }

n := DS:4AD2h + 1;
for i := 1 to n do                            { 無號 }
    <本模組 04DFh>(i, 遠指標(DS:4ACEh));      { 帶靜態鏈，巢狀程序 }

for 行 := 1 to 28h do
    for 列 := 1 to 3 do begin
        p := 遠指標(DS:4ACEh) ＋ 列 * 398h ＋ 行 * 17h ＋ 0FC51h;
        if (有號(p^[2]) > 8) and (有號(p^[2]) < 41h) then
            <本模組 0000h>(p^[0], p^[2], p^[11h]);
    end;
```

## 版面由配置大小夾出來

`overlay-18:09DBh`（結局動畫主迴圈，已解讀）配置的是
**`GetMem(DS:4ACEh, 0AC8h)` ＝ 2760 bytes**。本支的索引算式
`列 × 398h ＋ 行 × 17h ＋ 0FC51h`（`0FC51h` ＝ 有號 −3AFh）在
`列 = 1、行 = 1` 時剛好是 0，所以實際版面是

```
3 列 × 40 行 × 23 bytes  =  2760
```

**配置大小與索引算式互相夾出同一個數字**，這比單看任一邊可靠。

物件記錄 23 bytes 裡本支只讀三格：`+0`（word）、`+2`（word）、`+11h`（byte），
原樣轉給命令 `0Ch`。

## 送出的是命令 `0Ch`

`本模組 0000h` 就是台帳裡的「送出命令 `0Ch`（`retf 6`）：填 `DS:4FCAh` 起的
16-byte 命令區塊」。三個參數依序落進命令區塊的 `+0`／`+4`／`+6`。

`+2` 的可見範圍檢查（`> 8` 且 `< 41h`）在送出前擋掉畫面外的物件——
**只有 9..64 這一段會被畫**。

## ⚠ 兩處兩平台真的不同

| | DOS | PC-98 |
|---|---|---|
| 上界 | `+2 < 41h`（65） | `+2 < 42h`（66） |
| 送出 | `本模組 0000h(三個參數)` | `sub_175D(三個參數, 1)`，**多一個常數 1** |

上界差 1 與 PC-98 多出來的那一列有關（PC-98 的畫面比 DOS 高一列的可見範圍），
但本規格**不宣稱**那個 1 是什麼。這是 spec 783 的第 d 類，不是碼型差異。

## ⚠ `Move(arg_0^, var_3, 3)` 是死碼

抄進 `bp − 3` 的那 3 bytes，函式其餘部分沒有再讀（迴圈上界用的是
`bp − 1Dh`，是另一個變數）。**兩平台都有這一段**，不是反組譯問題。
`retf 0Ch` 宣告了 6 個 word，本體只用第一個遠指標——其餘四個 word 也沒被讀。

## 明確不宣稱

- 沒有宣稱 `本模組 04DFh(序號, 緩衝)` 做什麼（形狀上是「推進第 i 個物件」）。
- 沒有宣稱物件記錄 23 bytes 的其餘 19 格是什麼。
- 沒有宣稱 `DS:4AD2h` 是什麼（形狀上是物件數 − 1）。
- 沒有宣稱 `+0`／`+2` 哪個是 x 哪個是 y。
