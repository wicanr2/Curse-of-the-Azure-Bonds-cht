# 971 — DOS 的 `bigpic` 載入器：資源快取的第三格終於有名字

- 證據等級：`exact`（DOS 側逐條讀完；PC-98 對應支 spec 758 已讀完，本規格只做對照）
- 作法見 spec 783

## `overlay-29:00813h`（DOS 51 條）↔ `overlay-29:0072Bh`（PC-98 36 條）

`retf 2` ＝ 一個 byte（圖塊編號）。字串常數 `'bigpic'` 在 DOS `CS:080Ch`、
PC-98 `CS:0724h`。

```pascal
本模組 055Bh(@DS:722Ch);                       { 先把另一組資源整批釋放 }

if DS:7290h = 編號 then 離開;                  { 已經是這一張就什麼都不做 }

Str(DS:5BEEh, 寬度 1, var 磁碟);               { 0A54h:12ABh，一位數 }
檔名 := 'bigpic' ＋ 磁碟;                      { 0A54h:0634h ＋ 0A54h:06C1h }
<far 0297h:011Bh>(檔名, 編號, 0, 0, @DS:728Ch);
DS:7290h := 編號;
```

## `far 0297h:011Bh` 的參數順序定案

DOS 側三個呼叫端（本支、spec 874 的頭像與身體）推疊順序完全一致：

```
build-string 留在堆疊上的 @檔名   ← spec 916 的收尾規則
push 編號
push 0
push 0
push @目的遠指標
call far 0297h:011Bh
```

所以簽章是

```pascal
procedure 載入資源(檔名: string; 編號: byte; a, b: byte; var 目的: pointer);
```

⚠ **spec 874 把順序寫反了**（寫成 `(@DS:726Fh, 0, 0, 編號A)`）。
`overlay-29:005DDh` 的 `062Dh`..`063Ch` 逐條為
`push 編號`／`push 0`／`push 0`／`push ds:726Fh`／`call`——
**目的指標是最後一個參數，編號是第一個**。spec 874 已就地更正。

## 資源快取的三格全部命名

spec 750 的戰鬥開場一口氣釋放三格：

| 指標 | 編號哨兵 | 資源 | 出處 |
|---|---|---|---|
| `DS:726Fh` | `DS:726Eh` | `HEAD`（頭像） | spec 874 |
| `DS:7274h` | `DS:7273h` | `BODY`（身體） | spec 874 |
| **`DS:728Ch`** | **`DS:7290h`** | **`bigpic`（全螢幕大圖）** | **本支** |

`DS:7290h` 在新遊戲初始化時被設成 `0FFh`（spec 892），與另外兩格的
「沒載入」哨兵同一套寫法。三格的版面都是**指標 4 bytes 緊接編號 1 byte**
（`728Ch` ＋ 4 ＝ `7290h`）。

`'bigpic'` 就是原始映像裡的 `BIGPIC1.DAX`／`BIGPIC2.DAX`／`BIGPIC6.DAX`
（round-82 那一輪從資料側認出來的檔案）。DOS 把 `DS:5BEEh` 的磁碟編號轉成
一位數接在後面，湊出實際檔名——與 spec 926 的 `WALLDEF`、spec 882 的圖磚
是同一套組檔名手法。

## ⚠ 兩平台的快取守衛判斷的東西不同

| | DOS `00813h` | PC-98 `0072Bh` |
|---|---|---|
| 守衛 | `DS:7290h = 編號` → 跳過 | `DS:0A327h <> NIL` → 跳過 |
| 檔名 | `'bigpic'` ＋ 磁碟數字 | 只有 `'bigpic'` |
| 載入呼叫 | `0297h:011Bh`，5 個參數 | `02A8h:025Bh`，**多一個 0** |
| 局部緩衝 | `102h`（258 bytes） | `0Ah`（10 bytes） |

**DOS 換編號會重載，PC-98 換編號不會。** PC-98 只看指標在不在，所以在沒有
中間釋放的情況下第二次請求會被整支跳掉，畫面上留著前一張。這與 spec 874 的
「DOS 串接磁碟數字、PC-98 不串接」是同一組平台差異——PC-98 的資源位置固定，
而且大圖在它那邊是「一次載入用到底」的用法。

remake 要對齊哪一邊得先決定；照 DOS 的編號守衛寫比較安全。

## ⚠ DOS 重載時不釋放舊的那一塊

本支在 `0297h:011Bh` 之前沒有釋放 `DS:728Ch` 原本指到的記憶體，與 spec 874
的頭像／身體兩格完全一樣（PC-98 那兩格會先叫 `02A8h:10D5h` 釋放）。
本規格不宣稱 `0297h:011Bh` 內部有沒有處理，只記錄呼叫端這一層沒有。

## `本模組 055Bh` ＝ 八格資源表的整批釋放

開頭那個 `push ds; push di; push cs; call near ptr sub_55B` 是
**「`push cs` ＋ near call」模擬遠呼叫**的標準 Turbo Pascal 寫法
（目標以 `retf` 收尾）。

```pascal
n := 表^[0];
if n >= 1 then
    for i := 1 to n do
        <far 0297h:1D19h>(@表^[8i − 2]);       { 逐格釋放 }
FillChar(表^, 42h, 0);
DS:7278h := 0;
DS:728Ah := 0FFh;
```

把 `8i − 2` 與 `FillChar` 的 `42h`（66）合起來看，表的版面就定了：

| 位移 | 內容 |
|---|---|
| `+0` | 格數 n |
| `+1` | （未讀） |
| `+2 ＋ 8(i−1)` 起 8 bytes | 第 i 格 |
| 　└ 格內 `+4` | 遠指標（被 `0297h:1D19h` 收走的那一個） |

`i` ＝ 8 時最後一格是 `+58h`..`+65h`，**正好用滿 66 bytes ⇒ 表固定 8 格**。

PC-98 的對應支 `overlay-29:0045Ah`（spec 760）是同一份版面加 1：
`8i − 1`、`FillChar 43h`（67）、表頭 3 bytes，同樣 8 格。
spec 760 當時只記了「間距 8 bytes」，格數由本支補上。

`0297h:1D19h` 到目前為止的四個用法（本支、spec 750 的三格）全部是
「收一個遠指標的位址，之後呼叫端把哨兵寫回 `0FFh`／`0`」，
**形狀上就是釋放器**；本規格仍不宣稱它的內部行為。

## 中文化

`'bigpic'` 是檔名前綴，**不能翻**，也不能改大小寫——DOS 端最後會經
`FExpand` 轉大寫，但常數本身要照留。本支沒有任何給玩家看的字串。

## 明確不宣稱

- 沒有宣稱 `0297h:011Bh` 中間那兩個 `0` 是什麼。
- 沒有宣稱 `DS:722Ch` 那八格裝的是哪一類資源（只知道版面與釋放時機）。
- 沒有宣稱 `DS:7278h`（釋放後歸零）與 `DS:728Ah`（釋放後 `0FFh`，spec 876 用
  `= 50h` 分支）的意義。
- 沒有宣稱本支的呼叫端是誰。
