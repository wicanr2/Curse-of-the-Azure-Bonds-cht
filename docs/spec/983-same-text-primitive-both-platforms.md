# 983 — `0542h:0352h` 與 `0418h:0D17h` 是同一支；清單項的「反白」是換顏色欄位

- 證據等級：`exact`（兩支 overlay 函式逐條讀完；兩個常駐入口的堆疊框直接對照）
- 作法見 spec 783

## ★ 更正：兩平台的印字入口是同一支函式

spec 975 寫過「**這兩支是不同的函式，不能互相套用簽章**」——**那是錯的**。

把兩個常駐入口並排（線性位址換算：兩平台的 IDA 載入基底都是 `1000h`，
所以 `0542h:0352h` ＝ `START.EXE:15772h`、`0418h:0D17h` ＝ `PC98-GAME.EXE:14E97h`）：

| | DOS `15772h` | PC-98 `14E97h` |
|---|---|---|
| `retf` | `0Ch` | `0Ch` |
| 進來第一件事 | `限長(arg_0^, 本地, 0FFh)` | 同 |
| 座標守衛 | `arg_A > 27h` 或 `arg_8 > 27h` 就整支跳過 | 同 |
| 參數位置 | 字串 `bp+6`、`arg_4` `bp+0Ah`、`arg_6` `bp+0Ch`、列 `bp+0Eh`、欄 `bp+10h` | 同 |

**五個欄位一格不差**。兩支是同一份原始碼在兩個平台的編譯結果，
差別只在下游：DOS 逐字元呼叫 `15606h`（每畫一個字 `inc(欄)`），
PC-98 先過 `145CAh` 再把整串交給 `1692Dh`（DBCS 感知，見 spec 973）。

所以 spec 973 由 PC-98 堆疊框定出來的簽章 **DOS 也適用**，
spec 975 那句「不同的函式」已就地更正。

### ⚠ 第三、第四個參數是兩個顏色欄位，不是「顏色 ＋ 未用」

`15772h` 把自己的 `arg_6` 與 `arg_4` 原封不動往下傳給 `15606h`
（spec 937 的畫字元分派層），落在它的兩個顏色參數上。
所以呼叫端看到的形狀是

```pascal
印字(欄, 列, 顏色A, 顏色B, 字串);
```

而**各呼叫端把算出來的顏色放在哪一格並不一致**：

| 呼叫端 | 顏色A | 顏色B |
|---|---|---|
| `overlay-24:0177Ah`（訊息列，spec 693） | `0Ah` | `0` |
| `overlay-24:018F3h`（角色名字，spec 693） | 陣營色 | `0` |
| `overlay-26:00AF8h`（本規格） | 視窗`+24h` 或 `+22h` | `0` |
| **`overlay-26:00A56h`**（spec 975） | **`0`** | **視窗`+20h`** |

一直到 spec 975 為止，這被當成「DOS 把參數順序寫反了」。
**更合理的解釋是：那兩格是前景與背景，換一格就是反白。**
`00A56h` 與 `00AF8h` 是同一個清單的兩種畫法（一般／反白），
視窗記錄的 `+20h` 與 `+22h`／`+24h` 分別餵給不同的那一格。

⚠ **哪一格是前景、哪一格是背景，本規格不宣稱。**
spec 937 把 `15606h` 的 `arg_6` 標成前景、`arg_8` 標成背景；
照那個標法代回去，訊息列 `0177Ah` 會變成「黑字、亮綠底」，
與 Gold Box 實機畫面不符。**要定案得回頭把 `16147h` 逐條讀完**
（spec 935 只記到「前景與背景都要過 `DS:256Dh` 轉換表」）。
在那之前，spec 693 的 `(x, y, colour, mode, str)` 這個命名應視為未定。

## `dos overlay-26:00AF8h`（111 條，`retf 4`）— 反白版的單項重畫

`(視窗的 SS 偏移 arg_0, 項次 arg_2)`，與 `00A56h`（spec 975）逐句同構：

```pascal
p := <本模組 0011h>(項次, 視窗^[16h], 視窗^[14h]);
a := <本模組 09C4h>(p, 視窗);
b := <本模組 0A10h>(p, 視窗, a) − a ＋ 1;
色 := 視窗^[22h];
if p^[29h] <> 0 then 色 := 視窗^[24h];
印字(視窗^[1Eh] ＋ a − 1, 視窗^[1Ch] ＋ (項次 − DS:7292h), 色, 0, Copy(p, a, b));
```

**`p^[29h]` 是項目自己的旗標**，在 `+22h` 與 `+24h` 兩個顏色之間二選一。

★ 這一格對上 PC-98：spec 973 的 `pc98 overlay-26:00BFEh` 用的是 **`p^[51h]`**，
同樣在 `+22h`／`+24h` 之間選。所以

| DOS | PC-98 | 意義 |
|---|---|---|
| 項目 `+29h` | 項目 `+51h` | 選色旗標 |
| `DS:7292h` | `DS:0A32Ch` | 清單捲動起點 |

DOS 與 PC-98 的項目節點版面差很多（spec 756／760 記過 PC-98 重排過），
`+29h` ↔ `+51h` 是這條線上的新一格。

## `dos overlay-24:01975h`（123 條，`retf 8`）— 把圖庫的一張圖填進動畫 surface

`(組 arg_6, 編號 arg_4, 格號 arg_2, 要不要轉換 arg_0)`。

```pascal
每格 := 遠指標(DS:75E0h)^[11h];                 { surface 的「每 sheet 幾 bytes」 }

if 要不要轉換 <> 0 then begin
    <0297h:1C59h>(18h, 3, 1, 1, @暫存);          { 建一張新圖 }
    <0297h:0BB5h>(暫存, 遠指標[65D6h ＋ 組×8 ＋ 編號×4]);   { 轉換複製 }
    Move(暫存^ ＋ 17h,        DS:75E0h^ ＋ 格號×每格 ＋ 17h, 每格);
    Move(暫存^[13h]^,          DS:75E0h^[13h] ＋ 格號×每格,   每格);
    <0297h:1D19h>(@暫存);                        { 釋放 }
end
else begin
    Move(原圖^ ＋ 17h,   DS:75E0h^ ＋ 格號×每格 ＋ 17h, 每格);
    Move(原圖^[13h]^,     DS:75E0h^[13h] ＋ 格號×每格,   每格);
end;
```

兩條路都是**搬兩塊**：`+17h` 起的像素平面，以及 `+13h` 那個遠指標指到的遮罩平面
——與既有的 surface 版面（表頭 `17h` bytes、`+8` 張數、`+11h` 每張 bytes、
`+13h` 遮罩遠指標、`+17h` 起像素）完全吻合，**這一支是那份版面的直接用例**。

`DS:75E0h` 是一張**多格的動畫 surface**，本支負責填第 `格號` 格；
圖源是 spec 977 定案的二維圖庫表 `遠指標(DS:65D6h ＋ 組 × 8 ＋ 編號 × 4)`
（每組 8 bytes ＝ 兩個編號）。

`arg_0 <> 0` 走 `0297h:0BB5h` 轉換複製——與 `overlay-33:00508h`
（spec 977 引的既有結論「模式 > 3 走 `297h:0BB5h`」）是同一個轉換器。

⚠ `0297h:1C59h` 的五個參數是 `(18h, 3, 1, 1, @結果)`。`18h` ＝ 24 與
spec 979 讀到的 24 寬相符；`3` 若是「列」，依全專案不變量（一列 ＝ 8 條掃描線）
就是 24 條掃描線。**本規格不宣稱那四個常數各是什麼。**

## 明確不宣稱

- 沒有宣稱 `15606h` 的兩個顏色參數哪一個是前景（見上）。
- 沒有宣稱 `DS:75E0h` 那張動畫 surface 有幾格、由誰配置。
- 沒有宣稱 `0297h:1C59h`／`0BB5h` 的參數意義。
- 沒有宣稱 `overlay-26` 的 `0011h`／`09C4h`／`0A10h` 做什麼（同 spec 973／975）。
- 沒有宣稱項目節點 `+29h`（PC-98 `+51h`）代表哪一種狀態。
