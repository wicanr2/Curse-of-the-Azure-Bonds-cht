# 1005 — 效果分派表：147 個效果碼各配哪一支處理常式

- 證據等級：`exact`（DOS 側 569 條逐條讀完；PC-98 對側 569 條**助憶碼序列
  完全相同**，相似度 1.000。表的內容由 `scripts/effect_dispatch_table.py`
  從同一份 dump 機械解碼，不靠人工抄寫）
- 作法見 spec 783；完整對照表在
  [`docs/audit/effect-dispatch-table.md`](../audit/effect-dispatch-table.md)

## `dos overlay-12:02E3Ch` ↔ `pc98 overlay-12:02ED4h`（`retf`，不收參數）

兩側原本都是待解讀。整支沒有分支、沒有迴圈、沒有呼叫——
**569 條全部是 `mov ds:xxxx, ax` ／ `mov ds:xxxx, dx` 的直線賦值**，
把 141 個 far pointer 寫進 `DS:6FAAh`（PC-98 `DS:A044h`）起的一張表。

### 為什麼那些 far pointer 是「函式」

寫進去的段值只有兩個：DOS 的 `0094h` 與 `00C1h`。
兩者在 IDA 的段表裡都是 `CODE`，長度分別 720 與 272 bytes，
而寫入的位移彼此相差 **5**——正好是 Borland overlay 的 entry stub 長度
（`CD 3F` ＋ 進入點位移 word ＋ 旗標 byte）。

換算兩步就對回 `ovr-manifest.json`：

```
段:位移            → 線性  = (1000h ＋ 段) × 10h ＋ 位移      { IDA 載入基底 1000h }
executable_offset  → 線性  = 10000h ＋ offset − MZ 標頭長度
```

DOS 的 MZ 標頭是 123 個 paragraph（1968 bytes），PC-98 是 154 個（2464）。
對上之後，**每一個 far pointer 都精確落在某個 overlay entry 的 stub 上**，
沒有一個落空。

## ★★ 消費端與索引方式

全 DOS 只有一處讀這張表——`overlay-23:00C9h`，PC-98 符號名 **`CALLEFFECT`**
（spec 576 已讀完該支，但當時只知道「有一張 far pointer 表」）：

```asm
mov  al, [bp+10h]        ; 效果碼
xor  ah, ah
mov  di, ax
shl  di, 1
shl  di, 1               ; di := 效果碼 × 4
call dword ptr [di+6FA6h]
```

基底是 `6FA6h` 而第一個被寫入的槽是 `6FAAh` ⇒ **效果碼從 1 起算**。
最後一個被寫入的槽 `71F2h` ⇒ **效果碼 1..147**。

把兩邊的簽章接起來：

```pascal
procedure CALLEFFECT(效果碼: byte; 角色, 節點: 遠指標; 旗標: byte);
{ retf 0Ch。轉發時只推後四個（10 bytes），所以每支處理常式都是： }
procedure 效果處理(角色: 遠指標;   { bp+0Ch..0Fh }
                   節點: 遠指標;   { bp+08h..0Bh }
                   旗標: word);    { bp+06h }   { retf 0Ah }
```

這正是 spec 748 從 `0C61h` 自己的堆疊框推出來的那組參數位置，兩邊獨立對上。

### ★ `DS:7582h` 非零時整張表被跳過

`CALLEFFECT` 的第一道判斷是 `cmp byte ptr ds:7582h, 0`，非零就**不查表**，
直接 `call dword ptr ds:71F2h`——那正是**效果碼 147 的槽**。
也就是說旗標一開，所有效果呼叫都被導到同一支，**效果碼整個被丟掉**。
PC-98 同構（`DS:0A66Eh` ／ `DS:0A28Ch`），spec 576 記過這條分支，
現在知道它導去的是表內的最後一格，不是另一張表。

## ★★ 效果碼與效果節點的 `+0` 是同一個號碼

spec 999／1003 從**建構端**讀出兩朵雲的效果碼：毒霧 `28h`（40）、毒雲 `5Bh`（91）。
把這兩個號碼拿來查本表：

| 效果碼 | 處理常式 | 既有判讀 |
|---|---|---|
| 40 | `overlay-12:0C61h` | spec 748：解除雲霧，鏈頭 **`DS:755Bh`**、格數 4、磚碼 `1Eh` |
| 91 | `overlay-12:1CF6h` | spec 748：同一段原始碼的第二份，鏈頭 **`DS:755Fh`**、格數 9、磚碼 `1Ch` |

★ 鏈頭、格數、磚碼**三項全部對上**——毒霧配 40、毒雲配 91，一項不差。
兩個結論當初一個從建構端推、一個從解除端推，彼此沒有引用。

> **效果節點 `+0` 存的那個號碼，就是 `CALLEFFECT` 的索引。**

## ★ 128 支相異處理常式，121 支早就讀過

147 個效果碼指向 **128 支相異函式**（有重用），其中：

- **121 支在台帳上已是「已解讀」**——這張表等於一次把 spec 573／633／638／639／
  640／641／642／676／677／678／679／737／738／739／740／741／742／743／744／
  745／746／747／748／805／819／826／831／832／851 裡那些「不知道誰會呼叫」的
  處理常式，**全部接上了自己的效果碼**。
- 重用最多的是 `overlay-12` entry#135（`02E33h`／PC-98 `02ECBh`），
  一支**空函式**（spec 569），被 7 個效果碼共用：**5、19、24、92、127、140、146**
  ——形狀上是「這幾號沒有實作」。
- entry#5（`00075h`，兩平台同位址）被 5 個效果碼共用：**27、31、51、52、53**。
- 只有 5 個效果碼跨模組指到 `overlay-13`：**57、87、96、139、144**
  （engulf、眼魔眼柄、扭打結算等特殊攻擊）。

### ⚠ 六個效果碼從頭到尾沒有被指定

**86、88、90、128、131、132** 這六格，兩平台的初始化函式都沒有寫，
而全 DOS／全 PC-98 也**沒有任何其他地方寫這六個位址**
（`70FEh`／`7106h`／`710Eh`／`71A6h`／`71B2h`／`71B6h`）。

Turbo Pascal 的全域變數開機清零，所以它們是 `0000:0000`。
**真的用這六個號碼呼叫 `CALLEFFECT` 會 far call 到零位址。**
兩平台完全一致，形狀上是「這幾號在開發途中被拿掉了」。

## ★★ 七筆台帳被誤標成「邊界碎片」，其實是正式進入點

效果碼 **41、63、64、65、66、67、78** 指到的七支，台帳原本標
「邊界碎片：body 內沒有 ret」。但它們是 overlay entry stub 的目標，
**起點不可能是 IDA 猜的**；拿補洞匯出重讀，七支都是完整的 `retf 0Ah` 函式。

> 這是 spec 988 那條規則的第七、第八…次應驗：
> **補洞匯出與未補洞匯出打架時，補洞的那份贏。**

七支都已逐條讀完（兩平台各自讀，助憶碼序列相同）：

| 效果碼 | DOS | 內容 |
|---|---|---|
| 41 | `0100Fh` | `w := 取武器(DS:6506h)`；`w <> NIL` 且 **`w^.plus = 0`**（`+32h`，spec 1011）時 `<sub_F39>(角色, 64h)` |
| 63 | `01415h` | `DS:6F97h > 0`（法術編號）且 `byte[DS:6F97h × 16 ＋ 37DBh] < 4` 時 `<sub_1B>(0)` |
| 64 | `01569h` | `<sub_1454>(角色, 節點, **0**)` |
| 65 | `0157Fh` | `<sub_1454>(角色, 節點, **4**)` |
| 66 | `01595h` | `<sub_1454>(角色, 節點, **2**)` |
| 67 | `015ABh` | `<sub_14F9>(角色, 節點, <overlay-23 entry#9>(2, 8), 0)`——**2d8** |
| 78 | `0192Dh` | `<overlay-23 entry#23>(角色, 角色^[1A4h])`（`STANDUP`）回 0 時，`<sub_3C>(角色, 4Eh, 節點^[3], 1)` |

★ 64／65／66 三支只差一個常數（0／4／2），是同一支的三個包裝——
Turbo Pascal 沒有預設參數，作者就複製三份。

⚠ 兩處欄位偏移兩平台不同（spec 641 記過的同一類）：
效果碼 41 的武器欄位 DOS 是 `+32h`、PC-98 是 `+5Ah`（spec 1011：**整個物品節點在 PC-98 位移 `+28h`**）；
效果碼 78 的角色欄位 DOS 是 `+1A4h`、PC-98 是 `+1A5h`。
**引用前各自確認。**

## ★ IDA 的 `arg_N` 又一次對不上

同樣是 `retf 0Ah`、同樣是 `bp+0Eh`，IDA 在 `01569h` 標成 `arg_A`、
在 `02606h` 標成 `arg_8`。**`arg_N` 不等於 `bp+N`**，
簽章一律從被呼叫者自己的堆疊框重建（spec 983 同一條）。

## 明確不宣稱

- 沒有宣稱每個效果碼**叫什麼名字**。效果碼與 `DS:27BDh` 的**法術編號是兩套號碼**
  ——spec 842 的 `Fear 84`／`Slow 55`／`Sleep 21` 是法術編號，不是本表的索引。
- 沒有宣稱 `DS:7582h`（PC-98 `DS:0A66Eh`）由誰設定、代表什麼模式。
- 沒有宣稱效果碼 86／88／90／128／131／132 當初是什麼。
- 沒有宣稱 `sub_1454`／`sub_14F9`／`sub_F39`／`sub_3C`／`sub_1B` 的內部行為
  （它們是 `overlay-12` 的模組內共用子程序，另有台帳列）。
- `DS:37DBh`（PC-98 `DS:61B5h`）那張 16 bytes 一筆、以法術編號為索引的表，
  `+5` 已在 spec 1009 定案（低 nibble ＝ 目標模式）；其餘 14 個 byte 仍未宣稱。
