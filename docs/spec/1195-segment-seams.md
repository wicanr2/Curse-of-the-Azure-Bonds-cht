# 1195 — 分段驗收的接縫：直入宣告的前一段，和主線實際的前一段

狀態：`READY`（`LastECL` 與整包 ECL 記憶體都有分母、結果與修法；攜帶物還沒比）

## 問題

使用者 2026-08-16 決定**分階段驗收算數**（`AGENTS.md` §3）：每一段用 debug
進入點直入、各自對 reference 驗證無誤即算該段完成，**不必為了宣稱完成而跑一次
連續全程**。同一條決定接著寫：

> ⚠ 段與段之間的狀態交接本身就是一段（存檔、旗標、隊伍、pending ECL／combat
> transaction）。debug 旗標注入的是合成起始狀態，未必等於上一段真的跑出來的
> 結束狀態；**兩端都綠不等於接縫通過**，接縫要自己列一段驗。

那句話一直沒有數字。這份 spec 是它的第一個分母。

## 為什麼先比 `LastECL`

直入時 `internal/segment` 的 `EnterFrom` 會被寫進 `4BF2h`（LastECL）。這是
**唯一一個直入時被明文合成出來的欄位**——隊伍、旗標、攜帶物、ECL 記憶體在直入
時都是沿用當下的狀態，沒有「宣告值」可比。所以 `LastECL` 是唯一一個現在就問得
出「宣告 vs 事實」的欄位。

⚠ 反過來說，**這份報表通過不代表接縫通過**。它只證明「段的入口編號宣告對了」。

## 事實從哪裡來

主線跑一次，在**換段的瓶頸**上記下 `(前一段, 這一段)`：

```
requestMusicIfBlockChanged(previous)        // internal/game/music_events.go
    if 現在的 block != previous:
        recordBlockEdge(previous, 現在的 block)   // ← 這裡
        重新派曲
```

★ 搭這班車是刻意的：那正是**換段時要重新選曲**的地方。所以「漏掉某個轉移」與
「那個轉移的音樂會錯」是**同一件事**——兩個盤點共用一個訊號，不是各自獨立的
假設。要是哪天音樂在某個換段點沒換，這份接縫報表也會少一條，兩邊會一起紅。

⚠ 仍是**下界**：走不到那個瓶頸的換段方式（若有）錄不到。

## 結果

| | |
|---|---:|
| 註冊表的段 | 25 |
| 主線真的走到 | 18 |
| 宣告的前一段 ＝ 實際的前一段之一 | **18** |
| **對不上** | **0** |
| 全新開局（宣告 `00h`，沒有前一段可比）| 2 |
| 主線沒走到 | 5 |
| 主線走出來、沒有任何段宣告的入口 | 6／24 |

主線沒走到的五段是 `0x15`／`0x23`／`0x25`／`0x35`／`0x45`——**不是缺陷**，
是主線那條路線沒經過，它們的接縫沒有事實可比。

### 沒有任何段宣告的六個入口

```
04h → 50h    11h → 51h    12h → 11h
22h → 51h    30h → 50h    33h → 32h
```

⚠ 這些**不是錯誤**：一段可以有好幾個入口，而 `EnterFrom` 只挑「最順著劇情的
那一個」。列出來是因為**直入永遠走不到這些入口**——如果某一段的行為會因為從
哪裡進來而不同（`LastECL` 正是 initial lifecycle 會讀的東西），那個差異在分段
驗收裡看不見。它們是「分段驗收看不到的角落」的清單。

## 分類的順序有意義

`fresh-start` 要排在 `not-visited` 前面。宣告 `00h` 的段是**全新開局**，本來就
不會有「前一段」；把它算成「主線沒走到」會讓開場那兩段看起來像沒驗到，而實際上
它們是這條路的起點。`TestClassifyPutsFreshStartBeforeNotVisited` 釘住這個順序。

## 第二層：整包 ECL 記憶體差多少（`cmd/segment-handoff`）

`LastECL` 對得上只證明**入口編號**宣告對了。真正的問題是那條 ⚠ 的後半：
直入的合成起始狀態，和主線真的走到時的狀態，差多少？

做法：拿主線**剛換到那一段時**的快照，對上「造隊伍 → `EnterSegment` → 存檔」的狀態，
逐格比 ECL 記憶體。差異裡再挑出**這一段自己的碼真的會讀**的那些——
讀取點由靜態可達指令的運算元推出來（`code 01h`／`03h` 查 `memory[Word]`，
`02h` 是立即值，見 `internal/ecl` 的 `operandValue`）。

| | |
|---|---:|
| 比得成的段 | 20（取樣：剛換到 19、站上地城 1）|
| 直入與主線差幾格 | 1,132 |
| **其中那一段的碼真的會讀** | **251** |
| 分佈在幾段 | **20**（全部）|

★ 意思是：**每一段的直入驗收都缺了那一段自己會讀的狀態。** 這不是說分段驗收
無效，是說它驗的是「那一段在乾淨狀態下的行為」，不是「主線走到那裡時的行為」。

## 修法：讓分段驗收從真實的交接狀態進場

`State.SeedHandoffMemory(memory)` 設定「下一次進段時要先鋪上的交接狀態」，
由 `StartStorySegment` 在**載入這一段之後、initial lifecycle 之前**鋪上。

⚠ **順序有兩個地方會錯**：

1. 鋪在 initial lifecycle **之後**沒有用——那條 lifecycle 會讀劇情旗標決定要演
   什麼，鋪在後面等於它已經用錯的旗標跑完了。
2. 鋪在 `4BF2h`（LastECL）、`7ED5h`、`7EC9h` 那三個 `SetMemoryValue` **之前**——
   那三格是進段這一支自己管的，引擎的值要蓋過交接來的舊值。反過來會把 LastECL
   設成上一段存下來的那個，而那正是這裡要決定的東西。

前端入口是 `-segment-handoff <到達取樣目錄>`。

### 效果（同一份報表的前後兩欄）

| | 直入 | 鋪上交接狀態 |
|---|---:|---:|
| 與主線差幾格 | 1,132 | **62** |
| 其中那一段的碼會讀 | 251 | **39** |
| 分佈在幾段 | 20 | 18 |

剩下的 39 格按成因分：

| 成因 | 格數 | 該不該補 |
|---|---:|---|
| 引擎進段時自己設的（`4BF2h`／`7ED5h`／`7EC9h`）| 10 | **不該**：進段這一支自己管 |
| 由隊伍位置推出來的視圖暫存器（`C04Bh`..`C05Fh`，如 `C04Fh` ＝ 牆頂）| 18 | **不該**：引擎自己算的 |
| 進段的 initial lifecycle 自己算掉的 | 6 | **不能**：鋪了也沒用 |
| 歸不了因 | **5** | 這才是真正剩下來的 |

⇒ **251 → 5**。

### 「鋪了也沒用」是怎麼認出來的

同一段跑兩趟（鋪與不鋪），如果**直入那一側算出來的值一模一樣**，代表 initial
lifecycle 把交接來的值覆蓋掉了——那格是**那一段自己決定的東西**，交接給不給都
一樣。⇒ 它不是交接缺口，混進「歸不了因」會讓剩下的數字看起來大一倍。

★ 這個判準不必知道那一格是什麼意思，只要**同一支工具跑兩趟**就分得出來。

### 那 5 格查出來了：一組是路線查表，一組是工作暫存器

逐格印出來之後（`residue_other`），拿位址去**專案自己的規格**查——不是去查 Borland
符號表：

| 位址 | 是什麼 | 出處 |
|---|---|---|
| `4C9Bh` | 世界路線的**目的地選擇槽**（remake 這一側是 `pendingWorldDestination`）| `internal/game/state.go`、spec 1097 |
| `4C9Dh` | 世界路線查表的**索引** | `ECL1/0x50:110Ch GETTABLE 9D13 4C9D 4CA1` |
| `4CA1h` | 查出來的**城市**（`CurrentCity`）| spec 1163 §表 |
| `7F79h` | ECL 的**通用工作暫存器**，全作最熱的一格（167 次）| spec 1096 §四、1097 |

⇒ **沒有一格是劇情旗標。**

- 前三格是「**這一次世界移動要去哪**」的當下運算值。直入**沒有「正要去哪」這件
  事**，所以它們必然不同——那不是交接漏掉了什麼。
- `7F79h` 是工作暫存器，值就是「上一次運算剩下的東西」。拿兩段**不同執行歷史**的
  工作暫存器互比沒有意義。

⇒ 分類補上這兩類之後，**歸不了因 ＝ 0**：39 格全部歸得了因。

| 成因 | 格數 | 該不該補 |
|---|---:|---|
| 引擎進段時自己設的 | 10 | 不該 |
| 由位置推出來的視圖暫存器 | 18 | 不該 |
| initial lifecycle 自己算掉的 | 4 | 不能 |
| 世界路線的查表三格 | 3 | 不該 |
| ECL 通用工作暫存器 | 4 | 不該 |
| **歸不了因** | **0** | — |

⚠ 測試的門檻仍然是「歸不了因要少於四分之一」，**不是釘死 0**：新的段或新的取樣點
冒出沒見過的格子是正常的，那時候該做的是**查清楚它是什麼**，不是把門檻放寬。

### 一開始差點命名錯

拿這幾個位址去查 Borland 符號表（資料段 3113）會落在 `SCANLIST`（`7F6Eh`..）與
`SPELLNAME`（`49F0h`..）裡——看起來很像答案。兩個理由都不成立：

1. **符號表是稀疏的。** 那張表只有 1,725 個符號，兩個符號之間的空隙是**沒有名字的
   區域**，不是前一個符號的延伸。spec 1096 說 `DS:4F99h` 是 bank0 指標，而 `4F99h`
   正落在「`SPELLNAME` 之後的空隙」裡——所以那個空隙顯然不屬於 `SPELLNAME`。
2. **兩個位址空間。** ECL 的工作位址透過 `DS:4F99h`..`DS:4FA5h` 那四個 bank 指標
   間接定址，指到的是**執行時配置的緩衝區**；dseg 位移是另一回事。

⇒ 正確的查法是查**專案自己的 ECL 規格**（1096／1097／1163），那裡本來就有這幾格。

### 原本記在這裡的 5 格是哪幾格

報表逐格印出來（`residue_other`）：

```
ECL1/0x51   4C9Bh  4C9Dh  4CA1h  7F79h
ECL5/0x30   7F79h
```

兩段都是**世界路線／過場**：`0x51` 是世界地圖上的路線段（沒有地城幾何），
`0x30` 是**進去就無條件轉走**的過場 block（`SettlesAt` 非 0）。直入的落點與主線
經過那裡時的狀態本來就最不一樣。

（身分見上一節。）

`TestSeedingHandoffClosesMostOfTheGap` 釘住三件事：至少關掉八成、四類加起來等於
全部（少一類代表分類漏了一種成因）、歸不了因的要少於四分之一（否則這份分類等於
沒解釋什麼）。

### 取樣點差很多

第一版用的是段內快照（`inside-block-XX.json`）——那是隊伍**第一次站上該段地城**
時存的，那時 initial lifecycle 已經跑完、隊伍也走了幾步，量到的是
「交接 ＋ 主線又走了一段」。

改成在**換段的那一瞬間**另存一份（`COAB_ARRIVAL_SNAPSHOT_DIR`，掛在同一個換段
瓶頸上）之後：

| `ECL1/0x50` | 站上地城 | 剛換到 |
|---|---:|---:|
| 直入與主線差幾格 | 89 | **37** |
| 會讀且漏掉 | 32 | **11** |

⇒ 取樣點不對會讓這個數字大三倍。順帶多涵蓋 4 段（19 份到達快照 vs 16 份段內
快照），因為有些段主線是進去又出來、沒有停下來觀測過。

⚠ 仍有 1 段用 `站上地城` 取樣：`ECL2/0x01` 是**全新開局**，主線不是靠換段進去
的，所以沒有到達快照。那一段的數字是上界。

### 到達取樣**不是存檔**

⚠⚠ 取樣點在換段的瓶頸上，那是**指令執行到一半**的地方：PC 指在指令中間、呼叫
堆疊還有東西（實測 19 份裡有 12 份 `stack` 非空）。第一版把它寫成完整的 party
file，然後拿去餵按鍵測試，結果是：

```
按 Enter：VERTICAL MENU header at 3771: operand 0 is truncated
```

⇒ 改成**只寫記憶體**（`ArrivalSample`，`schema: coab-arrival-sample/1`），
檔案裡還帶一句 `note` 說明它不是存檔。用完整的存檔格式會讓下一個人以為它載得
回來——**而它看起來完全像一份存檔**。

### 兩側要走同一個存取器

⚠ 到達取樣走 `MemorySnapshot()`（**整份**，含程式碼視窗與零），存檔那一側走存檔
編碼器（零不收、程式碼另存一塊）。定義域不同就直接比的話：

```
差異 1,148 → 103,896
```

**而那個數字看起來一樣像個結果**——沒有任何東西會報錯，只是每一段都「差了幾千格」。
⇒ 兩側都用 `MemorySnapshot()` ＋ 同一個 `normalise`（去掉程式碼視窗 `8000h..9DFFh`、
去掉值為 0 的格）。改成對稱之後數字和原本的存檔往返完全一致（1,132／251），
那是一次通過的一致性檢查。

### 量過而**不影響**的：隊伍人數

直入那側造一名（`cmd/azure-bonds-game -segment` 的做法）與造六名（主線的人數），
每一段的差異格數**完全相同**——隊伍資料不在 ECL 記憶體裡。原本以為這是個必然
的偏差來源，量了才知道不是。

### 一個已經發生過的假零

第一版忘了「直入要先有隊伍」，於是每一段的 `SavePartyFile` 都失敗，而失敗路徑把
「漏掉幾格」留在 0。報表印出來是**「16 段比得成、漏掉 0 格」**——和「完全對得上」
長得一模一樣。

★ 救回來的是**備註欄**：每一段都印了「直入存不出來：…」，一眼就看得出不對。
⇒ 規則：比較類的報表，**失敗要有自己的欄位，而且不能算進分母**
（`TestFailedSegmentsAreNotCountedAsComparedZeroes`）。

## 這個數字證明不了什麼

- **`LastECL` 那一層只比一個欄位**；旗標、攜帶物、pending transaction 還沒比。
- 「對得上」是指**編號**對得上，不是指直入之後跑出來的狀態和主線一樣。
- 主線的轉移是下界（見上）。
- 5 段沒有事實可比，所以分母的**有效**部分是 18，不是 25。
