# 1011 — 開發者留下的物品除錯畫面：15 個欄位的原始名稱

- 證據等級：`exact`（DOS 側 529 條逐條讀完；PC-98 對側 540 條，
  `retf` 之後的差異全在函式外的資料區，實際程式碼逐條相同）
- 作法見 spec 783

## `dos overlay-19:010ABh` ↔ `pc98 overlay-19:01074h`（`retf 4`）

兩側原本都是待解讀。`les di, [bp+06h]`（原始位元組 `c4 7e 06`）
⇒ **唯一的參數是物品節點的遠指標**。IDA 把它標成 `arg_2`，又一次對不上。

整支的結構是「15 行標籤 ＋ 15 行數值 ＋ 等按鍵」，
全部用常駐的 `0542:0352h` 印字（spec 983，`印字(欄, 列, 前景, 背景, 字串)`）：
標籤印在 **欄 1**、數值印在 **欄 20**、列從 1 排到 15，顏色一律 `0Ah` on `0`。

> **這是開發時期的物品結構傾印畫面，兩個平台都留著，而且 PC-98 版的標籤
> 也是英文——從來沒有被在地化過。**

## ★★★ 15 個欄位的原始名稱

標籤是開發者自己寫的 Turbo Pascal 欄位名，逐行對應被印出來的位移：

| 列 | 標籤 | DOS | PC-98 | 型別 | 既有判讀 |
|---|---|---|---|---|---|
| 1 | `itemptr` | `+2Eh` | `+56h` | byte | 物品種類編號（spec 683／832 拿它索引 `DS:5CF6h`） |
| 2 | `namenum(1)` | `+2Fh` | `+57h` | byte | **本規格新增** |
| 3 | `namenum(2)` | `+30h` | `+58h` | byte | **本規格新增** |
| 4 | `namenum(3)` | `+31h` | `+59h` | byte | **本規格新增** |
| 5 | **`plus`** | `+32h` | `+5Ah` | byte | ★ spec 1005 的效果碼 41 測 `= 0`，當時只能說「形狀上是非魔法武器」 |
| 6 | `plussave` | `+33h` | `+5Bh` | byte | **本規格新增** |
| 7 | `ready` | `+34h` | `+5Ch` | byte | spec 832 的「已裝備」✓ |
| 8 | `identified` | `+35h` | `+5Dh` | byte | **本規格新增** |
| 9 | **`cursed`** | `+36h` | `+5Eh` | byte | spec 1004 的「詛咒旗標」✓ |
| 10 | `value` | `+3Ah` | `+62h` | **word** | **本規格新增**（用 `overlay-24 entry#9` 印 word） |
| 11 | `special(1)` | `+3Ch` | `+64h` | byte | **本規格新增** |
| 12 | `special(2)` | `+3Dh` | `+65h` | byte | spec 703 的「第二個效果槽」✓ |
| 13 | `special(3)` | `+3Eh` | `+66h` | byte | **本規格新增** |
| 14 | `dice large` | `byte[5CF8h ＋ itemptr × 16]` | 同構 | byte | **本規格新增** |
| 15 | `sides large` | `byte[5CF9h ＋ itemptr × 16]` | 同構 | byte | **本規格新增** |

★ **`plus` ＝ 魔法加值**。spec 1005 讀效果碼 41 時看到
`w^[32h] = 0` 才觸發某個效果，只能說「形狀上是非魔法武器」；
現在有了名字，那一句可以直接寫成「`plus` ＝ 0，也就是沒有魔法加值的武器」。

## ★★ 物品類別表 `DS:5CF6h` 的 `+2`／`+3` 是「對大型目標」的傷害骰

最後兩行不是讀物品節點，而是拿 `itemptr` 去查類別表：

```pascal
印(列 14, byte[5CF8h ＋ itemptr × 16]);   { 5CF8h − 5CF6h = 2 }
印(列 15, byte[5CF9h ＋ itemptr × 16]);   { 5CF9h − 5CF6h = 3 }
```

★★★ **AD&D 1e 的武器有兩組傷害骰：對 S／M 一組、對 L 一組。**
標籤明寫 `dice large`／`sides large`，所以類別表的 `+2`／`+3`
就是**對大型目標的骰數與面數**——那麼同一張表裡一定另有一組對中小型的。

類別表的欄位圖因此補到六格：

| 位移 | 內容 | 出處 |
|---|---|---|
| `+0` | 裝備槽編號（`9` ＝ 雙持） | spec 1000／683 |
| `+1` | 佔幾隻手 | spec 1004 |
| **`+2`** | **對大型目標的骰數** | **本規格** |
| **`+3`** | **對大型目標的面數** | **本規格** |
| `+0Dh` | 可用性遮罩（與角色 `+12Bh` 做 `and`） | spec 1004 |
| `+0Eh` | 旗標位元 | spec 1004 |

## ★★ 物品節點在 PC-98 整體位移 `+28h`

十三個欄位一個不差地相差 **`28h`（40 bytes）**：

```
DOS   +2Eh +2Fh +30h +31h +32h +33h +34h +35h +36h  +3Ah +3Ch +3Dh +3Eh
PC-98 +56h +57h +58h +59h +5Ah +5Bh +5Ch +5Dh +5Eh  +62h +64h +65h +66h
```

★ spec 1005 讀效果碼 41 時看到 DOS 測 `w^[32h]`、PC-98 測 `w^[5Ah]`，
差 `28h`；當時只能記成「⚠ 兩平台欄位位移不同」。
**現在有 13 個欄位同時佐證，這是整個物品節點的常數位移，不是零星差異。**

⚠ 但**不要**把這個 `+28h` 推廣到角色節點——角色節點的位移是 `+1`
且只從 `+11Ch` 之後才開始（spec 1010）。**兩種節點的位移規則不同。**

## ★★ `namenum(1..3)`：物品名稱是三段組出來的

三個相鄰的 byte 叫 `namenum(1)`、`namenum(2)`、`namenum(3)`。
形狀上是「名稱由三個編號各查一段字串再串起來」——
Gold Box 的物品名確實長成 `<形容詞> <本體> <後綴>`
（例：`Long Sword +1`、`Ring of Protection`）。

**中文化的關鍵**：物品名不是一整條字串，改一張表改不完；
而且中文語序與英文不同（英文的 `+1` 在後、中文的「魔法」在前），
三段的**串接順序**要能重排。本規格不宣稱那三個編號各查哪一張表。

## 流程

```pascal
procedure 傾印物品(物品: 遠指標);        { retf 4 }
<far 01A0:0000h>();                       { 清畫面 }
指標 := 物品;
for 列 := 1 to 15 do 印字(1,  列, 0Ah, 0, 標籤[列]);
for 列 := 1 to 13 do 印字(14h, 列, 0Ah, 0, Str(欄位[列]));
印字(14h, 0Eh, 0Ah, 0, Str(byte[5CF8h ＋ itemptr × 16]));
印字(14h, 0Fh, 0Ah, 0, Str(byte[5CF9h ＋ itemptr × 16]));
<far 0542:0946h>(0, 0Ah, 'press a key');  { 等按鍵 }
```

byte 用 `overlay-24 entry#10`、word 用 `entry#9` 轉字串（各收 1 word）。

## 中文化

★ **這 16 個字串一個都不用翻**——它是開發者的除錯畫面，
正常玩家路徑到不了。要翻反而會讓對照原始碼變難。

⚠ 但 `namenum(1..3)` 這個發現本身**對中文化很關鍵**，見上一節。
