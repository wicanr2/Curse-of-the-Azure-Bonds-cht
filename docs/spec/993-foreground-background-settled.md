# 993 — 前景／背景定案：`15606h` 的兩個顏色參數標反了

- 證據等級：`exact`（`16147h` 的位元判斷逐條讀完；三層呼叫的推疊順序逐一對照）
- 作法見 spec 783

## 決定性證據在 `START.EXE:16147h`

spec 935 讀過這一支（CGA 320×200 的字元寫入）。關鍵三行：

```asm
mov bl, [bp+arg_4] ; mov dl, [bx+256Dh]     ; dl ← 顏色表[arg_4]
mov bl, [bp+arg_2] ; mov dh, [bx+256Dh]     ; dh ← 顏色表[arg_2]
...
test [bx+6598h], ah      ; 測字模的那一個位元
jz   short loc_1618F     ;   位元 = 0
or   al, dl              ;   位元 = 1 → 用 dl
jmp  short loc_16191
loc_1618F:
or   al, dh              ;   位元 = 0 → 用 dh
```

**字模位元 1（筆畫）取 `dl`、位元 0（底）取 `dh`** ⇒
`16147h` 的 **`arg_4` 是前景、`arg_2` 是背景**（spec 935 的標法正確）。

`16147h` 的四個參數由高到低是 `arg_8`（欄，`×2`）、`arg_6`（列，`×140h`）、
`arg_4`（前景）、`arg_2`（背景）。

## ⚠ `sub_15606h` 的 `arg_6`／`arg_8` 在 spec 937 標反了

`15606h` 呼叫 `16147h` 時推的是

```asm
push arg_C   ; → 16147 的 arg_8（欄）
push arg_A   ; → 16147 的 arg_6（列）
push arg_8   ; → 16147 的 arg_4（前景）
push arg_6   ; → 16147 的 arg_2（背景）
push var_2   ; 字模索引，16147 沒有用到（字模已經在 DS:6598h）
call sub_16147
```

所以 **`15606h` 的 `arg_8` 是前景、`arg_6` 是背景**。
spec 937 把它們寫成「前景 `arg_6`、背景 `arg_8`」——**兩個標反了**，已更正。

## 往上傳播：三層都對得起來

### `0542h:0352h`（＝ `15772h`，字串輸出）

它推給 `15606h` 的是 `(欄, 列, 自己的 arg_6, 自己的 arg_4, 1, 字元, 1)`，
落點是 `arg_C, arg_A, arg_8, arg_6, arg_4, arg_2, arg_0`。所以

> **`印字(欄, 列, 前景, 背景, 字串)`**——第三個是前景、第四個是背景。

spec 693 的 `(x, y, colour, mode, str)` 裡的 `colour` **就是前景**（正確），
第四個不是「mode」而是**背景**。

代回各呼叫端，全部說得通：

| 呼叫端 | 前景 | 背景 | 效果 |
|---|---|---|---|
| `overlay-24:0177Ah`（訊息列） | `0Ah` | `0` | 亮綠字、黑底 ✔ |
| `overlay-24:018F3h`（角色名） | 陣營色 | `0` | 彩色名字、黑底 ✔ |
| `overlay-26:00AF8h` | 視窗`+24h`／`+22h` | `0` | **一般** |
| `overlay-26:00A56h` | `0` | 視窗`+20h` | **反白** |

★ 這同時解掉 spec 983 留的那個問號（「照 spec 937 的標法，訊息列會變成
黑字亮綠底，與實機不符」）——**確實是標法錯了**。
而 `00A56h` 與 `00AF8h` 的關係也定下來：**`00A56h` 是反白版、`00AF8h` 是一般版**
（spec 983 當時兩種可能都列，沒有斷言）。

## `dos overlay-26:001E5h`（180 條）— 逐字元三色繪製

`(視窗的 SS 偏移 arg_0, 項次 arg_2)`。這一支把上面的結論用得最完整。

```pascal
n := ss:[視窗 − 64h];                                  { 這一行有幾個字 }
if n = 0 then 離開;

for j := 1 to n do begin                                { 無號 }
    c := ss:[視窗 − 53h ＋ j];
    欄 := ss:[視窗 − 65h] ＋ j − 1;

    if (ss:[視窗 − 8Fh ＋ 2×項次] <= j)                  { 落在目前項的範圍內 }
       and (ss:[視窗 − 8Eh ＋ 2×項次] >= j)
       and (ss:[視窗 ＋ 0Eh] <> 0) then
        畫字元(欄, 18h, 0, ss:[視窗 ＋ 0Eh], 1, c, 1)    { 前景 0、背景 +0Eh ⇒ 反白 }
    else if c in ['0'..'9', 'A'..'Z'] then               { 集合在 CS:01C5h }
        畫字元(欄, 18h, ss:[視窗 ＋ 0Eh], 0, 1, c, 1)    { 熱鍵字元用 +0Eh }
    else
        畫字元(欄, 18h, ss:[視窗 ＋ 10h], 0, 1, c, 1);   { 一般字元用 +10h }
end;
```

（`0542h:01E6h` ＝ `START.EXE:15606h`，就是上面那支畫字元的分派層。）

### 三種顏色，一次看懂 Gold Box 的選單長相

| 情況 | 前景 | 背景 |
|---|---|---|
| **目前選中的那一項** | `0` | 視窗 `+0Eh` ⇒ **整段反白** |
| **熱鍵字元**（大寫英數字） | 視窗 `+0Eh` | `0` |
| 其他字元 | 視窗 `+10h` | `0` |

**熱鍵用的顏色與反白用的底色是同一格 `+0Eh`**——所以選中之後熱鍵字母
會與底色同色而「消失」，正是原版選單的樣子。

### 兩個既有結論在這裡收口

- 大寫英數字的集合（`CS:01C5h`）與 spec 978 的 `overlay-07:016D3h`、
  spec 977 的 `overlay-26:000D5h` **是同一個 36 成員集合**。
  **「大寫 ＝ 熱鍵」這件事在繪製層也成立**，不只在解析層。
- 每項的欄位範圍 `ss:[視窗 − 8Fh ＋ 2i]`／`[− 8Eh ＋ 2i]` **正是
  `overlay-26:000D5h` 建的那張表**（spec 977）。建表、查表、用表三支到齊。

### ⚠ 中文化

這一支**逐 byte 畫字元**，而且靠「這個 byte 是不是大寫英數字」決定顏色。
Big5 的低位元組範圍是 `40h..7Eh` 與 `A1h..FEh`，
**`41h..5Ah`（`'A'..'Z'`）整段落在裡面**——
所以**漢字的第二個 byte 會被誤判成熱鍵而變色**（`30h..39h` 在 `40h` 以下，
不受影響）。中文化必須改成以字元為單位判斷，
與 spec 978／985 的 DBCS 缺口同一批。

## 明確不宣稱

  （只知道本支怎麼用它們）。
- 沒有宣稱 `byte_211A6h` 的另外兩種顯示模式（`161E6h`／`16246h`）
  是不是同樣的前景／背景順序。
- 沒有宣稱 `DS:256Dh` 顏色轉換表的內容（同 spec 932／935）。
