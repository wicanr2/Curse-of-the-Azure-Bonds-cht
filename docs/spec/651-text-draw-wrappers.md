# 第六百五十一輪：文字輸出的三層包裝，與一個只有一個 byte 的來源緩衝

狀態：`READY`。日期：2026-08-14
位置：PC-98 `PC98-GAME.EXE` 的 `17250h`、`172A0h`、`172D5h`。

## `17CE9h` 的參數對應

`17CE9h`（[spec 647](647-pc98-palette-and-attribute.md)）有 7 個 word 參數。由兩個
呼叫端的推入順序對出來（Turbo Pascal 由左而右推，**最後推入的是第一個參數**）：

| 參數 | 用途 |
|---|---|
| `arg_0` | 來源 offset |
| `arg_2` | 來源 segment |
| `arg_4` | 格數（`CX`） |
| `arg_6`、`arg_8` | 傳給下游的屬性參數 |
| `arg_A` | 列 |
| `arg_C` | **格**欄（不是字欄） |

兩個呼叫端都把「字欄」`shl 1` 之後才當 `arg_C` 傳——**全形字佔兩格**，所以字欄要
乘 2 才是格欄。而 `17CE9h` 內部再算 `(列 × 50h + 格欄) × 2` 得到 byte 位移。

## `17250h`：Pascal 字串拆成「長度 ＋ 內容」

```text
<sub_1AC99>(arg_0, @var_100, 0FFh)     ← 複製 Pascal 短字串進區域
count := [var_100]                      ← 第一個 byte 是長度
<17CE9h>(@var_FF, SS, count, 0, arg_4, arg_6, arg_8 × 2)
```

**傳給繪製的是 `var_FF`（內容起點）而不是 `var_100`（長度所在）**，長度另外當
格數傳。這是 Pascal 短字串在組語介面的標準拆法。

## `172A0h`：來源緩衝只有一個 byte

```text
[var_1] := 0DBh
<17CE9h>(@var_1, SS, arg_0, 0, arg_2, arg_4, arg_6 × 2)
```

`0DBh` 是 PC-98 半形字元的實心方塊。但**格數 `arg_0` 由呼叫端給，緩衝卻只有一個
byte**——`172D5h` 呼叫時傳的是 `50h`（80 格，整整一列）。

繪製迴圈（`sub_17D22`，與 [spec 648](648-pc98-text-draw-core.md) 的 `16966h` 同一種
寫法）是 `lodsb` **逐 byte 往前讀**，停止條件是「讀到 0」或「格數用完」。緩衝之後
接的是堆疊上的 saved BP、返回位址與參數。

所以第一格畫的一定是 `0DBh`，**之後畫什麼取決於當下的堆疊內容**。

⚠ 這條需要 runtime 驗證再下最終結論。靜態證據只到「來源是單一 byte、格數來自呼叫
端、迴圈逐 byte 前進」為止；有沒有實際畫出雜訊，要看 saved BP 的低位元組是不是
剛好為 0。與 [spec 626](626-goduel-and-charrec-size.md) 的 `GODUEL` 物品迴圈同一類
標記。

## `172D5h`：畫訊息並等待

```text
<sub_1AC99>(arg_0, @var_51, 50h)       ← 複製字串（上限 80）
<172A0h>(50h, 0, 18h, 0)                ← 第 24 列鋪滿方塊
<17250h>(@var_51, arg_4, 18h, 0)        ← 在同一列畫字串
<sub_18036>()                            ← 回傳值存進區域變數後沒再讀
<172A0h>(50h, 0, 18h, 0)                ← 再鋪一次
```

第 `18h`（24）列是訊息列。前後各鋪一次方塊——前面是清底、後面是擦掉，中間夾著
`sub_18036`（多半是等待輸入）。

## 明確不宣稱

- `sub_1AC99`（字串複製）與 `sub_18036` 的行為。
- `17CE9h` 的 `arg_6`／`arg_8` 傳給下游後怎麼用。
- `172A0h` 實際畫出來的樣子（見上面的 runtime 標記）。
