# 992 — DOS 的 `FINDSTR` 是 6-bit 壓縮；PC-98 為了日文改成逐 byte

- 證據等級：`exact`（逐條讀完；位元運算逐步驗證）
- 作法見 spec 783

## `dos overlay-07:012AEh`（167 條）

spec 616 讀的是 **PC-98** 的 `FINDSTR`（`overlay-07:01364h`，**57 條**），
結論是「字面字串直接嵌在 ECL bytecode 裡，逐 byte 讀」。
DOS 這一支是它的對應——**但長了三倍，而且做的事不一樣**。
（`aligned_diff` 給的相似度只有 0.455，本來就不該當成同構函式看。）

```pascal
DS:[7648h ＋ slot × 100h] := '';
i := 0;  狀態 := 1;

while i < n do begin                                  { 無號 }
    if 狀態 < 4 then begin
        inc(word[DS:4FB4h]);                          { ECL_PC ＋1 }
        前 := 目前;
        目前 := byte[遠指標(DS:4FA5h) ＋ DS:4FB4h − 8000h];
        inc(i);
    end;

    case 狀態 of                                       { 全部是 byte 運算 }
      1: v := 目前 shr 2;
      2: v := byte((前 shl 6) ＋ (目前 shr 2)) shr 2;
      3: v := byte((前 shl 4) ＋ (目前 shr 4)) shr 2;
      4: v := 目前 and 3Fh;
    end;
    if 狀態 < 4 then inc(狀態) else 狀態 := 1;

    if v <> 0 then
        字串 := (字串 ＋ Chr(<本模組 070Dh>(v))) 上限 0FFh;
end;

if 狀態 = 4 then begin                                 { 收尾的第四個 }
    v := 目前 and 3Fh;
    if v <> 0 then 字串 := (字串 ＋ Chr(<本模組 070Dh>(v))) 上限 0FFh;
end;
```

## ★ 每 3 個 byte 解出 4 個 6-bit 值

把三個位元組 `b0 b1 b2` 代進四個狀態，逐位元驗算：

| 狀態 | 程式 | 展開 | 標準 6-bit 拆法 |
|---|---|---|---|
| 1 | `b0 shr 2` | `b0[7:2]` | `v1` ✔ |
| 2 | `byte(b0 shl 6 ＋ b1 shr 2) shr 2` | `((b0 and 3) shl 4) ＋ (b1 shr 4)` | `v2` ✔ |
| 3 | `byte(b1 shl 4 ＋ b2 shr 4) shr 2` | `((b1 and 0Fh) shl 2) ＋ (b2 shr 6)` | `v3` ✔ |
| 4 | `b2 and 3Fh` | `b2[5:0]` | `v4` ✔ |

兩處 `byte(…)` 的截斷是**必要的**：`b0 shl 6` 只留下 `b0 and 3`、
`b1 shl 4` 只留下 `b1 and 0Fh`，而兩次加法都不會溢位
（`(b0 and 3) shl 6 ≤ 192` 加 `b1 shr 2 ≤ 63` ＝ 255）。
**這不是巧合，是設計**——用 8-bit 加法省掉遮罩指令。

⚠ **狀態 4 不推進 `ECL_PC`**，所以三個位元組出四個字元。
而 `n`（`arg_2`）數的是**位元組數，不是字元數**——
迴圈條件是 `i < n` 而 `i` 只在狀態 1..3 遞增。

## ★ `070Dh` 的 6-bit → ASCII 對應就是字型的 64 個字模

```pascal
if v <= 1Fh then 結果 := v ＋ 40h else 結果 := v;
```

| 6-bit 值 | ASCII |
|---|---|
| `00h`..`1Fh` | `40h`..`5Fh`（`'@'`..`'_'`，含 `'A'`..`'Z'`） |
| `20h`..`3Fh` | `20h`..`3Fh`（`' '`..`'?'`，含數字與標點） |

值域正好是 **ASCII `20h`..`5Fh` 這 64 格**——
與 spec 937 的字型索引式 `UpCase(c) mod 40h` **完全同一組字元**。
壓縮字母表與字型字模表是同一件事的兩面：
**這個引擎的文字世界就是這 64 個字**。

`v = 0` 對應 ASCII `40h`（`'@'`），但程式**明確跳過 0**——
所以 `'@'` 不能出現在壓縮文字裡，`0` 被當成填充／終止用。

## ★★ 兩平台的字串來源機制不同

| | DOS `012AEh` | PC-98 `01364h`（spec 616） |
|---|---|---|
| 條數 | 167 | 57 |
| 編碼 | **6-bit 壓縮，每 3 bytes 4 字** | **逐 byte 原樣** |
| 字元集 | ASCII `20h`..`5Fh`（64 個） | 任意 byte |
| `n` 的單位 | **位元組** | **字元** |
| 目的槽 | `DS:7648h ＋ slot×100h` | `DS:0A8DAh ＋ slot×100h` |

原因很直接：**Shift-JIS 需要完整的 8 個位元**，6-bit 壓縮裝不下日文。
PC-98 移植時把整個壓縮層拿掉，改成原樣複製。

### 中文化的結論

**Big5 同樣需要 8 個位元，所以中文化必須走 PC-98 那條路。**
DOS 的 6-bit 格式在結構上**不可能**裝中文——它的字元集被硬編碼成
ASCII `20h`..`5Fh` 這 64 格，`070Dh` 沒有查表可以攔截。

具體影響：

1. **ECL bytecode 裡的字面字串要重新產生**，不能只翻譯——
   壓縮格式與長度欄位（`n` 是位元組數）都得改成逐 byte。
2. **`n` 的語意跟著變**：DOS 的 `n` ＝ 位元組數（字元數約 `4n/3`），
   PC-98 的 `n` ＝ 字元數。改編碼時呼叫端的運算元也要一起改。
3. 若要保留 DOS 執行檔相容，就得像 PC-98 一樣**把 `012AEh` 整支換掉**，
   而不是改字元表。

## 明確不宣稱

- 沒有宣稱 `DS:4FB4h`（DOS 的 `ECL_PC`）與 PC-98 對應全域的位址關係。
- 沒有宣稱壓縮字串的產生工具或原始碼側格式。
- 沒有宣稱 `0` 這個值除了「跳過」以外還有沒有別的語意。
