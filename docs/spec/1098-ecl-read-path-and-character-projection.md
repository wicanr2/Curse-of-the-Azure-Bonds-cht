# 1098 — ECL 變數的讀取端與寫入端對稱性，以及寫入側的角色欄位投影表

- 狀態：`READY`
- 證據等級：`exact`（DOS `overlay-07:00173h` 求值器 39 條、`overlay-07:00F3Ah` 讀取端、
  `overlay-07:007F1h` 讀投影 293 條、`overlay-07:00B6Dh` 寫投影 163 條逐條讀完）
- 映射基礎見 spec 1096；共用格子清冊見 spec 1097
- 回答 TODO `RE-15`

> **與既有規格的關係**：**讀取側**的角色欄位投影表 spec 624／1040 已經記錄過
> （spec 1040 更完整，含 `7CA5h`..`7CACh` 的公式、PC-98 對照，以及 `7CE4h`
> 是 `and 1` 取最低位元的更正）。本規格**不重列那張表**，新增的是三件事：
> ① 讀取端與寫入端的對稱性（`RE-15`）；② **寫入側也有一張投影表**
> （`overlay-07:00B6Dh`），且與讀取側**不同**——因此有唯讀投影；
> ③ ECL 資料實際用到哪幾個投影位址。

## 一、operand 求值鏈

```pascal
function 取operand值(索引: byte): word;      { overlay-07:00173h，retf 2 }
begin
    碼 := byte[DS:7685h + 索引];             { operand 碼 }
    高 := byte[DS:76C5h + 索引];
    低 := byte[DS:7705h + 索引];
    case 碼 of
      0:         結果 := 低;                          { 立即值（byte） }
      1, 3, 80h: 結果 := <讀ECL變數>(高×100h ＋ 低);  { ★ 解位址 }
      2, 81h:    結果 := 高×100h ＋ 低;               { 立即值（word），不解位址 }
    end;
end;
```

★ 三張平行表各 64 bytes（`7685h`／`76C5h`／`7705h`），索引就是 operand 序號。
★ operand 碼 `0`／`2`／`81h` 是立即值，`1`／`3`/`80h` 才會解位址
——這對應 `ecl-event-catalog` 裡 `code: "0x00"`（立即）與 `"0x01"`（位址）的分類。

## ★★★ 二、讀取端與寫入端完全對稱

`overlay-07:00F3Ah`（讀）與 `overlay-07:00D70h`（寫，spec 1096）：

| | 讀取端 `0F3Ah` | 寫入端 `0D70h` | 對稱？ |
|---|---|---|---|
| 分區 | `<sub_735>` | `<sub_735>` | ✓ **同一支** |
| 區 0 | `bank0 + (位址−4B00h)×2`，word | 同 | ✓ |
| 區 1 | `bank1 + (位址−7C00h)×2`，word | 同 | ✓ |
| 區 2 | `DS:4FA1h + (位址−7A00h)×2`，word | 同 | ✓ |
| 區 3 | `DS:4FA5h + 位址 − 8000h`，**`mov al` ＋ `xor ah,ah`** | `mov dl`，byte | ✓ 都是 byte |
| 區 4 邊界 | `0C04Bh` | `0BF68h` | ⚠ **不同** |
| 額外攔截 | 區 1 先走 `<sub_7F1>` | 區 1 寫完再走 `<sub_B6D>` | ⚠ 見 §三 |

> ★★★ **`RE-15` 的答案：分區表、`×2`、區 3 的 byte 寬度三項完全對稱。**
> ⇒ spec 1096 §四第 3 點成立——remake 的 `map[uint16]uint16` 對區 3
> 讀取會回傳完整 word，原作只回傳一個 byte（`0`..`255`）。
>
> ⚠ 區 4 的邊界兩端不同（讀 `0C04Bh`／寫 `0BF68h`），本規格不宣稱原因。

## ★★★ 三、區 1 的低段不是 bank1 記憶體，是「目前角色」欄位投影

區 1 的存取在真正碰 bank1 之前（讀）或之後（寫）會經過一張攔截表，
把特定 ECL 位址轉向 **`DS:6506h` 指向的目前角色記錄**
（`DS:6506h` ＝ 目前角色，spec 1040／1076／1085）。

### 讀取投影（`overlay-07:007F1h`）

```pascal
function 讀區1投影(idx: word; var 命中: byte): word;
begin
    命中 := 1;  idx := idx − 7C00h;
    case idx of … end;                   { 對照表見 spec 1040 }
end;
```

讀取端拿到 `命中 <> 0` 就用投影值，**不讀 bank1**。
**對照表見 spec 1040**（本規格逐條重讀一次，與該表一致，不重列）。

★ 本規格另外確認的兩點：
- **偏移不是固定加法**（`15h→13h` 差 −2、`18h→19h` 差 ＋1、`B8h→F7h` 差 ＋3Fh）
  ⇒ 只能查表，不能用算式推。
- 表中有一列的來源不是角色而是 bank1 本體：`7F3Eh → bank1 + 67Ch`，
  而 spec 1096 的算式給出 `(7F3Eh − 7C00h) × 2 = 67Ch`——**完全一致**。
  ⇒ 分區映射在一個與推導來源無關的地方再次被驗證。

### ★★★ 讀寫不對稱：12 個位址是唯讀投影

寫入端 `overlay-07:00B6Dh` 也有一張表，但**比讀取端短**。
兩端交叉驗證後確定 **9 個位址讀寫都投影到同一個角色欄位**
（`7CB8h`／`7CBBh`／`7CBDh`／`7CBFh`／`7CC1h`／`7CC3h`／`7CF7h`／`7CF9h`／`7D00h`）。

> ★★★ **其餘位址是唯讀投影：ECL 寫進去會落在 bank1，讀出來卻是角色欄位。**
> ⇒ 對這些位址而言，**寫了讀不到**——這是原作行為，不是缺陷。
> ⚠ 本規格只宣稱上表標 ✓ 的欄位；寫入端表的完整內容以自動比對抽出時
> 在多層 case 上會誤配，未逐條人工確認的部分不列入。

★ 另有 `7C80h`／`7C81h` 一對（寫入端獨有）分別把 `角色^[197h]` 設 0／1，
形狀是一組開關。⚠ 未逐條確認，不列入正式表。

## ★★★ 四、對 remake 的意義

1. **投影位址不能存在 map 裡。** `memory[0x7CB8]` 不是一格記憶體，是
   **目前角色的 `+0F7h`**；換一個「目前角色」，同一個 ECL 位址就該讀到不同的值。
   把它當普通格子存起來，換角色後會讀到陳舊值。

2. **remake 現行做法方向正確。** `internal/ecl/runtime.go:1108`..`1119` 在切換
   目前角色時，把角色欄位**手動寫進** `stringsMemory[0x7C00]`（名字）與
   `memory[0x7CB8]`——這正是手工模擬投影。
   ★ 且 `ControlMorale` 就是 `+0F7h`：`internal/party/dos_spell_record.go:332` 的
   `NPC: r.ControlMorale >= 0x80` 與 spec 1066 的「`< 80h` ＝ NPC」一致，
   `internal/game/combat_state.go:3255`／`3331` 也用同一條界線判可否操控。
   ⇒ **這一格語意正確。**

3. **實際缺口只有一格。** 對 1,355 條靜態可達指令做交叉檢查後，
   spec 1040 那張表的投影位址中 **ECL 只用到 3 個**：

   | ECL 位址 | 角色欄位 | 次數 | remake |
   |---|---|---|---|
   | `7CB8h` | `+0F7h` NPC 旗標 | 1（`COMPARE`） | ✓ 已模擬 |
   | `7D00h` | `+196h` | 1（`COMPARE`） | ✓ 有寫入 |
   | **`7CE4h`** | **`+192h`** | 1（`COMPARE`） | ⚠ **缺** |

   ⇒ 補一格即可，不是補 20 格。
   ★ `7CE4h` 早在 spec 1040 就記錄過：`7CE4h` ＝ `+192h and 1`（PC-98 是 `+193h`）。
   ⚠ 這是**靜態可達**的範圍；catalog 尚缺動態 branch（P0-RE-2），
   動態路徑是否用到更多投影位址未涵蓋。

## ★★ 五、角色 `+192h` 的產生端：唯一寫入者是舊格式轉換

`7CE4h` 投影到的 `角色^[192h]`，在兩平台各只有一個寫入者與一個讀取者：

| 平台 | 欄位 | 寫入者 | 讀取者 |
|---|---|---|---|
| DOS | `+192h` | `overlay-16:01F21h` @`219Ah` | `overlay-07:007F1h` @`0994h`（投影） |
| PC-98 | `+193h` | `overlay-16:026CFh` @`295Ah` | `overlay-07:008BDh` @`0A60h`（投影） |

★ 兩平台差 1，與 spec 1040「`+192h` 與 `+1A5h` 在 PC-98 各 ＋1」一致。

寫入處的形狀（`[bp+var_7]` ＝ 目的角色記錄，`ss:[arg_0−1C4h]` ＝ 來源結構）：

```pascal
目的^[10Bh] := ord(來源^[0B9h] > 0);
目的^[10Fh] := ord(來源^[0BAh] > 0);
目的^[0E5h] := 1;
if 來源^[26h] <> 0 then 目的^[192h] := 1;      { ★ 只設 1，沒有設 0 的路徑 }
bank1^[550h] := 0FFh;
```

> ★★ **`角色^[192h]` 是 byte 布林旗標**：由「舊格式來源結構 → 現行角色記錄」的
> 轉換函式在 `來源^[26h] <> 0` 時設 1，**全程沒有任何設 0 的路徑** ⇒ 預設值 0。
> 讀取端只有 ECL 的 `7CE4h` 投影，而且取 `and 1`（spec 1040）
> ⇒ **只有最低位元有意義**。
>
> ⚠ 本規格不宣稱 `overlay-16:01F21h` 整支的用途、來源結構 `ss:[arg_0−1C4h]`
> 的身分，以及 `來源^[26h]` 的語意。已知的是它同時寫 `+10Bh`／`+10Fh`／`+0E5h`
> 並把 `bank1^[550h]` 設成 `0FFh`（spec 1087 的 `PROGRAM 8` 也寫同一格）。

⚠ **不要與 `bank0^[192h]` 混淆**：`overlay-24:2BAAh` 與 `overlay-30:018Ch`
存取的 `es:[di+192h]` 來源是 `DS:4F99h`（bank0），對應 ECL 位址 `4BC9h`
（spec 1097 的共用格子），與角色記錄無關。

## ★★★ 六、三個實例都是同一個慣用法

```
SAVE            <索引> → 7F79h
LOAD CHARACTER  7F79h            { 把第 N 個角色設成「目前角色」}
COMPARE         <投影位址>, <值>  { 讀該角色的欄位 }
IF …
GOTO            …
```

| 出處 | 序列 | 意義 |
|---|---|---|
| `ECL5` block `0x30` `0x009B` | `LOAD CHARACTER 0` → `COMPARE 7CB8h, 80h` → `IF <` | **`+0F7h < 80h` ＝ 是 NPC**，與 spec 1066 的判準一字不差 |
| `ECL1` block `0x50` `0x19EB` | `LOAD CHARACTER 0` → `COMPARE 7CE4h, 0` → `IF <>` | `+192h`（spec 1040 的 `and 1`） |
| `ECL2` block `0x02` `0x0471` | `LOAD CHARACTER 10` → `COMPARE 7D00h, 0` → `IF =` → **`GOTO 0x84BC`** | ★★★ **這是 spec 1095 那個 `COMBAT` 候選的進入條件** |

> ★★★ **投影機制的用途在此閉合**：`LOAD CHARACTER` 設定目前角色，
> 緊接著用投影位址讀該角色的欄位做分支。三個實例、三份既有規格
> （1040／1066／1095）各自獨立地與投影表對上。
>
> ★ 順帶補上 spec 1095 缺的一塊：`ECL2` block `0x02` 的 `COMBAT`（`0x04BC`）
> 不是無條件執行的——**先載入第 10 個角色、檢查 `+196h = 0` 才跳過去**。

- 沒有宣稱哪些欄位在語意上需要有號延伸。
