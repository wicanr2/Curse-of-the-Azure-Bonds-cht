# 1197 — 按鍵玩到哪：力量 16 撞不開的門，與查表式的路線重放

- 證據等級：撞門表 `exact`（DOS 與 PC-98 兩份原始位元組逐條讀完）；
  重放改良為**實測**（同一份路線、同樣 1500 幀，四種走法各量一次）
- 產物：`internal/dungeon/bash.go`、`internal/dungeon/bash_test.go`、
  `cmd/azure-bonds-game/keydriven_test.go`、[spec 1026](1026-open-doors-table.md)

## 要回答的問題

README 一直帶著一句但書：主線**已經從開場走到結局**，但那是規則層走完的，
不等於拿鍵盤從頭玩到結局。這一輪把「拿鍵盤玩會停在哪」變成可以量的數字，
然後把量出來的第一個硬牆拆掉。

## ★★★ 第一個硬牆：力量 16 的角色永遠撞不開門

按鍵重放跑 1500 幀，隊伍停在 ECL 段 `0x02` 的 `(10,13)`，**762 幀零進度**。
逐格紀錄指出成因：那一格的南邊是一扇上鎖的門（`flags=2`），隊伍撞了 23 次，
**23 次全部失敗**。

遊戲內建的六個預設角色都是力量 16 的戰士。一次撞門是六個人各擲一次，
只要有一個人成功就開；照表算，力量 16 的成功率若是 3/6，一次撞門開門的機率
約 98%。**連續 23 次失敗的機率是 (1/64)²³ ≈ 3×10⁻⁴²**——這不是運氣，是表壞了。

成因在 `internal/dungeon/bash.go` 照抄公開 reference（`engine/ovr015.cs`）：

```csharp
else if (str >= 8 && str <= 15)  { ... }   // 先吃掉 15
else if (str == 15 || str == 17) { ... }   // 15 到不了這裡，16 不在這裡
```

⇒ **力量 16 一列都不符合，`worked` 永遠是 false**。

拿原始位元組核對（`dos overlay-14:0473h`）：

```
473:  3d 10 00        cmp    ax,0x10      ; 16
476:  7c 1b           jl     0x493
478:  3d 11 00        cmp    ax,0x11      ; 17
47b:  7f 16           jg     0x493
47d:  b0 01 50 b0 06 50   push 1 / push 6
483:  9a 4d 00 41 01  call   roll_dice
488:  3c 03           cmp    al,3
48a:  77 04           ja     0x490
48c:  c6 46 fa 01     mov    byte [bp-6],1   ; bash_worked := true
```

**是 16–17，而且門檻是 d6 ≤ 3。** PC-98 側同一列在 `overlay-14:0450h`：`cmp al,10h` ／ `jb` ／ `cmp al,11h` ／
`ja` ／ `cmp al,3` ／ `ja`，門檻與骰子完全相同（PC-98 用無號比較、DOS 用有號，
力量的值域內兩者等價）。兩份互相獨立的原始碼
都寫 16，reference 的 C# 是轉錄錯的。

同一段還抓到第二處：18／百分位 ≤ 50 在 reference 裡寫成「直接成功、事後補擲
一顆 d6」，原始位元組是 `cmp al,3` ＋ `ja`——**照擲，擲出 4 以上就是失敗**。

完整的表已經寫回 [spec 1026](1026-open-doors-table.md)（原本那一份把整欄
往上錯開了一列）。回歸測試 `TestBashDoorStrength16IsNotADeadRow`、
`TestBashDoorStrength15UsesTheEightToFifteenRow`、
`TestBashDoorStrength18NormalBranchRollsD6` 分別釘住三個邊界。

> ★ 這條收在 `AGENTS.md` §3：**reference 的反編輸出不是證據**。這一次的代價很
> 具體——一個轉錄錯的常數讓預設隊伍在第一扇上鎖的門前面永遠過不去，而所有測試
> 都是綠的，因為沒有人量過「按鍵玩得到哪裡」。

## ★★ 第二件事：路線重放從「往前找一段」改成「站在哪就查哪一格」

主線的決策用 `COAB_DECISION_LOG` 錄成 23,158 步（spec 1191）。原本的重放是
**滑動視窗**：從目前的進度往前找 `routeLookahead = 20` 個決策，比對得上就照它按。

視窗的問題不在大小，在**它假設重放和主線走的順序一樣**。按鍵這一場會多繞一些
路、少走一些捷徑，順序一旦錯開，視窗再大也只是把還沒用到的步驟提早吃掉。

改成兩張查表：

```
(ECL 段, x, y)  → 路線裡從這一格走出去的所有步驟，照錄下來的順序
選項簽章（以「｜」相接）→ 路線裡面對同一組選項的所有步驟
```

站在哪就查哪一格，跟中間繞了多遠無關。同一格被走過很多次時**輪流**取候選——
不能每次都取第一個（隊伍會在原地一直按同一個方向），也不能用過就永久劃掉
（主線在同一格來回經過很多次，用完之後隊伍就再也拿不到路線）。

### 實測（同一份路線、1500 幀）

| 走法 | 走過的格 | 記到的話 | 照路線按 | 走到的 ECL 段 |
|---|---:|---:|---:|---|
| 視窗（`routeLookahead = 20`）| 71 | 82 | 332 | `0x01` |
| 查表・用完就停 | 112 | 73 | 590 | `0x01` `0x02` |
| 查表・輪流 | 107 | 67 | 1,371 | `0x01` `0x02` |
| 查表・輪流 ＋ 撞門表修好 | **132** | **77** | 1,372 | `0x01` `0x02` |

⚠ **兩件事要分開看**：換成查表就讓隊伍第一次離開開場那一段（`0x01` → `0x02`），
這與撞門無關；撞門修好之後才從 107 走到 132 格，而且「路線帶不動」的次數
從 23 掉到 4。

幀數上限重量過：4,000 與 10,000 幀的結果與 1,500 幀**完全相同**（132 格、
最後一次踏上新格子在第 1,273 幀），所以預設維持 1,500。

## ★ 還沒過去的牆：段與段之間的交接

隊伍現在停在 ECL 段 `0x02`，走過 132 格。**路線本身幫不上忙**——
錄路線的戰役測試是用 `state.EnterSegment(seg)` **直接切段**的
（見 `cmd/dungeon-walk-probe`），所以那份紀錄是**每一段內部的移動 oracle，
不是一條從頭到尾的路**。段界怎麼過去，紀錄裡沒有。

`0x01` → `0x02` 是**走出去的**（第 248 幀），所以段界在遊戲裡確實過得去；
`0x02` → `0x03` 的觸發點還沒找到。逐格紀錄顯示隊伍走到 `(10,15)` 會彈回
荒野而不是換段。

**下一步**：從 ECL `0x02` 的可達指令裡把換段的觸發點列出來，比對隊伍走過的
132 格，看是「還沒走到」還是「走到了但條件不成立」。

## 這一輪加的量測

`cmd/azure-bonds-game/keydriven_test.go`：

- `COAB_KEY_FRAMES` — 幀數上限，用來量「到頂了沒」而不是猜。
- `COAB_KEY_TRACE` — 逐格紀錄：每一步的起點、路線給的方向、落點、
  沒動的時候四面通不通與門選單的 flags。
- 測試結尾多印三行：停在哪、最後一次踏上新格子是第幾幀、各畫面待了幾幀、
  卡住之後在哪些格子之間繞、ECL 段的變化序列（段@幀）。

★ 這幾行是這一輪能定位到「一扇門」的原因。在此之前，「跑到頂了」與
「卡在一扇門前面」在報表上看起來一模一樣。
