- 證據等級：撞門表 `exact`（DOS 與 PC-98 兩份原始位元組逐條讀完）；
  重放改良為**實測**（同一份路線、同樣 1500 幀，四種走法各量一次）
- 產物：`internal/dungeon/bash.go`、`internal/dungeon/bash_test.go`、
  `cmd/azure-bonds-game/keydriven_test.go`、`cmd/ecl-address-refs`、
  `gamepack/pack/00-core.json`（公會南側出口）、
  `gamepack/pack/10-content.json` ＋ 兩份 locale（酒館那兩個選項）、
  [spec 1026](1026-open-doors-table.md)

## 要回答的問題

README 一直帶著一句但書：主線**已經從開場走到結局**，但那是規則層走完的，
不等於拿鍵盤從頭玩到結局。這一輪把「拿鍵盤玩會停在哪」變成可以量的數字，
然後把量出來的第一個硬牆拆掉。

## ★★★ 第一個硬牆：力量 16 的角色永遠撞不開門

按鍵重放跑 1500 幀，隊伍停在 ECL 段 `0x02` 的 `(10,13)`，**762 幀零進度**。
逐格紀錄指出成因：那一格的南邊是一扇上鎖的門（`flags=2`），隊伍撞了 23 次，
**23 次全部失敗**。

遊戲內建的六個預設角色都是力量 16 的戰士。一次撞門是六個人各擲一次，
只要有一個人成功就開；照表算，力量 16 的成功率若是 3/6，一次撞門開門的機率
約 98%。**連續 23 次失敗的機率是 (1/64)²³ ≈ 3×10⁻⁴²**——這不是運氣，是表壞了。

成因在 `internal/dungeon/bash.go` 照抄公開 reference（`engine/ovr015.cs`）：

```csharp
else if (str >= 8 && str <= 15)  { ... }   // 先吃掉 15
else if (str == 15 || str == 17) { ... }   // 15 到不了這裡，16 不在這裡
```

⇒ **力量 16 一列都不符合，`worked` 永遠是 false**。

拿原始位元組核對（`dos overlay-14:0473h`）：

```
473:  3d 10 00        cmp    ax,0x10      ; 16
476:  7c 1b           jl     0x493
478:  3d 11 00        cmp    ax,0x11      ; 17
47b:  7f 16           jg     0x493
47d:  b0 01 50 b0 06 50   push 1 / push 6
483:  9a 4d 00 41 01  call   roll_dice
488:  3c 03           cmp    al,3
48a:  77 04           ja     0x490
48c:  c6 46 fa 01     mov    byte [bp-6],1   ; bash_worked := true
```

**是 16–17，而且門檻是 d6 ≤ 3。** PC-98 側同一列在 `overlay-14:0450h`：`cmp al,10h` ／ `jb` ／ `cmp al,11h` ／
`ja` ／ `cmp al,3` ／ `ja`，門檻與骰子完全相同（PC-98 用無號比較、DOS 用有號，
力量的值域內兩者等價）。兩份互相獨立的原始碼
都寫 16，reference 的 C# 是轉錄錯的。

同一段還抓到第二處：18／百分位 ≤ 50 在 reference 裡寫成「直接成功、事後補擲
一顆 d6」，原始位元組是 `cmp al,3` ＋ `ja`——**照擲，擲出 4 以上就是失敗**。

完整的表已經寫回 [spec 1026](1026-open-doors-table.md)（原本那一份把整欄
往上錯開了一列）。回歸測試 `TestBashDoorStrength16IsNotADeadRow`、
`TestBashDoorStrength15UsesTheEightToFifteenRow`、
`TestBashDoorStrength18NormalBranchRollsD6` 分別釘住三個邊界。

> ★ 這條收在 `AGENTS.md` §3：**reference 的反編輸出不是證據**。這一次的代價很
> 具體——一個轉錄錯的常數讓預設隊伍在第一扇上鎖的門前面永遠過不去，而所有測試
> 都是綠的，因為沒有人量過「按鍵玩得到哪裡」。

## ★★ 第二件事：路線重放從「往前找一段」改成「站在哪就查哪一格」

主線的決策用 `COAB_DECISION_LOG` 錄成 23,158 步（spec 1191）。原本的重放是
**滑動視窗**：從目前的進度往前找 `routeLookahead = 20` 個決策，比對得上就照它按。

視窗的問題不在大小，在**它假設重放和主線走的順序一樣**。按鍵這一場會多繞一些
路、少走一些捷徑，順序一旦錯開，視窗再大也只是把還沒用到的步驟提早吃掉。

改成兩張查表：

```
(ECL 段, x, y)  → 路線裡從這一格走出去的所有步驟，照錄下來的順序
選項簽章（以「｜」相接）→ 路線裡面對同一組選項的所有步驟
```

站在哪就查哪一格，跟中間繞了多遠無關。同一格被走過很多次時**輪流**取候選——
不能每次都取第一個（隊伍會在原地一直按同一個方向），也不能用過就永久劃掉
（主線在同一格來回經過很多次，用完之後隊伍就再也拿不到路線）。

### 實測（同一份路線、1500 幀）

| 走法 | 走過的格 | 記到的話 | 照路線按 | 走到的 ECL 段 |
|---|---:|---:|---:|---|
| 視窗（`routeLookahead = 20`）| 71 | 82 | 332 | `0x01` |
| 查表・用完就停 | 112 | 73 | 590 | `0x01` `0x02` |
| 查表・輪流 | 107 | 67 | 1,371 | `0x01` `0x02` |
| 查表・輪流 ＋ 撞門表修好 | **132** | **77** | 1,372 | `0x01` `0x02` |

⚠ **兩件事要分開看**：換成查表就讓隊伍第一次離開開場那一段（`0x01` → `0x02`），
這與撞門無關；撞門修好之後才從 107 走到 132 格，而且「路線帶不動」的次數
從 23 掉到 4。

幀數上限重量過：4,000 與 10,000 幀的結果與 1,500 幀**完全相同**（132 格、
最後一次踏上新格子在第 1,273 幀），所以預設維持 1,500。

## ★★ 第三件事：段界過不去，缺的是 game pack 少宣告一個出口

撞門修好之後隊伍停在 ECL 段 `0x02`，走過 132 格。**路線本身幫不上忙**——
錄路線的戰役測試是用 `state.EnterSegment(seg)` **直接切段**的（見
`cmd/dungeon-walk-probe`），所以那份紀錄是**每一段內部的移動 oracle，
不是一條從頭到尾的路**。段界怎麼過去，紀錄裡沒有。

用 `cmd/ecl-address-refs` 把 `ECL2/0x02` 的唯一一個 `NEWECL` 拆開：

```
0093 COMPARE 4C17h, 1      ; 第一次進這一段是 1（放開場動畫），之後被清成 0
0099 IF =  → 009A GOTO 821C
009E COMPARE 7ED5h, 0
00A4 IF =  → 00A5 EXIT     ; 沒有越界訊號就照常在這一段裡玩
00A6 CALL   C01E
00AA SAVE   FFh → 7EC9h
00B0 SAVE   00h → C04Ch    ; 到達 y := 0
00B6 SUBTRACT 0Ah, C04Bh → C04Bh   ; 到達 x := x − 10
00BF NEWECL 03
```

`7ED5h` 在整份 ECL corpus 裡**只被 `ECL2/0x03` 清成 0，沒有任何一支把它設成
非零**——它是引擎側的訊號：`RunDungeonExitLifecycle()`（`internal/game/state.go`）
在「一步走出 16×16 的地圖」時把它設成 1。

而 `MoveDungeon` 只有在 **game pack 宣告了那一格的 `external_exit`** 時才會走
越界那條路；沒宣告就照 `wrap` 繞回對邊。`tilverton.first-person`
（area 2／geometry block 1，也就是盜賊公會）**一個 `external_exit` 都沒宣告**，
所以按鍵往南走到 `(10,15)` 只會繞回 `y = 0`。

出口的座標有三份互相獨立的證據：

| 來源 | 內容 |
|---|---|
| `internal/game/ecl_integration_test.go` | 撞開 `(10,13)` 朝南那扇 `flags=2` 的門，往南走到 `(10,15)`，然後**明著呼叫** `RunDungeonExitLifecycle()` ⇒ 段 3、`(0,1)` 朝 4 |
| `cmd/azure-bonds-game` 的 `prepareSewerCheckpoint` | 把隊伍放到 `(10,15)` 朝 4，同樣明著呼叫 |
| ECL 本身 | 到達 `x := x − 10` ⇒ 到達 `x = 0` 對應出發 `x = 10`；到達 `y := 0` ⇒ 出發在南邊界 |

⇒ 補上 `tilverton.guild.south-to-sewers`（`x:10, y:15, direction:4`）。
**這是 pack 的資料缺口，不是引擎缺功能**：越界那條路早就寫好了，
只是沒有任何一格宣告自己是出口。

## ★★ 第四件事：搜尋才過得去的牆

進了下水道之後隊伍停在 `(10,12)`，路線說往西，四面卻是「北通東通南牆西牆」。
`tilverton.sewers.first-person` 的 `search_edges` 正好宣告了
`(10,12)` 朝西是一面 **`search_or_look` 才會出現**的邊。

主線的路線紀錄從那裡穿過去，因為錄路線那條測試是在規則層走的；按鍵這一場不搜尋
就永遠是一面牆，而畫面上看起來只是「走不動」。

⇒ 走法補一條：**路線說有路、按下去卻沒動**時，先按 `S` 開搜尋，再按 `L` 看一眼。
⚠ `ToggleDungeonSearch` 是**切換**，每次被擋都按會一開一關，一半的時間其實是關的
——所以只在搜尋還沒開的時候按。

⚠ 幀數重量過：4,000 與 10,000 幀與 1,500 幀**完全相同**。隊伍停在世界地圖上。

## ★ 量過但沒有採用：把路線裡重複的選法去掉

紮營選單在路線裡出現 **2,011 次，其中 2,008 次選的是「儲存」**——那是錄路線的
測試每到一個檢查點就存一份快照留下的痕跡，不是玩家的意圖。輪流取候選會被它稀釋掉，
於是隊伍在紮營選單裡存檔存到天荒地老（不設限那一版最後 700 幀就是這樣耗掉的）。

直覺上該把重複的選法去掉。實測（1500 幀，同一份路線，
cap ＝「同一個選單上同一個選法最多留幾筆」）：

| cap | 走過的格 | 記到的話 | 最深的段 |
|---|---:|---:|---|
| 1 | **168** | 112 | `0x50` |
| 2 | 134 | 99 | `0x03` |
| 3 | 114 | 87 | `0x03` |
| 6 | 113 | 91 | `0x03` |
| 12 | 137 | 120 | `0x51` |
| 不設限 | 137 | **124** | **`0x51`** ← 採用 |

⚠ **兩邊都不是線性的**，而且「走過的格」與「走到多深」往相反方向動：cap=1 的格數

## ★ 順手撿到的：整組英文選單一路演到玩家面前

按鍵這一場的「落回原文」判準原本只看 `Message` 與 `Prompt`，**不看 `Choices`**
——而選項正是玩家最常讀的那一塊。補上之後立刻抓到兩句：

```
選單 ASK ABOUT INJURIES｜IGNORE THEM
```

出處是提爾佛頓酒館：旁白「酒保有個黑眼圈，一隻手還吊著。」
（`tilverton.tavern.bartender-black-eye`，**旁白早就翻好了**）後面接的那組選項。
補上 `tavern_ask_injuries`／`tavern_ignore_injuries` 兩條 option rule 與譯文
（「詢問傷勢」「不理會」）。

★ 這一條的形狀值得記：**旁白翻好了不代表那一場翻完了**，而只查旁白的測試會一直是綠的。

同一條判準在試不同走法時又抓到四句：下水道巨魔殘塊那一場的
`MOVE ON`／`WATCH THE PIECES`／`BURN THEM`（旁白 `tilverton.sewers.troll-pieces`
也早就是中文），以及提爾佛頓酒館的 `HE TELLS TAVERN TALE # 37`。

⚠ 最後那一句露出一個**有分母的內容缺口**：Adventurer's Journal 收的酒館傳聞是
**1..62**，而 game pack 目前只宣告了 **16 則**（3、9、13、15、17、20、24、28、31、
43、44、45、52、56、59、60）。原作有兩種說法（`YOU OVERHEAR TAVERN TALE <n>` 與
`HE TELLS TAVERN TALE # <n>`），pack 的規則原本只覆蓋前一種。這一輪補上第 37 則
（「科米爾的阿祖恩國王正在提爾佛頓找他那個離家出走的女兒。」），
**剩下 45 則還沒接**。

## ★★ 第五件事：路線要有放手條件，而「有進展」不能算選單

不設放手條件時，隊伍在世界地圖的紮營選單裡**存檔存掉 700 幀**——路線在那個選單上
還有兩千筆候選，每一筆都是「儲存」。加一條：同一個選單從上一次有新東西到現在
出現超過 8 次，就不再問路線，交給啟發式（它會往下換一項）。

實測（4000 幀）三種處置：

| 處置 | 走過的格 | 記到的話 | 走到的段 |
|---|---:|---:|---|
| 不放手 | 137 | 126 | 6（多摸到 `0x51`，之後死在紮營選單）|
| **放手給啟發式** | 137 | **131** | 5 ← 採用 |
| 跳到「選法不同」的候選 | 137 | 103 | 5 |

⇒ 沒有一種全面贏。取「放手給啟發式」是因為句數最多、而且不會讓隊伍把大半場耗在
同一個選單裡；另一版的 `0x51` 是 `0x50` ↔ `0x51` 來回摸到的，不是留得住的進度。

### ⚠ 「有進展」的定義差點讓這一輪的結論整個是假的

第一版把「看到新的選單」也算成有進展。商店與神殿的選單把金幣與件數寫進選項
（「戰士（HP 0/0，0 GP）」），**數字一變簽章就變** ⇒ 幾乎每一幀都是「新選單」，
於是停滯偵測永遠不會觸發。報表印出「最後一次有新東西在第 24,672 幀」，
而那一場的格數、句數、段序列和第 1,500 幀的**一模一樣**。

改成只算新格子、新的一句話、新的段之後，同一場的答案是「第 942 幀」——
1,500、4,000、10,000 幀三種都一樣。

★ 形狀：**把「內容會變的字串」當成識別碼，會讓任何「還在動嗎」的偵測永遠回答「在動」。**
簽章要用穩定的部分，或者根本不要拿它當進展的來源。

## ★★★ 第六件事：一句沒翻的話就是一道牆

補完酒館傳聞之後，同一份走法、同一份路線，按鍵這一場從

	0x01 → 0x02 → 0x03 → 0x04 → 0x50

變成

	0x01 → 0x02 → 0x03 → 0x04 → 0x50 → 0x31 → …（0x50 ↔ 0x31 四趟）… → 0x32 → 0x33

——提爾佛頓 → 盜賊公會 → 下水道 → 火刀據點 → 世界地圖 → **哈普村 → 古熔岩洞 → 巫師塔**。
137 格／131 句 變成 **236 格／191 句**。

★ 這一段的因果值得寫清楚：**測試在遇到沒翻的字時 `t.Fatalf` 停下，於是那句話
就是整條路線的終點**。補完之前，4,000 幀與 1,500 幀的結果一模一樣——看起來像
「走法到頂了」，其實是「隊伍撞到一句沒翻的話」。**兩者在報表上長得一模一樣。**

⇒ 幀數上限重量：真正的進展在第 **1,937** 幀停下，2,500／3,000／4,000／10,000／
25,000 幀的結果完全相同，所以預設從 1,500 調到 **2,500**（跑一次約 10 秒）。

### 酒館傳聞：16 則 → 62 則，並擋掉一種會安靜講錯事情的錯

Adventurer's Journal 收的傳聞是 **1..62**，game pack 原本只宣告 16 則。原作有三種
說法：

	YOU OVERHEAR TAVERN TALE <n> .
	HE TELLS TAVERN TALE # <n>
	AS YOU CONSUME THE LOCAL EXCUSE FOR FOOD AND DRINK, YOU OVERHEAR TAVERN TALE <n>

pack 的規則只覆蓋第一種。這一輪把 62 則全部補上，前兩種各一條規則
（第三種與第一種共用同一條片段）。

⚠ **補的過程抓到一個原本就有的坑**：`MatchText` 是「第一個命中的規則就贏」而且
比對的是**子字串**——`YOU OVERHEAR TAVERN TALE 3` 是 `… TALE 30` 的前綴。
第 3 則的規則排在前面，所以第 30、32..39 共九則會顯示第 3 則的內容。
那不是錯誤訊息，是**一段讀起來完全正常、但講錯事情的中文**。

⚠ **不能靠尾隨空格斷詞**：第三種說法把編號放在**句尾**，後面沒有空格也沒有句點。
第一版的片段寫成 `"TAVERN TALE 3 "`，兩條既有的長路徑回歸立刻紅了。

處置：片段一律不帶尾隨空格，**只靠降冪排列**（62 的規則排在 6 前面），
單一位數的舊規則刪掉（新的同號規則已經涵蓋）。回歸測試
`gamepack/taverntales_test.go` 兩條：每一則的兩種說法都要對到同一段譯文、
而且 62 則的譯文兩兩不同——**逐則看沒有一則看起來是錯的，所以只能用「兩兩不同」抓**。

## ★★ 第七件事：`WHO` 選完人要把「有選到人」投影出去

補完法球那一場的譯文之後，隊伍卡在巫師塔一個**三個選項都叫「戰士」的選單**上，
提示是「請選擇角色」，按了五百多次都出不來。原作的腳本長這樣
（`ECL5/0x33:0C52`，用 `cmd/ecl-address-refs -opcode 0x39` 拆出來）：

```
0C52 WHO <提示文字>
0C67 COMPARE 7D00h, 1
0C6D IF =  → 0C6E GOTO 8C90      ; 有選到人就往下走
0C72 PRINTCLEAR <一句話>
0C8C GOTO 8C52                   ; 否則回到 WHO 再問一次
```

`7D00h` **不是普通格子**，是目前選中角色的欄位投影
（spec 624：`if char^[197h] <> 0 then 1 else 80h`，另有一個一次性旗標讓它讀成 0）。
remake 的 `WHO`（`internal/ecl/runtime.go` 的 `case 0x39`）把選中的名字寫進
`7C00h`、把索引記進 `selectedPlayerIndex`，**卻沒有寫 `7D00h`**——於是那個
`COMPARE` 讀到的是上一次 `LOAD CHARACTER` 留下的值，腳本自己的迴圈永遠出不去。

⇒ 選到有效隊員時補寫 `memory[0x7D00] = 1`。這與同一支檔案裡
`LOAD CHARACTER` 的既有作法同源（索引落在隊伍範圍內就寫 1）。

★ 形狀值得記：**腳本自己有重試迴圈的地方，缺一格投影不會報錯，會變成無限迴圈**，
而畫面上只是同一個選單。逐格紀錄把「按了 562 次、提示一直是『請選擇角色』」
印出來，才看得出那不是走法的問題。

## ★ 量過但沒有採用：把地圖編號記進路線

`recordMove` 原本只記 ECL 段。段與地圖不是一對一——重錄一次之後，16,048 個移動
裡有 **2,905 個**的段號與地圖編號不同。`Decision` 因此多了 `geo_block`，
查表也改成「路線檔有這一欄才帶」（早期錄的路線沒有這一欄，無條件帶著查會每一格
都查不到，而查不到是**安靜地沒有路線**）。

⚠ 但**重錄出來的那份路線反而讓隊伍走得更短**（246 → 93 格）。兩者的段分布與
相異格數幾乎一樣（2,086 對 2,088），差別在**同一格候選的順序**——而順序來自
錄製當時的測試執行路徑。這一輪改過的 game pack（公會南側出口）本身就會改變主線
錄到的路徑，所以新舊兩份不是同一條路。

⇒ 目前仍用先前錄的那一份。**這件事本身是個結論**：路線檔是**有版本的實驗輸入**，
不是可以隨手重生的衍生物；重錄會改變重放的結果，要當成一次獨立的實驗來量。

⚠ 重錄那一份也**露出一個新的卡點**：下水道天花板那一場
（`tilverton.sewers.something-on-the-ceiling`，「只有盜賊爬得上。有人要試嗎？」）
答「否」之後選單不會消失，隊伍在 `0x03` 原地按了一千多次。復現：
`COAB_ROUTE_JSON=workplace/campaign-frames/route-game.json`。尚未查成因。
