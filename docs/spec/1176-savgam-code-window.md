# 1176 — SAVGAM 的第四塊是**位元組定址**的程式碼視窗，先前匯出時整塊是 0

- 證據等級：`exact`（尺寸與位址範圍取自 spec 1163／1096）＋
  `measured`（全 corpus 對區 3 的存取逐處掃過）
- 上游：spec 1096（四個區的位址空間）、spec 1163（SAVGAM 的四塊 ↔ 四個區）

## 先前的行為

`internal/game` 匯出原版格式時，前三塊（區 0／1／2）從 session 的記憶體重編，
第四塊 `container.ECL` **只是把匯入來源那一份原封抄過去**：

```go
container.ECL = append([]byte(nil), s.savgamPrefix.ECL...)
```

⇒ 兩個可觀察後果：

- **新開的遊戲沒有匯入來源** ⇒ 那一塊 `make([]byte, 0x1E00)` ⇒ **整塊是 0**。
- 匯入之後隊伍換過段（`NEWECL`）再存檔 ⇒ 寫出去的是**匯入當時那一段**的
  位元組碼，不是現在這一段的。

## 這一塊與前三塊不一樣

| 塊 | 區 | 大小 | 定址 |
|---|---|---:|---|
| `Area1` | 0 `4B00h..4EFFh` | `0x800` | word |
| `Area2` | 1 `7C00h..7FFFh` | `0x800` | word |
| `Runtime` | 2 `7A00h..7BFFh` | `0x400` | word |
| **`ECL`** | **3 `8000h..9DFFh`** | **`0x1E00`** | **byte** |

⚠ **不能沿用前三塊的編碼。** `EncodeECLBank` 刻意跳過值為 0 的格子——原作分不出
「寫過 0」與「沒寫過」。位元組碼沒有這個問題，而且 `00h` 是真的指令（`EXIT`），
跳過會把程式打洞。所以第四塊有自己的一對 `DecodeECLCode`／`EncodeECLCode`，
**0 照收**。

## ★ 量測：CoAB 的 ECL 不改自己的位元組碼

`cmd/ecl-cell-refs -range 8000-9DFF` 掃出 3,012 處，opcode 只有三種：

| opcode | 處數 | 是讀還是寫 |
|---|---:|---|
| `GOTO` | 1,767 | 跳躍目標（讀）|
| `GOSUB` | 1,087 | 跳躍目標（讀）|
| `GETTABLE` | 148 | 表在區 3、**目的地在別區**（讀）|

**沒有任何一處把值寫進區 3。** 所以「自我修改的碼會遺失」在這一款遊戲不成立
——真正修掉的是上面那兩個後果，尤其「新開的遊戲匯出的存檔那一塊整塊是 0」。

⚠ 這是**這一款**的量測，不是引擎的性質。`GETTABLE` 的表就住在位元組碼裡，
表示引擎本來就把那一區當可定址記憶體；別的 Gold Box 遊戲寫進去也不奇怪。
所以 remake 這一側照通用做法存回去，不靠「反正沒人寫」這個前提。

## 匯入

`seedECLBanksFrom` 把第四塊換回目前這一段的程式碼視窗。

⚠ **原版存檔只存得下一份程式碼視窗**，所以呼叫端要確定目前這一段就是存檔當時
那一段。長度不符就整塊跳過，不要蓋半份上去。

## 明確不宣稱

- 沒有讀出原作把哪一段的位元組碼寫進第四塊的組語；結論是由尺寸、位址範圍與
  `GETTABLE` 讀得到區 3 三邊交叉出來的（spec 1163 同一個推導）。
- 沒有宣稱換段之後原版會不會把第四塊一起換掉。
