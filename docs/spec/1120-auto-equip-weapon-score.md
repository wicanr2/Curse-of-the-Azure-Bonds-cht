# 1120 — AI 自動換裝：評分算式、遠近取捨，以及類別表就是 `ITEMS` 成員

- 證據等級：`exact`（評分 `overlay-09:01542h`、挑選 `overlay-09:01681h`、
  半徑掃描 `overlay-24 entry#32` 三支 DOS 側逐條讀完；類別表的欄位對照由遊戲
  image 的 `ITEMS` 成員逐 byte 驗證）
- 對應工作項：`RE-07` → `ENG-08` 的「自動換裝」
- 上游 spec 1004（換裝主流程）、spec 1000（派生數值重算）、spec 683（類別表 `+0`）

## 類別表在哪

原作查的是 `DS:5CF6h`，每筆 16 bytes、以物品類別（`+2Eh`）為索引。那一段在常駐
資料段的 dump 裡是整片 `FF`——初始化資料在 `47E0h` 就結束了，`5CF6h` 落在 BSS。
它是**開機時從遊戲 image 的 `ITEMS` 成員載進去的**：2050 bytes ＝ 2 bytes 表頭
＋ 128 筆 × 16 bytes，正是 remake 的 `monster.ParseBaseItems` 已經在解析的那一份。

欄位一一對得上：

| 位移 | 內容 | 佐證 |
|---|---|---|
| `+0` | 裝備槽（0 ＝ 武器、1 ＝ 另一槽）| spec 683／1000；本支的兩個迴圈分支 |
| `+1` | 佔幾隻手 | spec 1004 |
| `+2`／`+3`／`+4` | 對**大型**目標的骰數／面數／加值 | spec 1011 |
| `+5` | 射速 | 只在「可發射」的位元下被加進分數 |
| `+0Ch` | 射程 | |
| `+9`／`+0Ah`／`+0Bh` | 對**小型**目標的骰數／面數／加值 | 匕首（類別 8）是 `1d3` 大／`1d4` 小 |
| `+0Dh` | 職業可用性遮罩，與角色 `+12Bh` 做 `and` | spec 1004 |
| `+0Eh` | 旗標 | 下表 |

`+0Eh` 的位元由 `ITEMS` 的實際資料驗證：

| 位元 | 意思 | 資料 |
|---|---|---|
| bit 3（`08h`）| **可發射**（有射速）| 18 個類別，含 41..47 的弓弩投石索、飛鏢（9）、85..88 等 |
| bit 4（`10h`）| **可投擲** | 13 個類別，含匕首（2）、短矛、手斧、飛鏢 |
| bit 0（`01h`）／bit 7（`80h`）| 選角色的哪一個彈藥槽（`+17Dh`／`+181h`）| |

飛鏢兩個位元都有——**發射與投擲不互斥**。

## 評分：`overlay-09:01542h`

`retf 8`。參數順序是 **`評分(角色, 物品)`**：`bp+0Ah` 讀角色欄位（`+185h`、
`+11Bh`、`+18Dh`），`bp+6` 讀物品欄位（`+2Eh`、`+32h`、`+36h`、`+3Dh`、`+3Eh`）。
Turbo Pascal 由左至右推參數，位址高的先宣告。

開頭把類別表整筆搬進區域變數（16 bytes），之後每個 `bp-xx` 都是 `記錄[位移]`：

```pascal
分 := 記錄[+9] * 記錄[+0Ah];                               { 對小型的平均傷害 }

if 有號(物品^[32h]) > 0 then 分 := 分 + 物品^[32h] * 8;    { 魔法加值權重 8 }
if 有號(記錄[+0Bh])  > 0 then 分 := 分 + 記錄[+0Bh] * 2;

if 物品^[2Eh] = 55h then                                   { 某個特定類別 }
    if (角色^[18Dh]^[0Ah] <> NIL) and (有號(目標^[0E9h]) > 0) then
        分 := 8;                                           { 覆蓋，不是累加 }

if 記錄[+0Eh] and 08h <> 0 then 分 := 分 + (記錄[+5] - 1) * 2;   { 射速只對發射類有意義 }
if 記錄[+1] <= 1 then 分 := 分 + 3;                        { 單手加分 }
if 角色^[185h] + 記錄[+1] > 3 then 分 := 0;                { 手不夠 }

if (物品^[3Eh] = 84h) and ((物品^[3Dh] and 0Fh) <> 角色^[11Bh]) then 分 := 0;
if 物品^[3Dh] = 53h then 分 := 0;
if 物品^[36h] <> 0  then 分 := 0;                          { 詛咒 }
```

`角色^[11Bh]` 是**陣營**（spec 1102 已解讀），所以物品效果碼 `84h` 那一條是
**陣營限制**：低四位是要求的陣營，對不上就一律不裝。

容易寫錯的地方：

- **`分 := 8` 是覆蓋**（`mov byte ptr [bp-2], 8`）。
- **手數界線是 `> 3`**，不是換裝主流程用的 `> 2`／`< 2`。呼叫這一支之前主流程
  已經把已裝備物品的手數扣掉了，所以這裡的 `+185h` 是「其他東西佔掉的手」。
- 三個歸零條件在最後而且**沒有 else**，任一成立就一定是 0。
- `+32h` 與 `記錄[+0Bh]` 的門檻是**有號**比較，`記錄[+1] <= 1` 是無號。

## 掃鏈與兩個候選：`overlay-09:01681h`

```pascal
for 每件物品 q（走 +2Ah 的鏈）do begin
    if byte[5CF6h + q^[2Eh]*10h] = 0 then begin            { 只看武器槽 }
        if byte[5D03h + q^[2Eh]*10h] and 角色^[12Bh] = 0 then 繼續;   { 用不了 }
        分 := 評分(角色, q);
        f  := byte[5D04h + q^[2Eh]*10h];
        if ((f and 08h <> 0) or (f and 10h <> 0)) and (分 > 分A) then 最佳A := q;
        if  (f and 08h = 0)                      and (分 > 分B) then 最佳B := q;
    end
    else if byte[5CF6h + q^[2Eh]*10h] = 1 then begin       { 另一槽 }
        if byte[5D03h + q^[2Eh]*10h] and 角色^[12Bh] = 0 then 繼續;
        if 有號(q^[32h]) >= 0 then 分 := q^[32h] + 1 else 分 := 0;
        if 分 > 分C then 最佳C := q;
    end;
end;
```

投擲武器**兩組都進**（bit 4 有、bit 3 沒有 ⇒ 兩個條件都成立），因為它近戰也能用。

## 遠近取捨

```pascal
彈藥 := NIL;  f := 0;
if 最佳A <> NIL then begin
    f := byte[5D04h + 最佳A^[2Eh]*10h];
    if f and 10h <> 0 then 彈藥 := 最佳A;                  { 投擲：自己就是彈藥 }
    if f and 08h <> 0 then begin
        if f and 01h <> 0 then 彈藥 := 角色^[17Dh];
        if f and 80h <> 0 then 彈藥 := 角色^[181h];
    end;
end;
有彈藥 := (彈藥 <> NIL) or (f = 0Ah);

投擲就緒 := (最佳A <> NIL)
            and (byte[5D02h + 最佳A^[2Eh]*10h] > 1)        { 射程 > 1 }
            and (f and 14h = 14h);

if (最佳A <> NIL) and (分A > 分B div 2) and 有彈藥
   and (投擲就緒 or (<overlay-24 entry#32>(角色, 1) = 0)) then
    選 := 最佳A
else
    選 := 最佳B;
```

★★ **門檻是 `分A > 分B div 2`，不是 `分A > 分B`。** 原作明顯偏好遠程：遠程只要
贏過近戰分數的一半就會被選走。寫成 `>` 會讓 AI 幾乎不用弓。

`overlay-24 entry#32(角色, 半徑)` 是**半徑內敵方戰鬥員的數量**：它掃出候選、
用 `overlay-24 sub_25B0`（`+197h = 0 ⇒ 1，否則 0`，也就是「對面那一隊」）過濾、
壓縮清單後回傳筆數。所以 `= 0` 就是**沒有人貼身**。

## 詛咒的裝備換不掉

```pascal
可換 := 1;
if 角色^[151h] <> NIL then
    if (角色^[151h] = 選) or (角色^[151h]^[36h] <> 0) then 可換 := 0;
```

`+36h` 是物品節點的詛咒旗標（開發者自己的欄位名就叫 `cursed`，spec 1011）。
同一個檢查在第二槽（`+155h`）也出現一次。

## remake 這一側

`internal/monster/autoequip.go`：`ScoreWeaponForAutoEquip` 與
`ChooseAutoEquipWeapon`，輸入是 `ItemRecord` ＋ `BaseItem` ＋ `AutoEquipCharacter`。
類別表直接用 `BaseItemCatalog`，不需要另外匯出資料。

同一輪把 `BaseItem.IsMissileWeapon`／`IsThrownWeapon` 改成讀 `+0Eh` 的位元。
先前是「類別 41..47」與「只有飛鏢」的列舉，會漏掉 11 個發射類與 12 個投擲類
——那些武器在戰鬥中原本被當成近戰。

接線在 `internal/game/auto_equip.go`，跑在 AI 回合開頭。原作的換裝屬於 AI 模組
（`COMPTACT`），所以它管的是「這一回合由電腦操作的人」——**包含開了快速戰鬥的
隊員**，手動操作的隊員不會被換裝。

兩個角色側的輸入是從已解讀的欄位推出來的，不是新猜的：

- **職業可用性遮罩**（`+12Bh`）由角色的職業組出位元，對照沿用
  `BaseItem.UsableByMask` 早就記著的那一組（法師 1、牧師 2、盜賊 4、戰士 8…）。
- **兩個彈藥槽**（`+17Dh`／`+181h`）＝ 裝備槽區塊的第 11 與第 12 格：
  區塊從 `+151h` 起、每格 4 bytes，`17Dh` 與 `181h` 剛好落在那兩格。
  所以「有沒有彈藥」＝「有沒有裝備中的物品，其類別表 `+0` 是 11 或 12」。

`+185h`（佔手數）在評分時傳 0：主流程在掃描之前已經把每件已裝備物品的手數
全部扣回去了。欄位保留是為了對得上原作的算式。

## 明確不宣稱

- 沒有宣稱類別表 `+6`（`ACAdjustment`）／`+7`／`+8`／`+0Fh` 的語意。
- 沒有宣稱 `+0Eh` 的 bit 1／bit 2 是什麼；`f and 14h = 14h` 照整組比對，
  `f = 0Ah` 也照數值比對。
- 沒有宣稱物品類別 `55h`、物品 `+3Dh = 53h`、`+3Eh = 84h` 的 `84h` 本身是什麼
  效果，只知道 `84h` 那一條的低四位要對上陣營。
- 沒有宣稱目標 `+0E9h` 是什麼。
- 沒有宣稱 PC-98 側的對應函式逐條相同——spec 1004 量過主流程 451 條相似度
  1.000，本支的評分與取捨段沒有單獨比對。
- 沒有宣稱怪物也會自動換裝：接線只對隊伍側生效，因為怪物的物品鏈還沒進到
  `Fighter`。那是資料來源的缺口，不是規則的。
- 沒有宣稱盾牌那一槽會被換上：本支算得出分數，但換上去要動派生數值重算的另一段。
