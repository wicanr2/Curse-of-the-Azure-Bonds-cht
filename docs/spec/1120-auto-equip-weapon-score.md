# 1120 — 自動換裝的評分算式，以及物品類別表不在執行檔裡

- 證據等級：`exact`（評分那一支 DOS 側 `overlay-09:01542h` 逐條讀完，
  `retf 8`）／`negative`（`DS:5CF6h` 在常駐資料段是未初始化區，附正對照）
- 對應工作項：`RE-07` → `ENG-08` 的「自動換裝」
- 上游 spec 1004（換裝主流程）、spec 1000（派生數值重算）、spec 683（類別表 `+0`）

## 評分：`overlay-09:01542h`

spec 1004 把它記成「回傳一個 byte 的評分，本規格不宣稱它怎麼算」。IDA 只認出
前 13 個位元組（`push bp` 到第一條 `les`），所以那一支在函式清單裡看起來是個
空殼；直接對 `overlay-09.bin` 線性反組譯才看得到完整的 317 條。

參數順序與 spec 1004 寫的**相反**：`bp+6` 讀的是物品欄位（`+2Eh` 類別、
`+32h`、`+36h` 詛咒、`+3Dh`、`+3Eh`），`bp+0Ah` 讀的是角色欄位（`+185h` 佔手數、
`+11Bh`、`+18Dh` 戰鬥狀態）。Turbo Pascal 由左至右推參數 ⇒ 位址高的先宣告 ⇒
真正的簽章是 **`評分(角色, 物品)`**。

開頭先把類別表整筆搬進區域變數：

```pascal
記錄 := 複製16bytes(ds:[5CF6h + 物品^[2Eh] * 10h]);   { 區域變數 bp-12h }
```

之後每一個 `bp-xx` 都是 `記錄[bp-12h 起算的位移]`。算式：

```pascal
分 := 記錄[+9] * 記錄[+0Ah];

if 有號(物品^[32h]) > 0 then 分 := 分 + 物品^[32h] * 8;
if 有號(記錄[+0Bh])  > 0 then 分 := 分 + 記錄[+0Bh] * 2;

if 物品^[2Eh] = 55h then                                   { 某個特定類別 }
    if 角色^[18Dh]^[0Ah] <> NIL then                       { 目前有目標 }
        if 有號(目標^[0E9h]) > 0 then 分 := 8;             { 覆蓋，不是累加 }

if 記錄[+0Eh] and 08h <> 0 then 分 := 分 + (記錄[+5] - 1) * 2;

if 記錄[+1] <= 1 then 分 := 分 + 3;                        { 單手加分 }

if 角色^[185h] + 記錄[+1] > 3 then 分 := 0;                { 手不夠 }

if (物品^[3Eh] = 84h) and ((物品^[3Dh] and 0Fh) <> 角色^[11Bh]) then 分 := 0;
if 物品^[3Dh] = 53h then 分 := 0;
if 物品^[36h] <> 0  then 分 := 0;                          { 詛咒 }
```

幾個容易寫錯的地方：

- **`分 := 8` 是覆蓋不是累加**（`mov byte ptr [bp-2], 8`）。類別 `55h` 那一段
  把先前算出來的分數整個丟掉。
- **手數的界線是 `> 3`**，不是 spec 1004 主流程用的 `> 2`／`< 2`。兩個數字各自
  出現在不同的位置，不要統一。呼叫這一支之前主流程已經把**已裝備**物品的手數
  扣掉了，所以這裡的 `+185h` 是「其他東西佔掉的手」。
- `+32h` 與 `記錄[+0Bh]` 的門檻用**有號**比較（`jle`），`記錄[+1] <= 1` 用的是
  無號（`ja`）。
- 三個歸零條件寫在最後且**沒有 else**，所以任何一個成立就一定是 0，
  不論前面加了多少分。

`記錄[+9] * 記錄[+0Ah]` 是類別表裡的另一組骰數 × 面數（spec 1011 已認的
`+2`／`+3` 是**對大型目標**那一組）。本規格不宣稱 `+9`／`+0Ah` 是對哪一種體型。

## `DS:5CF6h` 那張表不在執行檔裡

想照 spec 1111 的作法把類別表匯出來，結果是**整片 `FF`**：

```
5CF6h 起連續 100 筆 16 bytes → 全部 FF FF FF …
```

正對照三項，確認不是 dump 壞了或位址算錯：

| 檢查 | 結果 |
|---|---|
| 法術屬性表 `37DAh + 1*10h` | `00 01 06 00 06 00 0A 04 00 04 01 02 0A 01 00 00`（＝ 祝福，spec 1111 對得上） |
| 法術名稱表 `27BDh + 1*29h` | `05 'Bless'`（Pascal 短字串，長度正確） |
| 常駐資料段的 `FF` 連續區 | **`47E0h`..`8F00h`**，唯一一段 ≥ 256 bytes 的 |

`5CF6h` 落在那一段裡 ⇒ 它是 **BSS**，執行檔映像裡沒有內容，執行時才填。
再對兩平台 36 個 overlay 的完整反組譯掃一次 `5CF6h`..`5D04h`：**81 處全是讀取，
一處寫入都沒有**——這也符合「整批載入」（用遠指標搬，立即數裡看不到位址）。

所以自動換裝現在缺的不是算式，是**那張表的來源**：要先找出開機時把它填進去的
那一次載入，才有辦法把 16 bytes × N 筆匯出成 game pack 的資料。

## remake 這一側

**還沒接**。理由不是算式不明（本規格已經是 `exact`），是**輸入不存在**：
評分的每一項都要查類別表，而類別表還沒有來源。硬接會變成一支永遠拿不到資料的
函式，覆蓋報告上看起來像做完了。

接上之前要先關掉的是「`DS:5CF6h` 是從哪一個檔案讀進來的」。

## 明確不宣稱

- 沒有宣稱類別表 `+5`／`+9`／`+0Ah`／`+0Bh` 各是什麼欄位，只知道它們怎麼進算式。
- 沒有宣稱物品類別 `55h`、物品 `+3Dh = 53h`、`+3Eh = 84h` 分別是什麼。
- 沒有宣稱角色 `+11Bh` 是什麼（只知道要與 `物品^[3Dh] and 0Fh` 相等）。
- 沒有宣稱目標 `+0E9h` 是什麼。
- 沒有宣稱 PC-98 側的對應函式逐條相同——spec 1004 量過主流程 451 條相似度
  1.000，本支沒有單獨比對。
