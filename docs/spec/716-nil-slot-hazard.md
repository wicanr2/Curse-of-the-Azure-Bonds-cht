狀態：`READY`。等級：`exact`。日期：2026-08-14
掃描範圍：整個 DOS `overlay-22`。

> 本輪原本要把 `4791h`／`20E1h`／`3EE2h`／`2F5Eh` 當成新判讀寫進台帳，被護欄擋下

## 問題

spec 681 早已從「計數 ＋ 第 1 筆」的形狀推出 DOS 的目標陣列基底，spec 709 再從
`1C39h` 的迴圈獨立確認了一次。而 `1C39h` 之類的 opcode 會把不合格的目標
**寫成 `NIL` 而不動筆數**。所以走訪 `[7431h + k×4]` 的函式必須自己檢查 `NIL`。

`overlay-22` 裡取用這個陣列（`les 暫存器, [di+7431h]`）的地方共 **16 處**。
用 `scripts/nil_check_scan.py` **以取用點為單位**（不是以函式為單位）掃，
往回看 14 條指令內有沒有 `or ... [di+7433h]`：

| | 處數 |
|---|---|
| 前方有 NIL 判斷 | 7 |
| 前方沒有 | 9 |

沒有的 9 處：

```text
10D2h 內 119Dh、11B8h      （spec 719，模式 4 建清單）
1C39h 內 1C77h            （spec 709，篩選）
22B4h 內 22F0h、2338h、2361h（spec 715，Sleep，三處）
3804h 內 3851h            （spec 718，通用影響 N 個）
4A8Fh 內 4AEEh            （spec 724，恐懼）
5AA8h 內 5B4Dh            （spec 725，區域吐酸的類別比對迴圈）
```

`5AA8h` 那一處正是第一版漏掉的：那支函式的另一個迴圈（`5C1Bh`）有檢查，
以函式為單位掃時整支被算成「有檢查」。

**這份清單是「需要人工確認」而不是「確定有缺陷」**：窗格是固定 14 條，
用別種寫法（例如先搬進區域變數再判斷）一樣會被列進來。目前逐條讀過而確認
真的沒有任何檢查的是 `1C39h`、`22B4h`、`4791h`、`5AA8h` 的迴圈 A。

## 後果

`NIL` 是 `0000:0000`。`les di, [di+7431h]` 之後取 `es:[di+0E5h]` 會讀到
**中斷向量表**的內容（實模式下 `0000:00E5h`）。讀是不會當掉的，但拿到的是
當時的向量值——**同一段腳本每次跑的結果可能不同，而且不會有任何錯誤徵兆**。

寫入更嚴重：spec 656 已經記過另一支在同樣情況下會**寫進中斷向量表**。

## 已知會留下 `NIL` 的來源

| 出處 | 動作 |
|---|---|
| `1C39h`（spec 709） | 篩掉不符合的目標 |
| `24CDh`（spec 709） | 狀態 1 時清第 1 格 |
| `4194h`（spec 714） | 同上 |
| `22B4h`（本輪確認，spec 715） | Sleep 扣不起 HD 的目標 |
| `4822h`（spec 711） | 把筆數夾小（不是寫 `NIL`，但同樣讓陣列與筆數不同步） |
