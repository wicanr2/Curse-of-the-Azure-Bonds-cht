# 第六百九十一輪：`DS:5D02h` 的 16 bytes 一格物品表

狀態：`READY`。等級：`exact`。日期：2026-08-14
位置：DOS `overlay-24` 的 `2828h`、`3018h`、`305Bh`。

## 表的形狀

`3018h` 與 `305Bh` 用同一個算式取值：

```text
k  := 角色^[151h]^[2Eh]          ← 先解一層 far 指標，再取它的 +2Eh
di := k shl 4                    ← 一格 16 bytes
byte [5D02h + di]                ← 欄位 A
byte [5D04h + di]                ← 欄位 B（同一格的 +2）
```

`shl 4` 定死了**一格 16 bytes**，兩個基底差 2 定死了**欄位 A 在格內 +0、
欄位 B 在格內 +2**，整張表從 `DS:5D02h` 起。索引沒有上界檢查。

## `3018h`：欄位 A > 1

```text
if 角色^[151h] = NIL then 回傳 0                  ← 兩個 word 同時為零才算 NIL
if byte [5D02h + k shl 4] > 1 then 回傳 1 else 回傳 0
retf 4
```

比較是 `jbe`，**無號**。

## `305Bh`：再加驗欄位 B 的兩個位元

```text
if 3018h(角色) = 0 then 回傳 0
if (byte [5D04h + k shl 4] and 14h) = 14h then 回傳 1 else 回傳 0
retf 4
```

`14h` ＝ bit 2 與 bit 4，而且是 **`and` 之後比對等於 `14h`**——兩個位元要同時
成立，不是「任一成立」。寫成 `!= 0` 會多放行一半的情況。

`305Bh` 先呼叫 `3018h` 再自己重算一次 `k`，沒有共用中間結果。

## `2828h`：把 `+18Dh` 指到的結構清掉四個 byte

```text
角色^[18Dh]^[3] := 0
角色^[18Dh]^[0] := 0
角色^[18Dh]^[7] := 0
角色^[18Dh]^[6] := 0
回傳 1（常數）
retf 4
```

`+18Dh` 是 far 指標。四次寫入**各自重新載入 `arg_0` 再解一次 `+18Dh`**，沒有
暫存。清的順序是 3、0、7、6——不是遞增，重寫時照著抄沒有意義，但若那四個
byte 之間有觸發關係則順序要留。

## 跨平台位移

`docs/audit/cross-platform-field-offsets.json` 記載角色紀錄 `+14Ch..+1A6h`
是 DOS ＝ PC-98 − 1，所以：

| DOS | PC-98 |
|---|---|
| `+151h` | `+152h` |
| `+18Dh` | `+18Eh` |

引用到 PC-98 側時要換算，直接照抄會差一個 byte。

## 明確不宣稱

- `DS:5D02h` 那張表的長度、其餘 14 個 byte 的用途。
- `+151h` 指向什麼、它的 `+2Eh` 是什麼編號。
- `+18Dh` 指向什麼、被清掉的四個 byte 是什麼。
- 三支各自的呼叫端與用途。
