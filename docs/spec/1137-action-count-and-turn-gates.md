# 1137 — 動作計數與累計轉向擋住什麼；背後攻擊的三段 AC

- 證據等級：`exact`（`+0Fh`／`+12h` 的讀寫由 36 個 DOS overlay ＋常駐段全掃，
  且每一處都要求前 20 bytes 內有 `les …, es:[… + 18Dh]` 才計入；
  `sub_14E8` 的三段分支逐條讀完）
- 上游 spec 786（誰寫這兩格）、spec 1010／1019／771（三處讀者的既有出處）、
  spec 1136（這一格是怎麼被翻出來的）

## 一、★ 先修正普查口徑：`es:[暫存器+位移]` 認不出「指到哪個記錄」

第一版掃描找 `es:` 前綴、`mod=01`、`disp8 ∈ {07h, 0Fh, 12h}` 的存取，得到七處讀者。
**那個口徑會把所有走遠指標的記錄混在一起**：

| 位置 | 實際讀的是 | 出處 |
|---|---|---|
| `overlay-23` `1A36h` | **角色記錄** `+12h` ＝ 智力**基準值**（`+10h + i×2`，i=1）| 屬性重算 `sub_18D8` |
| `overlay-31` `028Ah`／`0298h`／`03A2h`／`03B0h` | **視線狀態記錄** `+12h`／`+14h` ＝ Bresenham 的步進 | spec 854 |

判準是**先看到指標怎麼來的**：只有前面有 `les …, es:[… + 18Dh]` 的才是 22 bytes
的戰鬥狀態記錄。加上這道限制之後的完整普查：

| 欄位 | 寫 | 讀 |
|---|---:|---:|
| `+03h` 先攻 | 9 | 18 |
| `+07h` 保留的機會攻擊 | 5 | 1 |
| `+09h` 目前面向 | 6 | 18 |
| **`+0Fh` 動作計數** | **3** | **4** |
| **`+12h` 累計轉向** | **3** | **2** |

## 二、`+0Fh` 動作計數：三個寫、四個讀

寫：`overlay-08` `0279h`（回合開始清 0，spec 804）、`overlay-13` `0908h`（清 0）、
`overlay-13` `1958h`（`inc`，就是 spec 786 的轉向函式 `sub_194A`）。

⇒ **它數的是「這一回合轉向過幾次」**，而轉向發生在移動與攻擊的前置。

四個讀者：

| 位置 | 所屬 | 條件 | 擋住什麼 | 出處 |
|---|---|---|---|---|
| `0BC4h` | `sub_95A` 離開接觸 | `+3 <= 0` **且** `+0Fh <> 0` | 成立才做 90° 扇形的面向檢查；**不成立就無條件打** | spec 1010 |
| `19FBh` | `sub_19D8` 攻擊動作 | `+0Fh < 2` 且旗標為 0 | 成立才轉向面對目標 | spec 1019 |
| `295Ch` | `sub_28C3` 武器類別白名單 | `+0Fh > 1` | 額外攻擊的其中一道 | spec 771 |
| **`16B2h`** | **`sub_14E8` 攻擊結算** | **`+0Fh > 1`** | **背後攻擊的第一道** | 本規格 |

## 三、`+12h` 累計轉向：三個寫、兩個讀

寫：`overlay-08` `0286h`（回合開始清 0）、`overlay-13` `0915h`（清 0）、
`overlay-13` `19CE h`（`sub_194A` 的 `(舊值 + 差) mod 8`）。

讀只有兩處：`19B7h` 是 `sub_194A` 自己那次讀改寫（不是閘），
真正的閘只有 **`16DFh`**（`sub_14E8`，`+12h > 4`）。

## 四、★ `sub_14E8`（攻擊結算）的三段 AC

`sub_14E8` 的堆疊框：`[bp+14h]/[bp+16h]` ＝ **攻擊者**（它的 `+18Dh^[4]` 是這一
輪的攻擊次數，驅動後面的迴圈）、`[bp+10h]/[bp+12h]` ＝ **防禦者**（AC 從它身上讀）。

```pascal
[bp-18h] := 0;
if <sub_28C3>(攻擊者, 防禦者) <> 0 then begin        { 武器類別白名單，spec 771 }
    AC := 防禦者^[19Bh] − 4;                          { ← 第三段 }
end else begin
    if 防禦者^[18Dh]^[0Fh] > 1 then                   { ★ 這一輪轉過不只一次 }
        if <sub_29A2>(攻擊者, 防禦者) = 防禦者^[18Dh]^[09h] then
            { 「攻擊者→防禦者」的方向等於防禦者的面向 ⇒ 防禦者背對著你 }
            if 防禦者^[18Dh]^[12h] > 4 then           { ★ 累計轉向 > 4 }
                背後 := 1;
    if 背後 <> 0 then [bp-18h] := 1;
    AC := 防禦者^[19Ah + [bp-18h]];                    { ← 第一／第二段 }
end;
<sub_1CE2>(攻擊者, 防禦者, var AC);                    { 命中判定吃這個 AC }
```

三段同時決定送進 `sub_1CE2` 的 AC，以及一個 0／1／2 的攻擊種類碼（`[bp-17h]`）：

| 段 | 條件 | AC 來源 | 種類碼 |
|---:|---|---|---:|
| 0 | 其餘 | 防禦者 `+19Ah` | 0 |
| 1 | 動作計數 > 1 ＋ 背對 ＋ 累計轉向 > 4 | 防禦者 `+19Bh` | 1 |
| 2 | `sub_28C3` 成立（白名單武器 ＋ 它自己那組條件）| 防禦者 `+19Bh` − 4 | 2 |

⇒ **兩個欄位一起構成「背後攻擊」的判準**：光是背對不夠，防禦者還要在這一回合
**轉過不只一次**且**累計轉向超過 4**。

## remake 現況

三個閘目前都沒有對應欄位：`Fighter` 沒有戰鬥中的面向（`IconDirection` 是圖示
方向不是 `+09h`）、沒有動作計數、沒有累計轉向，`ActionState` 也沒有。
要接需要三件事，缺一件就會變成「照感覺補一個規則」：

1. 戰鬥面向 `+09h`（誰寫、什麼時候寫——`sub_194A` 與 `sub_19D8` 各寫一次）。
2. 動作計數與累計轉向兩個欄位，以及它們**唯一的增量點**（`sub_194A`）。
3. 防禦者的第二個 AC 欄位 `+19Bh`（spec 1000 算得出來，但 remake 只投影一個 AC）。

## 明確不宣稱

- 沒有宣稱 `+19Ah`／`+19Bh` 各自的語意；本規格只證明**攻擊結算依這三段挑其中一個**。
  （spec 1000 讀過兩者的算法、spec 1044 對過兩平台的位移，語意仍未定。）
- 沒有宣稱 `[bp-17h]` 那個 0／1／2 的種類碼由誰讀。
- 沒有宣稱 `sub_29A2` 的完整簽章；本規格用到的是「兩個角色遠指標 → 方向碼」，
  由 `sub_19D8`（spec 1019）與本支的呼叫形狀共同確認。
- 沒有宣稱 `overlay-13` `0908h`／`0915h` 那一組清 0 屬於哪個流程。
