# 1193 — 走訪未達成的三種成因

狀態：`READY`（分類已實作，數字由 `cmd/cell-reachability` 產生）

## 問題

走訪可達性報表說：259 個分派索引，實跑與冷走的聯集是 214。剩下的 45 個只是
一個數字——看不出**要補路線、要補劇情旗標、還是根本補不了**。這三種的處置
完全不同，混在一起就不知道下一步該做什麼。

## 三種成因

判準用的是**純幾何**（`CanMoveDungeon`），不跑 ECL：走過去又被劇情推回來那種
不算「走不到」——那是內容不是幾何，混進來會讓分類失去意義。

| 成因 | 判準 | 要做什麼 |
|---|---|---|
| 站得上去，但從段入口走不到 | 那個地形碼出現在**某個連通分量**的格子上，但不在入口那一塊 | 補路線：從那一塊自己的入口格另外走一趟 |
| 圖上有，但四面都不通 | 地形碼只出現在**沒有任何可通行邊**的格子上 | 走路永遠站不上去；要嘛靠事件傳送，要嘛它本來就不是玩家會站的格子 |
| 圖上根本沒有這個地形碼 | 分派表有這一格，整張地圖掃過去沒有 | 分母裡的死索引，補不了也不用補 |

目前：**44 / 1 / 0**。

★ **死索引是 0，所以未達成全部都是真的待辦**，不是分母灌水。這一點本來只能猜。

## 走路的上限

「站得上去」的索引有 **258**（259 減掉那個四面不通的）。

★ **那才是走訪這條路的天花板，不是 250。** 把分派索引總數當目標，會讓永遠差的
那一格看起來像還有事情可做。目前的 214 是天花板的 83%。

## 為什麼「站得上去」要另外算

一張圖常常不是一整片。巫師塔每一層在 GEO 上是**獨立的小房間**，層與層之間只靠
樓梯**事件**接（spec 1161）——從入口用走的永遠到不了別層。所以：

- 「從段入口走得到」是**下界**：它看不到那些要靠事件才進得去的房間。
- 「站得上去」是**上限**：只問幾何，不問怎麼進去那一塊。

兩個都要，差額就是「要靠事件才進得去」的那些房間。

## 這個數字證明不了什麼

- 「站得上去」**不表示玩家到得了**：進到那一塊要靠事件，而事件要不要觸發是內容。
  它是上限不是預測。
- 分類完全不看 ECL，所以「站得上去但從入口走不到」裡混著兩種：幾何上斷開的，
  和**門擋著**的。要再分下去得看門的旗標。
- 分母仍然直接取自 `cell-sweep -index-json`，**這一支不重算**——兩邊各自算一定會
  漂（第一版自己算得到 299 而實測是 250，兩個數都自洽，放在一起就是假的覆蓋率）。

## 相關

- `cmd/dungeon-walk-probe`：`-walkable-json`（站得上去）、`-on-map-json`（圖上有）
- `cmd/cell-reachability`：`-walkable-cells`／`-on-map-cells`／`-json`
- `docs/audit/cell-reachability.md`
- spec 1161（巫師塔的房間是靠樓梯事件接的）

## 冷走要跑好幾種策略再取聯集

單一策略的結果**看起來都很合理**，但每一種都會被某一類岔路擋住：

| 策略 | 被什麼擋住 |
|---|---|
| 選單挑第一項 | **收費關卡**（下水道的奧提尤格要食物）——付不出去就進不去 |
| 選單挑最後一項 | 「要離開嗎」那種提示上直接走人 |
| 踏上去被事件搬走時**不從落點繼續** | 等於把「走上樓」記成「走到樓梯口」，靠樓梯才進得去的樓層永遠不會被走到 |

目前跑 8 種（選第 1／2／3／最後項 × 跟不跟傳送）取聯集。效果：

| 走法 | 冷走走得到的索引 | 聯集 |
|---|---:|---:|
| 只選第一項、不跟傳送 | 153 | 178 |
| ＋跟傳送 | 154 | 179 |
| ＋選最後一項 | 165 | 189 |
| ＋選第 2／3 項 | **179** | **193** |
| ＋選第 4 項 | 179 | 193（沒有變化，跑一趟多兩分半 ⇒ 收斂了） |

⚠ **跟傳送單獨看反而更差**：它讓 `ECL6/0x43` 的格子從 191 走到 235，但走訪順序
一變，某些 once-only 事件就在別的地方觸發，**索引反而少踩到兩個**。所以是取聯集
不是換一種——兩種互不涵蓋。

## 「門要劇情旗標」只解釋了其中 3 個

「站得上去，但從段入口走不到」這一類，直覺上的成因是**門要劇情旗標才開得了**：
冷走每一段都開一支新隊伍、沒有旗標，所以那些門對它永遠是牆。

`cmd/campaign-snapshot-walk` 直接驗了這個假設：拿主線在各段落存下來的 23 份快照
（就是一般的存檔格式，帶著那一刻的旗標），在那一段做同樣的多策略廣度優先走訪。

第一版用的是**段界**快照，23 份裡有 7 份讀回來停在荒野或地圖模式（`ECL4/0x22`
眼魔洞穴那一份就是）——那時的結論是「只有 3 個」，但**證據不夠**：走不了的那幾段
本來就沒被驗到。

於是讓主線在**第一次踏進每一段的地城時**也存一份（`captureInsideSegment`），
拿到 13 份**段內**快照，涵蓋 12 個有地形分派的 block **全部**。這一次每一份都
讀得回來也走得動（只有 `0x50` 世界地圖沒有地形分派，如實報出）。

結果：**只有 4 個索引是「非得帶旗標才走得到」的**。

⇒ 結論不變而且證據變強了：剩下的絕大部分**不是門的問題，是幾何**。那些房間要靠
樓梯／傳送事件才進得去，而那個事件要在**劇情的正確位置**才會觸發——不是「隊伍
有沒有旗標」的問題，是「隊伍當下在不在那個位置」。帶著旗標從段內任何一點開始走，
都走不進去。

⚠ 段內快照每一段只存**第一次**進地城的那一刻：存太多份會讓走訪時間乘上份數，
而同一段內旗標的差異對「走得到哪些格子」影響很小。

### 讀存檔取段號的陷阱

`Area.LastECLBlockID` 是存檔格式裡的欄位，但**遊戲跑的時候從來沒有人寫它**，
讀出來是 0——而 0 是一個**合法的 block 編號**，查下去會拿到完全不相干的地圖
而且不會報錯。段要跟 **ECL session** 拿（`State.CurrentECLBlockID`）。

## 邊界要記「(格子, 進入方向)」，不是只記格子

樓梯事件是**站對方向踏上去**才觸發的：`ECL5/0x33:090Ch` 用地形碼查表拿方向，
朝向不對就直接 `EXIT`——**畫面上什麼都不會發生**（spec 1161）。

三支走訪器原本都只用格子當 `seen` 的鍵。於是第一次從錯的方向踏上樓梯格，那一格
就被封死，另外三個方向永遠不會再試 ⇒ **靠樓梯才進得去的樓層永遠走不到**，
而報表只會顯示「那幾格走不到」，看不出是走法的問題。

改成邊界記 `(格子, 進入方向)`、「這一格去過沒有」另外記之後：

| | 修正前 | 修正後 |
|---|---:|---:|
| 巫師塔 `ECL5/0x33`（快照走訪）| 15 格／2 個地形碼 | **207 格／22 個地形碼** |
| 冷走走得到的索引（14 段合計）| 198 | **220** |
| 實跑踏到（250 的分母內）| 177 | **182** |

⚠ 聯集仍是 195：多出來的大部分落在 `0x33`／`0x25` 這些**不在分母裡**的段，
分母內多出來的那幾個又已經被另一把尺涵蓋。**修正是對的，但它不會讓聯集動** ——
這兩件事要分開講，否則下次會以為「走法沒問題，是內容不夠」。

## 分母本來漏了兩段，因為它們「冷進不去」

`cmd/cell-sweep` 是逐格實測，它每一段都**冷開一支隊伍**走進去。有些段的入口是
**一整段過場**——巫師塔是德拉坎德羅斯那一串、`ECL4/0x25` 是魔法商店那一段——
冷走完會停在**世界地圖**而不是地城，於是那些段整段被記成「進不去」，
**它們的格子從來不在分母裡**。

那些格子玩家真的走得到。所以 `cell-sweep` 加了一條路：冷進不去時改從
**主線的段內快照**進（`-snapshots`，`captureInsideSegment` 產生）。

⇒ 分母 **250 → 259**、聯集 **195 → 204**、覆蓋率 78% → 79%。（後來每段多存幾份快照，聯集再到 **210**、81%，見下。）

⚠ 從快照進的段，隊伍**帶著主線那一刻的旗標**，和其他段冷進的隊伍不是同一個起點。
報表在那一段標明，不要混在一起讀成「冷開就走得到」。

### 一個安靜的坑：`note` 是「這一段掃不了」

第一版把來源註記寫進 `blockSweep.note`。但 `note` 的語意是**這一段掃不了**——
渲染時看到它就整段跳過。結果一段**掃得好好的**段從報表裡消失，分母從 259 掉回
250，**而且沒有任何錯誤訊息**。註記要用自己的欄位（`fromSnapshot`）。

## 一段要存**好幾份**快照，不是一份

從**同一個起點**走，走得到的就是那一塊連通分量。`ECL4/0x22`（眼魔洞穴）那種段，
主線是靠劇情事件一路被帶進去的——只存「第一次進段」那一份，等於只拿到入口那一小塊
（16 格／2 個索引）。

改成沿路每隔幾次觀測存一份（每段最多 6 份）之後：

| | 一段一份 | 一段多份 |
|---|---:|---:|
| 冷走走得到（259 分母內）| 194 | **205** |
| 聯集 | 204 | **210** |
| 未達成 | 54 | **48** |
| `ECL2/0x02` | 3 | **7**（滿） |
| `ECL4/0x22` | 7 | **9** |

⚠ 份數不能無上限：走訪時間是「份數 × 選單策略數」。目前是「每段最多 6 份、
每份至少隔 6 次觀測」。

### 再多存幾份沒有用（量過的）

「同一塊裡多存幾份走出來的東西幾乎一樣」本來只是註解裡的一句斷言。把上限從
6／6 提到 12／3 之後：

| | 6 份／段 | 12 份／段 |
|---|---:|---:|
| 快照份數 | 114 | 204 |
| 走出來的 (block, 地形碼) | 329 | **333**（一個都沒少）|
| 冷走走得到 | 205 | 206 |
| **聯集** | **214** | **214**（沒動）|
| 走訪時間 | 約 20 分 | 約 27 分 |

⇒ 維持 6／6。**要再提高覆蓋率不能靠多存快照**——多出來的份數落在同一塊連通
分量裡，走出來的是同一批格子。

### 冷走也可以帶劇情旗標了

⚠ 冷走（`cmd/dungeon-walk-probe`）每一段都開一支新隊伍、**沒有任何劇情旗標**，
所以要旗標才開得了的門對它永遠是牆——那正是「站得上去但走不到」的主要成因。

spec 1195 為了量接縫做的 `State.SeedHandoffMemory` 正好補上這一塊：主線在每一段
的**到達取樣**就是那一刻的劇情旗標，鋪上去再走，門就開得了。

| | 不鋪旗標 | 鋪上旗標 |
|---|---:|---:|
| 冷走走得到的分派索引 | 220 | **225** |
| 冷走走得到（259 分母內）| 205 | **217** |
| **聯集** | 214 | **224** |
| 未達成 | 44 | **34** |
| 覆蓋率（走得上去的 258 格內）| 83% | **87%** |

⚠ 這仍然**不是**「玩家走得到」的證明，是**帶著劇情旗標的幾何可達性**——和
`cmd/campaign-snapshot-walk` 同一個口徑，只是入口從快照換成「乾淨進段 ＋ 鋪旗標」。

⚠ **不給 `-arrivals` 不會報錯**，只會少幾格——而少幾格和「那裡本來就走不到」
長得一模一樣。用法已經把那一步寫進去。

#### 從主線站過的格子起走：聯集 224 → 233

到達旗標解掉的是**門**那一類。剩下的成因是另一種：**幾何上斷開**——那些格子站得
上去，但從段入口沒有任何一條路走得過去，原作是靠**樓梯／傳送事件**把隊伍搬進去的
（巫師塔每一層在 GEO 上就是各自獨立的小房間）。

旗標鋪再多也開不了那種「門」，因為根本沒有門。但主線的路線紀錄
（`COAB_DECISION_LOG`）裡有隊伍**真的站過**的座標——從那裡起走就在那一塊連通分量
裡了。

| | 到達旗標 | ＋ 路線起點 |
|---|---:|---:|
| 冷走的分派索引 | 225 | **256** |
| 冷走走得到（259 分母內）| 217 | **232** |
| **聯集** | 224 | **233** |
| 未達成 | 34 | **25** |
| 覆蓋率（走得上去的 258 格內）| 87% | **90%** |

★ 只從「那一格的索引第一輪沒走到」的位置起走：其餘起點只會把同一塊連通分量再走
一遍，時間翻倍而一格都不會多。567 個相異起點因此只跑了少數幾趟。

⚠ 這證明的是「**劇情把你放到那裡之後，那一塊走得完**」，不是「你走得到那裡」——
走得到那裡是主線紀錄本身的事。口徑仍然是**帶著劇情旗標的幾何可達性**。

> ⚠ 這一版第一次跑出來是「索引 225 → 256，但可達性一格都沒動」。原因是新的那一輪
> walk 寫在 `records` 收集**之後**——`walk.reached` 長了，輸出檔沒長。
> **同一份資料的兩個出口要一起看**：只看其中一個會得到「有效但沒有用」這種
> 不可能的結論，而它看起來只是「這條路沒用」。

#### 段內再多取幾份旗標：量過了，沒有用

到達那一份只代表**剛進段那一刻**的旗標。主線在一段裡走著走著才會開的門（拿到
鑰匙、打完某一場、觸發某個開關）在那一刻還沒開，所以下一個想法是**沿路多取幾份
旗標**，每一份各走一趟再取聯集。

⚠ 這和前面那個「一段存好幾份**快照**」是**不同的問題**：那個比的是**入口位置**
（同一塊連通分量裡多存幾份沒用）；這個比的是**旗標的時間點**，冷走的入口始終是
段入口，只有門開不開會變。所以前一個的負面結果不能直接套用到這裡——要另外量。

量出來：

| | 只有到達那一份 | ＋ 段內 90 份 |
|---|---:|---:|
| 冷走的分派索引 | 225 | **228** |
| 冷走走得到（259 分母內）| 217 | 217 |
| **聯集** | **224** | **224** |
| 未達成 | 34 | 34 |
| 走訪時間 | 約 2 分 | 約 22 分 |

⇒ 多出來的三個索引**落在可達性分母之外**（那份分母是 13 個 block 的 259 個索引，
冷走涵蓋 14 段）⇒ **對這一列一格都沒加**，而時間是十倍。

⇒ 取樣改由 `COAB_FLAG_SAMPLE_DIR` 單獨開關，**預設不產生**；`cmd/dungeon-walk-probe`
的聯集邏輯留著（有樣本就用），換一組取樣策略時還用得上。

### 快照有**兩個**產生者，而且目錄要先清掉

⚠ 主線不經過的段（提爾佛頓那三段，`0x01`／`0x02`／`0x03`）的段內快照**只來自
路線測試**。`cmd/campaign-snapshot-walk` 的用法本來只寫了主線那一支，照著跑會
少掉三段——**而且不會有任何錯誤訊息**：報表只是少幾列，看起來和「那幾段沒東西
可走」一模一樣。

⚠ 走訪讀的是**目錄裡的每一個檔**，不是這一次產生的那些。沿用舊目錄會把上一次
（不同程式、不同測試組合）留下的快照一起走進來，得到一個**比現在的程式真的產
得出來還大**的數字。用法已改成「先 `rm -rf` 再跑兩支測試」。

> 這兩件事是查一個矛盾查出來的：把上限調高之後走出來的組合反而**變少**
> （329 → 274）。原因不是調高沒用，是拿來比的那個舊目錄裡有 23 份現在的指令
> 產不出來的快照。**先確認兩邊是同一個東西產的，再比數字。**

## 「實跑踏到」本來漏掉了大半的步

那一欄的來源是**觀測迴圈**，不是每一步移動——走過去又馬上被劇情推走的格子
從來沒被取樣。報表自己標明了這是下界，但沒有辦法補。

`COAB_DECISION_LOG`（spec 1191）錄的是 `MoveDungeon` 的**每一次**呼叫，正好補上
那個缺口。`cmd/route-cells` 把 824 步移動的起點換算成 (ECL 段, 地形碼)，得到
119 個組合，併進「實跑踏到」：

| | 只有觀測迴圈 | ＋每一步移動 |
|---|---:|---:|
| 實跑踏到 | 191 | **198** |
| 聯集 | 210 | **214** |
| 未達成 | 48 | **44** |

⚠ 錄的是**起點**座標，所以最後一步的終點會漏掉——仍然是下界，只是密了很多。

⚠ 三個段（`0x04`／`0x12`／`0x21`）沒有地形分派，那 154 步換算不出地形碼；
它們本來就不在分母裡。
