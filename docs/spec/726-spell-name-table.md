# 第七百二十六輪：法術名稱表在 `DS:27BDh`，一格 41 bytes

狀態：`READY`。等級：`exact`。日期：2026-08-14
位置：DOS `overlay-22:6209h`（`retf 0Ah`：法術編號、訊息 far 指標、施法者 far 指標）。

## 名稱表

兩處都是同一個算式：

```text
di := 法術編號 × 29h
push ds ; push di + 27BDh
```

`29h` ＝ 41 ＝ **長度位元組 ＋ 最多 40 個字元**，和物品節點的名字欄位
（spec 696 `+00h`）寬度完全相同。所以

> `DS:27BDh` 是法術名稱表，一格 41 bytes，索引就是法術編號。

表本身在 resident 的資料段，不在 `overlay-22` 裡，所以 `scan_pascal_strings.py`
掃不到它——**法術名稱不在 `docs/audit/embedded-strings.md` 裡，中文化時要另外
處理這張表**。

## 兩種顯示模式

```text
if DS:4FBAh = 5 then                                    ← 一種畫面
    <overlay-24 entry#20>(施法者, '<名字> Casts a Spell'（CS:61F4h）, 0Ah, 1)
    <01A0:04CDh>(17h, 27h, 17h, 0)                      ← 清第 23 列
    <0542:0352h>(0, 17h, 0Ah, 0, 'Spell:'（CS:6202h）＋ 法術名)
else
    <01A0:04CDh>(16h, 26h, 12h, 1)                      ← 清一塊
    <overlay-24 entry#22（18F3h）>(施法者, 1, 13h, 0)    ← 在 (1, 19) 畫施法者名字
    <0542:0352h>(施法者^[0] + 2, 13h, 0Ah, 0, 訊息)      ← 接在名字後面
    <0542:0352h>(0, 14h, 0Ah, 0, 法術名)                ← 下一列
    <0542:0B33h>()                                       ← 阻塞（等按鍵）
    <overlay-24 entry#21>()
```

第一種把「`Spell:` ＋ 名稱」串成一行；第二種把施法者名字、訊息、法術名分成
兩列排。**只改其中一種的版面會讓另一種畫面錯位。**

## `施法者^[0] + 2` 又是一次 Big5 陷阱

`施法者^[0]` 是 Pascal 字串的長度位元組，也就是**位元組數**。名字從第 1 欄開始
畫，訊息接在 `長度 + 2` 欄——留一格空白。

換成 Big5 之後，`長度位元組` 仍是位元組數，而顯示寬度是它的一半（全形字兩個
位元組佔兩欄，剛好抵消）——**這一次反而不會錯**。

但 spec 693 `18F3h` 裡那個 `arg_4 + 角色^[0]` 是把 `'s` 直接接在名字**結尾的
下一格**，中間沒有空白；那裡全形字同樣佔兩欄，所以也對得上。

> 兩處重看之後結論要修正：**這種「欄位 ＝ 起點 ＋ 長度位元組」的算法對
> Big5 是成立的**，因為全形字元的位元組數與顯示欄數都是 2。spec 693 說它
> 「會少算一半」是錯的，已更正。真正的問題只剩 `'s` 這個後綴本身在中文裡不
> 存在。
