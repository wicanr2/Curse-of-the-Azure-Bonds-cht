## 付款拆成白金與金幣，完全對上幣值表

`+101h` 與 `+103h` 是角色錢包 `+0FBh ＋ j × 2` 的第 3 與第 4 格
（spec 858／863／875 定的順序：0 銅、1 銀、2 琥珀金、**3 金**、**4 白金**）。

```
白金 := 價 div 5;    零頭 := 價 mod 5;
```

**1 白金 ＝ 5 金幣**，與 spec 858 的換算係數一模一樣。
所以 `價` 的單位是**金幣**，付款時盡量給白金、除不盡的部分給金幣。

裝不下時（負重，spec 863 的 `far 1134h` 同一組常式）**多出來的白金退回
`DS:6F80h`**——那正是 spec 858／863 的第 4 格公用池（白金）。
零頭的金幣**沒有這個保護**，一律直接加上去。

## ⚠ 原版 bug：同一個欄位被要求同時等於兩個值

```asm
cmp byte ptr es:[di+2Eh], 49h
jnz short 走 ÷20
cmp byte ptr es:[di+2Eh], 1Ch     ; ← 同一個 +2Eh
jz  short 走 ×數量
```

兩次讀的都是 `物品^[2Eh]`（中間重新 `les di, [bp+arg_0]`，位址相同），
所以 `= 49h` 且 `= 1Ch` **永遠不成立**——
**`價 := 數量 × 價` 那條分支是永遠走不到的死碼**，
成疊物品一律走 `÷ 20`。

**兩平台一致**，不是反組譯問題。形狀上第二個比較應該讀別的欄位，
或兩個條件應該是 `or`。這與 spec 856（物品堆疊合併把三個效果欄位
跟自己比）是同一類的打字錯誤。

remake 若要重現原版售價，**照原樣保留 `÷ 20`**；要修的話得先決定
那兩個類別碼（`49h`、`1Ch`）本來想表達什麼。

## 賣價是基本價的一半

`物品^[3Ah]`（word）是基本價，`div 2` 之後才是店家出的價。
`物品^[39h]` 是數量、`+2Eh` 是類別碼——三個欄位都在 spec 832 的
物品節點裡，本支是它們第一次被當成價格用。
