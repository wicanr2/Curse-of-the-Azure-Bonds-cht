# 985 — 名字編輯的游標（只有 DOS 有）與 PC-98 的三平面圖層合成

- 證據等級：`exact`（兩支逐條讀完；參數位置由原始 bytes 確認）
- 作法見 spec 783

## `dos overlay-17:02724h`（122 條，`retf 4`）＝ `pc98 overlay-17:02DB7h` 的對應

⚠ `scripts/aligned_diff.py` 把這一支判成**單邊**，但它與 spec 976 讀的
`pc98 overlay-17:02DB7h` 是同一支：都是巢狀程序（`arg_0` ＝ 父層 `bp`）、
都用 `ss:[父bp − 37h/38h]` 當欄位編號、都是 `0..5` 屬性／`6` HP／`7` 名字
三分支。**配對工具漏了，不代表沒有對側**——同 spec 981 記的
「查詢回空不能當成不存在」。

```pascal
欄位 := ss:[父bp − 37h];
if (欄位 >= 0) and (欄位 <= 5) then                { 有號 }
    <overlay-19 entry#3>(反白 arg_2, 欄位)          { 六個屬性 }
else if 欄位 = 6 then
    <overlay-24 entry#3>(反白 arg_2, 12h, 4, DS:6506h)   { HP }
else if 欄位 = 7 then begin                         { 名字 }
    if 反白 <> 0 then begin
        <0542h:0311h>(名字長 ＋ 1, 1, 0, 1);        { 清底色 }
        <0542h:0352h>(1, 1, 0Dh, 0, 名字);          { 整個名字，顏色 0Dh }
        c := ss:[父bp − 3Fh];                       { ★ 游標位置 }
        if 名字[c] = ' ' then
            <0542h:0352h>(c, 1, 0Fh, 0, '%')        { CS:2722h，長度 1 }
        else
            <0542h:0352h>(c, 1, 0Fh, 0, Chr(名字[c]));
    end
    else
        <0542h:0352h>(1, 1, 0Ah, 0, 名字);          { 一般，顏色 0Ah }
end;
```

### ★ 游標是「把同一格用另一個顏色重畫一次」

DOS 在畫完整個名字之後，**再畫第三次**：只畫游標所在的那一格，顏色從 `0Dh`
換成 `0Fh`。那一格若是空白，改畫常數 `'%'`（`CS:2722h`，長度 1）——
空白沒有形狀，得換一個看得見的字模當游標。

⚠ 字型只有 64 個字模且索引是 `UpCase(c) mod 40h`（spec 937），
`'%'` ＝ `25h` 落在 `20h..5Fh` 這一段的自然位置。**本規格不宣稱那一格的字模
被畫成什麼形狀**（原版可能把它重繪成方塊或底線）。

### ⚠ PC-98 沒有這第三次繪製

spec 976 讀的 `pc98 overlay-17:02DB7h` 在同一個分支只做兩件事：
`0418h:0139h(名字長 ＋ 1, 1, 0, 1)` 清底色，然後用 `0Dh` 印整個名字。
**沒有游標那一格。**

| | DOS `02724h` | PC-98 `02DB7h` |
|---|---|---|
| 清底色 | `0542h:0311h` | `0418h:0139h`（同一支的兩平台位址） |
| 整個名字 | 顏色 `0Dh` | 顏色 `0Dh` |
| 游標那一格 | **再畫一次，顏色 `0Fh`；空白時畫 `'%'`** | **沒有** |

`0542h:0311h` ↔ `0418h:0139h` 的四個參數完全相同（`名字長+1, 1, 0, 1`），
是繼 `0542h:0352h` ↔ `0418h:0D17h`（spec 983）之後第二對確認的常駐孿生入口。

### 中文化

游標是**逐半形格**定位的（`c` 直接當欄，`名字[c]` 直接當字元）。
Big5 名字裡一個漢字佔兩個 byte／兩個顯示欄，
**`名字[c]` 會取到半個漢字**，畫出來是亂碼，而且游標只蓋住半格。
名字輸入要支援中文，這一段必須改成以字元為單位前進，
與 spec 978 的 `'_'` 逐 byte 替換屬同一類 DBCS 缺口。

PC-98 沒有這段程式碼，**所以 PC-98 版的名字輸入本來就看不到游標**——
中文化若以 PC-98 為底，等於直接繞過這個問題，但也少了游標。

## `pc98 overlay-16:00F17h`（121 條，`retf 8`）— 把一張圖疊上另一張

⚠ IDA 的 `arg_2`／`arg_6` 與 `[bp+6]`／`[bp+0Ah]` 是同兩個位置
（原始 bytes 已確認）。只有兩個遠指標參數，`retf 8` 對得上。
宣告順序是 `(來源 bp+0Ah, 目的 bp+6)`。

```pascal
每平面來源 := 來源^[0] × 來源^[2];          { 高 × 寬 }
每平面目的 := 目的^[0] × 目的^[2];

for i := 0 to 來源^[0] − 1 do                { 無號 }
  for j := 0 to 來源^[2] − 1 do begin
      for k := 0 to 2 do                     { ★ 三個像素平面 }
          目的^[17h ＋ k×每平面目的 ＋ i×目的^[2] ＋ j]
              := 目的^[…] or 來源^[17h ＋ k×每平面來源 ＋ i×來源^[2] ＋ j];

      目的^[13h]^[i×目的^[2] ＋ j]
          := 目的^[13h]^[…] and 來源^[13h]^[i×來源^[2] ＋ j];
  end;
```

### ★ 三個像素平面 OR、一個遮罩平面 AND

- **像素用 `or` 疊加**：來源的亮點會加到目的上，目的原有的點不會被清掉。
- **遮罩用 `and`**：兩張圖的「透明區」取交集——只有兩邊都透明的地方才still透明。

**平面數正好是 3**，與既有結論一致：PC-98 只用 B／R／G 三個平面 ⇒ 8 色。

### surface 版面再補一格

本支不讀 `+11h`（每張的位元組數），**自己用 `+0 × +2` 算**。
這正是 spec 977 記過的差異：`pc98 overlay-33:00508h` 的第二次 `Move`
也是用 `p^[0] × p^[2]`，而 DOS 兩次都用 `p^[11h]`。
兩處一致 ⇒ **PC-98 側「一個平面的位元組數 ＝ 高 × 寬」是通例，不是個案**。

累積到目前的 surface 版面：

| 位移 | 內容 |
|---|---|
| `+0`（word） | 高 |
| `+2`（word） | 寬（位元組） |
| `+8` | 張數 |
| `+11h` | 每張的位元組數 |
| `+13h`（dword） | 遮罩緩衝遠指標，單一平面、`高 × 寬` bytes |
| `+17h` 起 | 像素資料，**PC-98 是三個平面連續排列**，每平面 `高 × 寬` bytes |

### ⚠ 兩個沒有防護的地方

1. **完全沒有邊界檢查**：迴圈上界取自**來源**的高與寬，但寫入的是**目的**。
   目的比來源小就直接寫出界。
2. **尺寸為 0 會爆掉**：上界是 `來源^[0] − 1`，無號遞減後變成 `0FFFFh`，
   而迴圈條件是 `0 <= 上界`（無號）⇒ **零高或零寬的圖會跑 65536 圈**。

兩者 remake 都要補。

## 明確不宣稱

- 沒有宣稱 `'%'` 那一格的字模畫成什麼。
- 沒有宣稱 `ss:[父bp − 3Fh]`（游標位置）由誰維護。
- 沒有宣稱 `overlay-16:00F17h` 的呼叫端是誰、疊圖用在哪個畫面。
- 沒有宣稱 DOS 側有沒有對應的疊圖函式（DOS 的平面配置與 PC-98 不同）。
