# 驗證報告：`SEG-01` ECL block 轉移機制

- 日期：2026-08-20
- 範圍：主線分段驗證計畫的 `SEG-01`（「怎麼進去、怎麼出來」）
- 結論：**通過**。25 個 block 每一個的進出機制都說得出來，並有可重跑的產生器與回歸測試。

## 一、要回答的問題

分段驗證要把「一個 ECL block」當一段、「一條轉移邊」當一段交接。前提是
**每個 block 的進入邊與離開邊都要說得出來**。開工前的假設是「世界地圖進到各章
走的不是 `NEWECL`，那條邊不在靜態圖裡」。

## 二、做了什麼

1. 讀 `overlay-02:3772`（ECL 主迴圈）的分派段，逐條。
2. 讀世界地圖 hub（`ECL1/0x51`）的全部指令與它三張 `GETTABLE` 表的原始位元組。
3. 追 `4BF2h`／`4CA1h` 兩格在引擎側的存取點（`docs/audit/ecl-shared-cells.md`）。
4. 用 `ecl.TraceGraph`（**會跟 `ON GOTO` 目的地**）對整份 image 重算轉移圖。

## 三、結果

| 問題 | 答案 | 證據 |
|---|---|---|
| 誰決定載哪一個 block | 主迴圈讀 `bank0 +1E4h`（LastECL），載完寫回去 | `overlay-02:3772` |
| 新遊戲從哪開始 | `LastECL = 0` ⇒ block `1`，`DS:4FBCh ≠ 0` 時是 `0x52`（開場） | 同上 |
| 轉移怎麼發生 | `20h NEWECL` 改 `LastECL` | spec 1141 |
| 有幾條邊 | **47 條**，25 個 block，只有 `0x52`（開場）與 `0x43`（結局）沒有出邊 | `cmd/ecl-block-graph` |
| 世界地圖 hub 的出邊 | `0x50` → 6 條、`0x51` → 6 條 | 同上 |

**開工前的假設是錯的。** 進入邊就是 `NEWECL`，一直都在圖裡——看不到是因為
量錯了。

## 四、量錯在哪（這一項比結論更值得記）

`docs/audit/ecl-event-catalog.md` 的可達性**不跟 `ON GOTO`／`ON GOSUB` 的目的地**
（它自己的「限制」一節寫了，但那句話沒有被讀進計畫）。後果：

| | 事件目錄 | `ecl.TraceGraph` |
|---|---:|---:|
| `NEWECL` 邊 | 21 | **47** |
| 沒有出邊的 block | 9 | **2** |
| `ECL1/0x51` 的可達指令 | 85 | **726** |
| 全部可達指令 | 4,222 | 14,177 |

⇒ **兩個世界地圖 hub 在那份圖裡看起來一條出邊都沒有**，而它們是整條主線的樞紐。
拿它下「這個 block 沒有出口」的結論，會得到一個自洽但錯的計畫。

處置：`cmd/ecl-block-graph` 產生正確的圖，並附一條回歸測試
（`TestBlockGraphShape`）——它特別檢查兩個 hub 的出邊 ≥ 5，可達性再退化會直接紅。

## 五、順帶更正的一個斷言

`+342h`（City，ECL `4CA1h`）**不是拿來載區域的**。它唯一的引擎側讀取點
`overlay-10:0FC7` 把它抄進 `DS:4A14h` 之後，接的是三支**野外戰場地形生成**
（spec 749）。世界地圖 hub 用 `GETTABLE` 填它，是為了讓那一格的野外戰鬥長得像
那個地方。

推導鏈原本是「共用格子表列出 `overlay-10:0FC7` 存取 `+342h`」→「所以 City 驅動
載入區域」。**中間那一步是猜的**，讀了那支函式就翻掉了。
