# 驗證報告：`SEG-12` 47 條 `NEWECL` 邊的交接

- 日期：2026-08-20
- 範圍：主線分段驗證計畫的 `SEG-12`（段與段之間的交接）
- 結論：**通過**。47 條邊每條一個測試，全部接得起來。

## 一、一條邊做的事

`TestEveryNewECLEdgeHandsOff` 對每條邊：

1. 進來源段，`SavePartyFile` 存一份快照；
2. 用一份新的 `State` 讀回快照；
3. 帶著**來源 block 當 `LastECL`** 進目的段——這是 spec 1141 的轉移機制本身；
4. 驗目的段的 initial lifecycle 跑得完、停在宣告的 block、隊伍跟得過來、
   所在層級與宣告一致、模式不是不該出現的那幾個。

邊的來源是 `docs/audit/ecl-block-graph.md` 的段落清單（由 `cmd/ecl-block-graph`
產生，另有 `TestBlockGraphShape` 驗它與工具一致）。條數對不上 47 就直接紅。

## 二、⚠ 這一條擋的是什麼、不擋什麼

**擋得住**：某條邊的目的段從那個前段進不去、initial lifecycle 中途出錯、
過完邊停錯 block、隊伍在交接時掉了。

**擋不住**：照劇情真的走到那裡會如何。來源用的是**段的入口**狀態，不是段走完
的結束狀態；後者要等 `SEG-10` 把每段拆成自己的測試之後才存得到。

## 三、反向對照

把目的 block 換成不存在的 `0xEE`，測試立刻紅在第一條邊上——這條測試會失敗，
不是永遠綠的裝飾。47 個子測試逐條列出，紅的時候看得出是哪一條邊。

## 四、明確不宣稱

- 沒有宣稱來源段在執行期真的會發出那個 `NEWECL`；邊的清單來自靜態走訪
  （`ecl.TraceGraph`，會跟 `ON GOTO`）。
- 沒有宣稱目的段在不同前段進來時行為相同——本輪只驗它進得去。
- 沒有宣稱隊伍的 HP／記憶法術／物品跨邊不變；只驗人數（那是 `SEG-31`）。
